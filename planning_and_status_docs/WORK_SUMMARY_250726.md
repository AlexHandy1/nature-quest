# Work Summary — 25 July 2026

## What was built

- **`prototypes/scripts/e2e_walk_spike_clustering.py`** — new standalone prototype fork of `e2e_walk_spike_polygon.py` (per the "copy, don't edit a checkpoint" convention). Answers: is a density-grid cluster of a species' occurrences a better representation of "where a walker would actually find this species" than the current plain average-of-all-occurrences centroid (`hotspot_lat`/`hotspot_lon` in `rank_species()`)?
  - **Kept**: NL query → LLM structured-output species selection (Haiku, one call per run), taxon resolution/merge logic, GBIF common-name lookup, user-supplied polygon areas.
  - **Stripped** (explicit scope cut to save time/cost, not needed to answer the clustering question): the batched per-species description call and the structured narrative call — both removed entirely, along with their Wikipedia-lookup dependency.
  - **New**: `cluster_species_hotspot(occurrence_points, grid_n=5)` — adaptive N×N density-grid clustering. Divides a species' own occurrence bounding box into an N×N grid (cell *size* adapts to that species' spread; N itself, default 5, is a fixed/arbitrary resolution, not tied to real-world distance — this trade-off is deliberately surfaced in logging, not hidden). Buckets each occurrence point into a cell by `(row, col)` index, picks the cell with the most points, and returns that cell's own centroid as the new hotspot. Falls back to the plain average when a species has fewer than 3 occurrences (`MIN_POINTS_TO_CLUSTER = 3`) — clustering is meaningless at 1-2 points. Guards the zero-range-axis edge case (e.g. all points sharing one latitude) by treating that axis as a single bin rather than dividing by zero.
  - **New**: `rank_species()` now keeps every occurrence's raw `(lat, lon)` per species (for map plotting and clustering input) and computes both `avg_lat`/`avg_lon` (old) and `hotspot_lat`/`hotspot_lon` (new, from clustering) per species.
  - **New**: `log_cluster_comparison()` — prints, per species: total obs count, grid dimensions, cell size in meters (via `haversine_m`), how many cells were occupied, the winning cell's point count, and the straight-line distance between the old average and the new cluster centroid ("avg↔cluster").
  - **New**: `generate_cluster_comparison_map()` — replaces the old adventure-style quest-log map with a plain comparison map: raw occurrence dots per species (small circle markers, species-colour-coded), the winning grid cell's bounds (dashed rectangle), the **old** average centroid (grey circle marker) and the **new** density-cluster centroid (numbered coloured marker) shown side by side so the difference is visually inspectable, not just asserted from logs. Written to `prototypes/artifacts/clustering_comparison_map.html`.
  - **New**: `--polygon-file` CLI flag accepts a raw GeoJSON Feature/Polygon exactly as pasted from `https://www.latlong.net/polygon-drawer` — no manual coordinate editing needed. `geojson_polygon_to_wkt_and_center()` handles the conversion; GeoJSON's `[lon, lat]` coordinate order already matches GBIF WKT's own `"lon lat"` convention, so **no flip is needed** here (unlike `server_polygon.py`'s `polygon_points_to_wkt()`, which does flip Leaflet's `[lat, lon]` browser points). The polygon's own vertex average becomes the waypoint-ordering start point — a separate, already-accepted use of "centroid" (start point only, not species display) from the one this prototype is testing. No flag defaults to the same Retiro polygon every other prototype script uses.
  - **New**: `--grid-n` CLI flag (default 5) to experiment with grid resolution without editing code.
  - **Deliberately no browser draw tool / server / HTTP layer** — this stays a single CLI script (unlike `server_polygon.py` + `index_polygon.html`). User's explicit call: keep it simple since the map output is the thing being inspected, not the walk UX; "draw your own area" is satisfied instead via `--polygon-file`.
  - **Deliberately no unit tests** — user's explicit instruction this session: "no TDD is required for this, its a standalone prototype," overriding this codebase's usual light-TDD-for-deterministic-logic norm (`test_intent_query_spike.py`'s precedent). Validated instead via an ad-hoc inline sanity check (not persisted to the repo) plus a live end-to-end run.

## What was explored / learnt

- **Confirmed live run** against the default Retiro polygon, query `"Today I want to learn about plants"`: selected Bellis perennis, Chelidonium majus, Allium neapolitanum, Potentilla indica, Viburnum tinus. Per-species avg↔cluster distances ranged **55m to 332m** — a real, visible difference, not noise. Total cost $0.0043, 6.0s wall time (one LLM call only, GBIF/common-name lookups free).
- **Ad-hoc sanity check** (inline `python -c`, not saved as a test file) confirmed: a 7-point two-cluster case correctly centers on the denser 5-point sub-cluster rather than the overall average; a 2-point case correctly falls back to the plain average unchanged; an all-same-latitude case doesn't crash and still splits correctly along longitude.
- **Grid resolution (N) clarified during `/grill-me`**: N is the number of divisions per axis over a species' own occurrence bounding box — e.g. N=5 → `lat_step = (max_lat - min_lat) / 5`, `lon_step = (max_lon - min_lon) / 5`, giving 25 cells. Critically, **N is fixed/arbitrary, not derived from the polygon's or species' real-world geographic size** — only the *cell size* adapts (scales to that species' bounding box), not the *count* of divisions. This means "same spot" can mean ~20m for a tightly-packed species and ~400m for a widely-scattered one, at the same N=5. Decided (for this round) to make this trade-off visible via logging (cell width/height in meters per species) rather than solving it now with a physical cap — explicitly deferred, not resolved.
- **Which "centroid" this targets, disambiguated early** (two candidates existed in the codebase): the per-species `hotspot_lat`/`hotspot_lon` averaging in `rank_species()` (this one — "showing observations on the map") vs. `polygon_centroid()` in `server_polygon.py` (the user-drawn polygon's own vertex average, used only as the waypoint-ordering start point). Confirmed with the user: **only the former** is in scope. The latter's naive-averaging behaviour is untouched and reused as-is in this fork's `--polygon-file` centre calculation.
- **Waypoint ordering re-explained mid-session** (worth recording since it's non-obvious and the user asked twice): `order_waypoints()` is a **greedy nearest-neighbour walking tour**, not "sort all species by distance from the centre." Only the *first* stop is chosen by nearness to the drawn area's centre point; every stop after that is chosen by nearness to the *previous stop* (the "current position" moves along with the tour), not the original centre. Worked example from the live run above:
  1. From centre `(40.4153, -3.6844)` → nearest is **Allium neapolitanum** → visited 1st.
  2. From Allium's location → nearest remaining is **Bellis perennis** → visited 2nd.
  3. From Bellis's location → nearest remaining is **Viburnum tinus** → visited 3rd.
  4. From Viburnum's location → nearest remaining is **Potentilla indica** → visited 4th.
  5. Last one left, **Chelidonium majus**, visited 5th by elimination.
  Total route: 1090m (1.09km). This greedy-tour heuristic and "sort by distance-from-centre" only coincide when species happen to sit in neatly expanding rings around the centre — they can diverge whenever the nearest-to-centre species isn't also nearest to whatever gets visited next. This script's only change to `order_waypoints()` versus the original: it now walks between each species' **density-cluster** hotspot instead of the old averaged one — the old average locations are shown on the map purely for visual comparison, they don't participate in ordering.

## Decisions and trade-offs

- **Decision:** Target the per-species `hotspot_lat`/`hotspot_lon` averaging (not `polygon_centroid()`) as the thing to replace with clustering. **Why:** the backlog item's wording ("showing observations on the map," "densest area of observations") and the user's confirmation that averaged species markers have "looked odd visually in a few examples" both point to the species-marker location, not the polygon-vertex start point. **Trade-off:** none — the two are genuinely separate concerns, this just avoids conflating them.
- **Decision:** Adaptive N×N density-grid binning (not DBSCAN or k-means) for the clustering method, N=5 as a starting default. **Why:** user's own hypothesis — low observation counts (e.g. 5 occurrences of one plant) are the common case here, and DBSCAN's `eps`/`min_samples` tuning is unpredictable at that scale, whereas a grid degrades gracefully (worst case, points spread across many near-empty cells, close to the plain average). Also matches this codebase's stated preference for hand-rolled, dependency-free logic in prototypes (`haversine_m` precedent). **Trade-off:** N is fixed/arbitrary rather than tied to real-world cell size (see "what was learnt" above) — accepted as a known, logged limitation for this round, not solved now.
- **Decision:** Strip the per-species description and narrative LLM calls from this fork entirely. **Why:** explicit user instruction — this round is only testing the clustering method, and those calls add real cost/time on every iteration without helping answer the clustering question. **Trade-off:** the rendered map has no species description/journal panel; popups show only name, common name, total observation count, and old-vs-new distance.
- **Decision:** Show both the old (average) and new (density-cluster) markers on the same map, plus raw occurrence points and the winning grid cell's bounds. **Why:** user wanted the trade-offs visually inspectable, not just asserted from logs — this also doubles as a first pass at a real end-user feature idea (showing total occurrence count per species), which the user explicitly flagged wanting in the production build too, independent of the clustering decision itself.
- **Decision:** CLI-only, no server/browser draw-tool layer (unlike `server_polygon.py` + `index_polygon.html`). **Why:** explicit user call — keeps this fork simple since the map output is what's being inspected, not the walk UX. "Draw your own area" support is preserved via `--polygon-file` accepting raw GeoJSON (as pasted from `https://www.latlong.net/polygon-drawer`) instead of a live Leaflet.draw tool. **Trade-off:** no live in-browser drawing; testing a new area requires generating/pasting a GeoJSON file first (acceptable to the user, who anticipated needing help generating these boundaries from the polygon-drawer tool).
- **Decision:** No unit tests for this script. **Why:** explicit user correction this session ("no TDD is required for this, its a standalone prototype") — overrides the general codebase norm of light TDD for deterministic prototype logic (`test_intent_query_spike.py`'s precedent). Validated instead via one ad-hoc, non-persisted sanity check plus a live run. **Trade-off:** the clustering logic's correctness rests on that one manual check and eyeballing the rendered map, not a regression-proof test suite — acceptable for a throwaway prototype per the user's framing.
