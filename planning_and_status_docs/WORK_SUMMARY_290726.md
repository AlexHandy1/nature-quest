# Work Summary — 29 July 2026

## What was built

- **`prototypes/scripts/e2e_walk_spike_full_validation.py`** — new standalone prototype combining `e2e_walk_spike_clustering.py` (density-cluster hotspots, user-drawn polygon support, GBIF scale guard/retry) and `e2e_walk_spike_server.py` (common-name/Wikipedia enrichment, batched description, structured narrative, quest-log map render). Splits the combined pipeline into two functions instead of one:
  - `resolve_species_query(user_query, polygon_wkt, center_lat, center_lon, grid_n, intent_model, override=False)` — STEPS 1-5 (NL query → intent → resolve taxa → fetch/rank with density-cluster hotspots → nearest-neighbour waypoint ordering). Cheap: one LLM call + free GBIF calls. Returns `{"status": "ok" | "needs_clarification", "message": str | None, "species": [...], "notes": [...]}`.
  - `run_pipeline(species, user_query, description_model, narrative_model, notes, open_browser)` — STEPS 6-8 (common name, Wikipedia, batched description, narrative, quest-log map render), given an already-resolved species list. Expensive: 2 more LLM calls, Wikipedia lookups.
  - CLI runnable standalone: `python prototypes/scripts/e2e_walk_spike_full_validation.py "<query>" [--polygon-file ...] [--grid-n N] [--override]`.
- **`prototypes/scripts/server_full_validation.py`** — new Flask server, port 5052 (alongside `server.py`'s 5050 and `server_polygon.py`'s 5051). Two endpoints: `POST /gbif-species-query` (STEPS 1-5 only, returns the validation verdict) and `POST /run-walk` (STEPS 6-8 only, given a species list). Stateless — species data round-trips through the client between the two calls (`species_to_client()`/`species_from_client()` conversion helpers), no server-side session state.
- **`prototypes/web/index_full_validation.html`** — new frontend, fork of `index_polygon.html`. Adds one new state to the existing draw/form/loading/map flow: the **needs_clarification card** (shown only for case 1/4), with "Try a different query" (client-side, no call) and "Show most-observed instead" (re-calls `/gbif-species-query` with `override: true`) buttons. Case 2/3 notes render as a banner inside the map view. Also restores the raw-occurrence-points click-to-reveal feature from `e2e_walk_spike_clustering.py` (see below).
- **`planning_and_status_docs/FEATURE_IDEAS_BACKLOG.md`** — added a "Shareable walk link" entry, surfaced while weighing stateless vs. server-side-cached designs for the new validation endpoint.
- **`prototypes/README.md`** — added §10 documenting this prototype (full detail below); updated "What's proven vs. still open" to reflect what got resolved this session (rare-query handling, sparse-area UX) vs. what's still open (case-3 actual marker merge, extending the validation gate to the other server flows).

## What was explored / learnt

- **Reviewed prior UX flow in full before designing anything** (`server.py`, `e2e_walk_spike_server.py`, `web/index.html`, and the polygon-drawing equivalents) after an initial attempt to jump straight into a state-machine prototype was correctly pushed back on. This surfaced that today's actual behaviour differs from what a first read of the backlog suggested:
  - **Total failure** (zero species anywhere): `run_pipeline()` returns `None`, server turns it into a generic error, frontend shows a plain red banner on the landing form — exits the quest experience entirely.
  - **Partial result** (1-4 species, or some `taxonFilters` groups dropped/empty): `select_species_across_groups` silently hands back whatever's available; pipeline proceeds all the way to a rendered map with no user-facing signal at all. Not previously understood as "silent" — this was a real correction mid-session.
  - **Overlapping waypoints**: no handling at all; `order_waypoints` computes 0m legs happily, map stacks numbered medallions on top of each other (root-caused in `WORK_SUMMARY_250726.md`'s Rascafría finding — a genuine GBIF shared-recording-location data artifact).
- **Ran a `/grill-me`-style design interview** (this session, condensed) to resolve the API/UX shape one branch at a time rather than building ahead of a clear design — see "Decisions" below for the resolved branches.
- **Live-tested the built prototype at both the CLI and server/curl level**, not just unit-level: confirmed case 1 stops before any GBIF fetch (`"Show me something colourful"`), the override path completes a full real walk (birds near Retiro, $0.0076/15.9s), and a real sparse/overlapping case (`"I want to see reptiles"` near Retiro) produced exactly the case-3 overlap note with no other noise.
- **Found and fixed a real bug via this live testing**: the raw-occurrence-points feature was initially wired only into the CLI script's own `generate_quest_log_map()` — the actual browser flow renders through `index_full_validation.html`'s separately-duplicated `renderMapView()` JS (per this codebase's "prototypes stay standalone" convention), which hadn't been touched, and `/run-walk`'s JSON response didn't carry a `points` field per species at all. Fixed by updating `server_full_validation.py`'s `species_payload` construction and the frontend's `renderMapView()`/`openQuestModal()` to match the Python-side implementation.
- **Found and fixed a UX/legibility issue via user testing**: the raw-occurrence dots were initially styled in muted thematic tan/brown (`#7a5a2d`/`#d9c28a`), which blended into the sepia-filtered map tiles and was reported as "not working." Fixed by switching to the same bold, saturated per-species palette (`SPECIES_COLORS`) already used elsewhere in this codebase, with a dark outline for contrast — confirmed working after the fix.
- **Found and fixed a scope-creep issue via user testing**: an early version of the case-2/case-3 notes logic also surfaced GBIF sub-taxonomy detail ("No species found nearby for: class/Crocodylia, class/Sphenodontia") whenever a multi-class query (e.g. "reptiles" → 4 classes) had some empty sub-groups, even when the overall 5-species target was still met. User feedback: target users have no concept of GBIF classification and don't care which sub-group came up empty — removed this note type entirely (dropped/empty-group detail is still logged server-side for debugging, just never surfaced to the user).
- **Rarity-based queries flagged as the highest-priority remaining edge case, not yet handled.** Removing `sort: "rarest"` this session (see Decisions below) closed off the old messy behaviour, but it left a real gap: a query like "rare plants" still has a real taxon signal (`kingdom/Plantae` resolves fine), so it never reaches case 1 — it just silently returns the most-observed plants, with no guidance that "rare" was understood but ignored. This is now the query-handling structure's most visible remaining failure case with zero user guidance. Worth prioritising over other edge cases because (a) rarity is likely a genuinely interesting angle for users ("show me something I might not normally see"), and (b) unlike qualitative terms unmappable to GBIF (colour, "impressive"), GBIF actually has usable metadata and sort/filter mechanics for it (occurrence counts, date-based recency signals) — this isn't a dead end like "colourful," it's an underbuilt feature.

## Decisions and trade-offs

- **Decision:** Model query validation as a state check that runs after STEP 1-5 (intent → resolve → fetch/rank → merge → order), not as a separate pre-flight gate before touching GBIF at all — but only case 1 (no taxon filters produced, or all given filters unresolved) is cheap enough to detect *before* any GBIF fetch happens (right after STEP 2). **Why:** STEPS 1-5 are cheap (one LLM call + free GBIF calls); only STEPS 6-8 (2 more LLM calls, Wikipedia lookups) are worth gating. **Trade-off:** none identified — this cleanly separates "cheap enough to always run" from "expensive enough to gate."
- **Decision:** Split the pipeline into two functions/endpoints — `resolve_species_query()`/`POST /gbif-species-query` (STEPS 1-5) and `run_pipeline()`/`POST /run-walk` (STEPS 6-8) — rather than pausing mid-way through one `run_pipeline()` call. **Why:** user's own proposal, refined further once the actual STEP boundaries were mapped — this makes one reusable validation seam for all cases (not just case 1) instead of three special-cases bolted into a single function, and cleanly separates "cheap" from "expensive" halves of the pipeline. **Trade-off:** one extra network round-trip on every query (not just edge cases) — accepted since it's the fast half of the pipeline (~1-3s).
- **Decision:** Stateless design — the species list from `/gbif-species-query` round-trips through the client back into `/run-walk`, rather than being cached server-side against a request ID. **Why:** no server-side session state exists anywhere else in this codebase yet (every existing `server*.py` is a stateless in-process call); introducing it here would answer a question this prototype isn't asking (expiry policy, memory growth, restart-loses-state). **Trade-off:** the client is trusted to send back what it was given unmodified — a non-issue for a local prototype with no auth, but worth a line in the eventual production spec. Logged the "shareable walk link" feature idea as a legitimate *future* reason to revisit this trade-off (`FEATURE_IDEAS_BACKLOG.md`).
- **Decision:** Only cases 1 and 4 (no taxon filter to search on; a resolved filter that found zero occurrences here) gate with `needs_clarification`. Cases 2 (1-4 species found) and 3 (overlapping waypoints) proceed automatically with an explanatory note. **Why:** the governing principle settled on mid-session — the *only* thing that should block is about to silently substitute the unfiltered `most_observed` default in place of what the user actually asked for. Cases 2/3 still run the exact same search the user asked for (just fewer results, or two results landing close together) — nothing gets substituted, so asking "do you want a walk or not?" is an odd question when the walk is already fully determined. **Trade-off:** case 3's actual fix (merging overlapping markers into one shared stop) is still not built — this round only detects and annotates it.
- **Decision:** "Proceed anyway" (the "Show most-observed instead" button) is always the same client action — re-call `/gbif-species-query` with `override: "proceed"` — rather than the frontend branching on whether a species list already exists. **Why:** keeps the frontend dumb/uniform; the server decides internally whether it already has a partial list (case 2 — just returns it) or needs to run the unfiltered fallback fetch (case 1/4 — hasn't run yet). **Trade-off:** none identified.
- **Decision:** `/run-walk` is only ever reached after either the user's original query submission (when nothing needed clarifying) or an explicit "proceed anyway" click — never as an automatic side-effect of a fallback resolving cleanly on its own. **Why:** explicit user requirement, stated after an ambiguous first draft of the sequence — "I don't want that happening silently anymore." **Trade-off:** none — this was the core requirement being validated.
- **Decision:** `MIN_WAYPOINT_SPACING_M = 20` (not the initially-recommended 50). **Why:** real data from `WORK_SUMMARY_250726.md` showed valid, distinct species separations as low as 55m at Retiro — a 50m threshold risked false-flagging normal variation. 20m targets the genuine data-artifact case (the Rascafría collision was exactly 0m) without catching legitimate closeness. **Trade-off:** none identified; easy to retune later (named constant, same pattern as `--grid-n`).
- **Decision:** Overlap detection checks all pairs of selected species' hotspots, not just consecutive route legs. **Why:** two species can sit close together without being visited back-to-back in `order_waypoints`' nearest-neighbour tour. **Trade-off:** none — cheap at 5 species (10 pairs).
- **Decision:** "Rare" query handling removed entirely rather than fixed or left alone. `sort: "rarest"` deleted from `QUERY_SCHEMA_TOOL` (the LLM literally cannot produce it now, since tool-use schemas are enforced) and from `rank_species()`. "Show me something rare" now gets identical case-1 treatment to any other non-taxon-mappable request. **Why:** explicit user instruction — the old rarest-sort behaviour surfaced singleton/1-observation records with messy labels (flagged in `WORK_SUMMARY_250726.md`) and the user wants to wait until there's real investment in GBIF-metadata-driven cases (e.g. "show me old species") before building "rare" properly. **Trade-off:** "rare" intent is now completely unhandled as a distinct concept — acceptable per explicit instruction, not an oversight.
- **Decision:** Case 2/3 notes never include GBIF sub-taxonomy detail (which specific dropped/empty class or family underlies a partial result). **Why:** explicit user feedback after seeing it live — target users have no concept of GBIF classification and don't care which sub-group came up empty, only whether the walk itself came up short. **Trade-off:** less debugging detail in the user-facing note (still logged server-side).
- **Decision:** Raw occurrence points (not just the cluster centroid) are kept per species and round-tripped through the stateless client boundary, rendered as small circle markers toggled on marker click. **Why:** explicit user request to restore a feature from `e2e_walk_spike_clustering.py`. Styled in bold, saturated per-species colours (`SPECIES_COLORS`, matching the CLI script) rather than muted thematic tones — the first styling attempt was found illegible against the sepia-filtered map tiles during live testing. **Trade-off:** none identified.
