Replaces the 5 isolated per-species Claude Agent SDK `query()` calls with ONE batched agent session (single `query()` call covering all 5 species; the agent calls `fetch_wikipedia_summary` once per species within that session, then returns a JSON array of descriptions parsed back out programmatically). `MODEL` is now a `--model` CLI argument instead of a hardcoded constant, with a `MODEL_PRICING` fallback dict (`claude-sonnet-5`, `claude-haiku-4-5-20251001`). Narrative generation step left unchanged/isolated so the batching experiment isolates one variable. - `prototypes/scripts/species_narrative_cost_experiment2.py` — forked from experiment1. Drops the Claude Agent SDK entirely: no `query()`, no `ClaudeAgentOptions`, no `fetch_wikipedia_summary` tool, no in-process MCP server, no `claude` CLI subprocess. Wikipedia lookups are called directly in Python (deterministic, same pattern as the existing GBIF lookup) instead of via agent tool-calling. Rewritten to be fully synchronous (no `asyncio`/`async`/`await`) after discussion established there was no functional need for async in either script beyond mirroring experiment1's shape — nothing in the pipeline runs concurrently, and async adds no measurable runtime difference for sequential calls (event-loop overhead is microseconds vs. seconds of network/inference wait). ## What was explored / learnt

- **Cache-write savings from batching (experiment1 vs. the original per-species-isolated spike):** batching 5 species into one Agent SDK session cut `cache_creation_input_tokens` from ~12,181 (isolated, per prior session's notes) to 5,291 total (3,260 for the batched description session + 2,031 for the still-isolated narrative call) on Sonnet 5. Confirms the hypothesis from the previous session (18 July) that isolation was the direct cause of repeated cache-write overhead.
- **Model comparison within the agentic approach (experiment1, Sonnet 5 vs. Haiku 4.5):** Haiku had **zero** cache activity at all (no cache writes or reads on either step) vs. Sonnet 5's 5,291 cache-write / 2,001 cache-read tokens — a real behavioural difference between models, not just a cost artifact. Total cost: Sonnet $0.0511 vs. Haiku $0.0260 (~2x). Wall time comparable (26.2s vs. 28.6s). Haiku made 6 Wikipedia tool calls instead of 5 (retried "Common Mallard" → "Mallard"), and used a markdown `#` header in the narrative despite the prompt explicitly saying not to — Sonnet followed that instruction correctly.
- **Non-agentic vs. agentic (experiment2 vs. experiment1, same models):** dropping the Agent SDK for plain Messages API calls was the single biggest lever in the whole exercise:
  - Sonnet 5: agentic 26.2s/$0.0511 → non-agentic 18.0s/$0.0180.
  - Haiku 4.5: agentic 28.6s/$0.0260 → non-agentic **10.2s/$0.0061** (~2.7x faster, ~4.3x cheaper).
  - Non-agentic Sonnet 5 ($0.0180) beat agentic Haiku 4.5 ($0.0260) on cost — the Agent SDK/CLI-subprocess overhead outweighs the Sonnet→Haiku price difference.
  - Non-agentic runs show zero cache activity on either model (expected: no Claude Code system prompt riding along on a plain API call, so there's nothing to cache). Input token counts also dropped sharply (e.g. Haiku: 1,377 total tokens in non-agentic vs. 9,083 in agentic) since there's no system prompt or tool-definition overhead baked into each request.
  - Haiku's markdown-header quirk in the narrative persisted in the non-agentic version too — confirms it's a Haiku instruction-following gap, not something tied to the agentic/non-agentic axis.
- **`anthropic` package was not actually installed** in the venv despite `import anthropic` succeeding — it resolved to an empty namespace-package stub (`anthropic.__file__` was `None`, `pip show anthropic` reported not found). Root-caused via `python -c "import anthropic; print(anthropic.__path__)"` showing a `_NamespacePath`. Fixed with `pip install anthropic` (0.117.0) and added to `prototypes/requirements.txt`.
- **Async was unnecessary in experiment2.** User asked why async was used at all; established that experiment1's `async`/`await` was required only because the Agent SDK's `query()` is an async generator (streams from a subprocess) — nothing else in either script does concurrent work. Confirmed async adds no meaningful runtime difference for sequential calls (microseconds of event-loop overhead vs. seconds of network/inference latency), so the choice was about code clarity, not performance. Converted experiment2 to plain sync (`Anthropic()` client, `def` functions, no `asyncio.run`).

## Decisions and trade-offs

- **Decision:** Keep experiment1's narrative step isolated/unchanged (not folded into the same batched session as the descriptions). **Why:** isolates the one variable under test (per-species isolation vs. batching) so the cache-write comparison is clean. **Trade-off:** the narrative step still pays its own isolated cache-write cost in experiment1 — a further optimisation (folding narrative into the same session) was considered but not built, left as a possible future experiment.
- **Decision:** experiment2 fetches Wikipedia summaries directly in Python rather than via any tool-calling mechanism, even though it's no longer using the Agent SDK. **Why:** this is the defining feature of "non-agentic" — no LLM-directed tool use at all, matching the deterministic style already used for the GBIF lookup step. **Trade-off:** none identified; this is strictly simpler and also removes the order-matching fragility that experiment1's tool-call-order zip approach had.
- **Decision:** experiment2 is fully synchronous. **Why:** explicit user request after confirming async added no functional value or performance benefit for this sequential, non-concurrent pipeline. **Trade-off:** none — this is strictly simpler code for identical behaviour.
- **Decision:** cost in experiment2 is always the token-based estimate from `MODEL_PRICING` (never a reported `total_cost_usd`, unlike experiment1/the original spike which preferred the Agent SDK's authoritative figure when available). **Why:** the plain Messages API response has no such field. **Trade-off:** cost figures rely on the approximate public per-MTok pricing table rather than an authoritative billed amount — acceptable for a directional cost comparison, not for precise accounting.
- **Decision:** No tests written for either new experiment script. **Why:** consistent with all of `prototypes/` (throwaway scripts, no test suite), same override of the default TDD workflow as agreed in the 18 July session for this same file family.

## Session 2 — UX prototype: game-like map + narrative layout

Switched to `/prototype` to explore the game-like adventure UX (Pokemon Go / Zelda / Minecraft feel) called for in the 18 July session's "fantasy video game journey" direction, starting with the map + narrative layout using the fixed real output from `prototypes/artifacts/retiro_narrative_map_cost_experiment2_claude_haiku_4_5_20251001.html`.

### What was built

- `prototypes/ux/map_narrative_layout_prototype.html` — new standalone throwaway UI prototype (no existing page to host variants in, so sub-shape B per the `/prototype` UI process). Three structurally distinct layout variants, switchable via `?variant=A|B|C` and a floating bottom bar (← → arrows, keyboard-navigable), all built on the real 5-species Retiro data and narrative text captured from the Haiku experiment2 artifact (the stray leading `# ` markdown header from that raw output was stripped for display — a known rendering quirk, not meaningful content):
  - **A — Quest Log (Zelda):** slide-out parchment journal (accordion, one entry per waypoint), numbered medallion map markers, modal "quest entry" per species with a "Mark Discovered" action that checks off the journal entry.
  - **B — PokéStop (Pokemon Go):** full-bleed map, top XP/discovery bar ("n / 5"), pulsing circular markers that stop pulsing once visited, bottom-sheet species card on tap, floating book-icon FAB opens the full narrative as a dark expedition-log overlay.
  - **C — Inventory (Minecraft):** split map + blocky 5-slot inventory sidebar that fills in with the species image as markers are clicked, detail box below it, pixel-font scrolling achievement log with the full narrative.
- First-pass map base-layer treatment (superseded by the vector re-skin below, kept in place for reference): swapped the stock OSM tile layer for OpenTopoMap (free, no API key, contour/hillshade/green terrain) and applied per-variant CSS `filter` (sepia/saturate/contrast) scoped to Leaflet's `.leaflet-tile-pane` only (so filters never touch markers/popups, which live in separate Leaflet panes) plus per-variant vignette/grain/scanline overlay divs and frame borders (ornate wood frame for A, glowing rounded HUD for B, pixel-bevel + chunk-grid for C).
- `prototypes/ux/map_narrative_layout_prototype_v2.html` — new file (forked from v1, which was deliberately left untouched rather than edited in place, at the user's request, so it stays available as a reference point). Replaces the OpenTopoMap-plus-filter treatment with a genuine vector re-skin: no tile provider at all in any variant. Real Retiro Park geometry — captured via the raw OSM REST API in this session (see below) — is embedded as a static `PARK_GEO` constant (lakes, 45 curated trail paths, a 15-vertex convex-hull park-boundary approximation) and rendered as styled Leaflet vector shapes (`L.polygon`/`L.polyline`), with a genuinely different rendering treatment per variant rather than a shared shape with different colours:
  - **A (Zelda):** flat moss-green park fill, ink-blue lake fills, dashed brown "ink" trails, `.leaflet-container` background set to a parchment tone so the area outside the park hull reads as the page itself.
  - **B (Pokemon Go):** candy-flat bright green/blue fills; the park hull is drawn twice — an offset, blurred-looking dark-green copy underneath (`SHADOW_OFFSET = -0.0006` degrees latitude) plus the real hull on top in bright green with a white cartoon outline — faking a 2.5D diorama "pop."
  - **C (Minecraft):** identical real geometry run through a new `snapToGrid(coords, step)` helper (`STEP = 0.00028` degrees, ~31m) before rendering, so the coastlines/paths are genuinely jagged/blocky — the blockiness comes from quantizing real vertices, not a CSS filter faking it.
  - Curated the previously-captured 537 footways down to the 45 longest by haversine length (671 points before simplification, 371 after stride-2 downsampling) so trails read as a legible primary path network rather than noise.
  - Approximated the park boundary as the convex hull (15 vertices) of all captured trail + lake points, since Retiro's true boundary is an OSM relation the raw REST endpoint can't return (see below).

### What was explored / learnt

- **User feedback: the filtered-OSM approach was rejected as too limited.** Ran the map+narrative prototype past `/frontend-design` for a real design discussion rather than more incremental CSS. Diagnosis: real cartographic tiles (road-network hierarchy, place-name typography, institutional map colours) carry a visual grammar that a CSS filter can recolour but not remove — it still reads as "a real map with an Instagram filter," not as designed game cartography. None of Pokemon Go / Zelda / Minecraft's maps are photographic tiles with a skin; they're either custom-rendered from real geometry or fully illustrated.
- **Three directions were proposed and discussed with the user:**
  - **A — Vector re-skin:** render real OSM geometry (park bounds, paths, water, tree cover) ourselves as flat game-styled vector shapes instead of consuming raster tiles at all. Scales to "start with your location" later for free, since it's driven by real OSM data rather than bespoke art.
  - **B — Illustrated diorama:** bespoke hand-drawn/AI-generated map art of Retiro specifically, with markers overlaid at real coordinates. Most visually striking, but doesn't generalise — arbitrary future locations would need a real generative-art pipeline (cost/latency/consistency), not just a rendering change.
  - **C — Fog-of-war exploration layer:** the park starts obscured and clears per waypoint as it's discovered — Pokemon Go's actual signature mechanic, layerable on top of either A or B.
  - **User decision:** direction **A** (vector re-skin), fog-of-war (**C**) explicitly deferred to a later round — map base treatment first.
- **Overpass API reconfirmed unreliable — do not use it.** Attempted to fetch Retiro Park's true boundary as a single relation/multipolygon via Overpass QL (`overpass-api.de/api/interpreter`, then the `overpass.kumi.systems` mirror) to get exact geometry beyond what the raw OSM REST API's bbox endpoint returns (which excludes relations). `overpass-api.de` returned a `504` gateway timeout. User stopped this line of work immediately: Overpass's unreliability was already established in an earlier session (see `overpass_spike.py`'s own docstring — "Isolated test: can we get OSM footpaths... "). **Correction: stick to the raw OSM REST API (`api.openstreetmap.org/api/0.6/map.json?bbox=...`) only** — this is what `overpass_spike.py` already uses successfully, and what actually worked in this session (see below).
- **Real geometry captured via the raw OSM REST API (one bbox call, no Overpass):** using the existing `BBOX = "-3.690,40.4076,-3.675,40.4216"` from `overpass_spike.py`, fetched all nodes/ways in that box and extracted, by shoelace-area ranking:
  - Lake polygons: `El Estanque Grande` (id 4088758, 95 points, the main lake near the Egyptian Goose / Black Swan / Mallard waypoints), `Estanque del Palacio de Cristal` (id 23594997, 75 points), `Estanque de la Noria` (id 194088944, 5 points) — all exact, real closed-ring geometry.
  - Footways/paths: filtering `highway` in `{footway, path, pedestrian}` (excluding `access=private`) and keeping only ways whose centroid falls inside a manually estimated tighter "core park" sub-bbox (`lat 40.4082–40.4192, lon -3.6875 to -3.6765`, tighter than the full fetch bbox which also covers surrounding city blocks) yielded 537 ways / 3,371 points — simplified (stride-3 downsampling, endpoints preserved) to 1,920 points. **Not yet finalised**: 537 distinct trails is too dense to read as a handful of clear, bold game-map trails — still needs filtering down to a curated subset (e.g. top N longest/most primary ways) before embedding.
  - **No exact real polygon for the overall park boundary** was obtained — the largest `leisure=park` way in the bbox turned out to be a small observatory garden (`Real Observatorio de Madrid`), not Retiro itself; Retiro's true boundary is very likely mapped as a relation/multipolygon, which the raw bbox REST endpoint doesn't return (relations aren't included, only nodes/ways). Planned workaround, not yet built: approximate the park's outer silhouette as a hand-derived organic polygon roughly matching the known bbox extent, rather than pursuing exact relation geometry.
- **User raised a production concern to keep front-of-mind:** how many API calls this kind of data-fetch requires, and what a fast production load path looks like. Applied for this round: `map_narrative_layout_prototype_v2.html` makes **zero** live OSM/Overpass calls — `PARK_GEO` is captured once and hardcoded, consistent with how `species_narrative_spike.py` already hardcodes a captured GBIF snapshot. **User explicitly flagged this doesn't solve the real problem**: capture-once-serve-static only works for a fixed, pre-known location (Retiro) — it does **not** generalise to a user selecting an arbitrary location live, which is the "start with your location" flow planned for a later version. That remains a genuinely open design question, not resolved by this session's approach — see Next steps.

### Decisions and trade-offs

- **Decision:** Standalone new file (`prototypes/ux/map_narrative_layout_prototype.html`) rather than adjusting an existing page. **Why:** no existing page exists to host UX layout variants in yet — this is a wholly new UI surface (`/prototype` UI process sub-shape B).
- **Decision:** Pursue direction A (vector re-skin from real OSM geometry) over B (illustrated diorama), with fog-of-war (C) deferred. **Why:** explicit user choice — A scales to arbitrary future locations for free since it's driven by live-captured real data rather than bespoke per-location art; fog-of-war is a bigger scope addition better tackled once the base map direction is settled.
- **Decision:** Use only the raw OSM REST API (`api.openstreetmap.org/api/0.6/map.json`), never Overpass. **Why:** Overpass's public instances are unreliable (confirmed again this session via a `504` from `overpass-api.de`); this was already established in an earlier session per `overpass_spike.py`'s framing. **Trade-off:** the raw REST API only returns nodes/ways within a bbox, not relations/multipolygons — so the exact real Retiro Park boundary (mapped as a relation) isn't directly obtainable this way; a convex-hull approximation was used instead of chasing exact relation geometry.
- **Decision:** Approximate the park boundary as the convex hull of captured trail + lake points rather than hand-drawing a silhouette. **Why:** still grounded in real captured coordinates (not a guessed shape) despite not being the exact concave boundary; simple to compute (Andrew's monotone chain, no external library) and gave a usable 15-vertex polygon. **Trade-off:** a convex hull can't represent concave bites out of the park's real outline, so the shape is a looser approximation than the true boundary would be.
- **Decision:** Curate footways to the top 45 by length rather than rendering all 537. **Why:** explicit design goal (stylized, legible game-map trails, not cartographic completeness) — 537 real paths read as clutter, not a curated adventure-map trail network. **Trade-off:** minor/decorative real paths are dropped; only the primary path network survives.
- **Decision:** Built `map_narrative_layout_prototype_v2.html` as a new file rather than editing v1 in place. **Why:** explicit user request, so v1 (the filtered-tile approach) stays intact as a reference/history point rather than being overwritten mid-iteration.
- **Decision:** Capture-once-serve-static for this round's geometry, explicitly scoped to Retiro only. **Why:** matches the existing GBIF-snapshot pattern and directly answers the "how many live calls" concern for the fixed-location case. **Trade-off, called out by the user, not resolved:** this approach does not extend to a user picking an arbitrary location live — that would need either an on-demand fetch-and-cache step server-side or a different data strategy entirely, which is still an open design question for the "start with your location" flow.
