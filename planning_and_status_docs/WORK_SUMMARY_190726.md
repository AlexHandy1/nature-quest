## What was explored / learnt

- **Cache-write savings from batching (experiment1 vs. the original per-species-isolated spike):** batching 5 species into one Agent SDK session cut `cache_creation_input_tokens` from ~12,181 (isolated, per prior session's notes) to 5,291 total (3,260 for the batched description session + 2,031 for the still-isolated narrative call) on Sonnet 5. Confirms the hypothesis from the previous session (18 July) that isolation was the direct cause of repeated cache-write overhead.
- **Model comparison within the agentic approach (experiment1, Sonnet 5 vs. Haiku 4.5):** Haiku had **zero** cache activity at all (no cache writes or reads on either step) vs. Sonnet 5's 5,291 cache-write / 2,001 cache-read tokens — a real behavioural difference between models, not just a cost artifact. Total cost: Sonnet $0.0511 vs. Haiku $0.0260 (~2x). Wall time comparable (26.2s vs. 28.6s). Haiku made 6 Wikipedia tool calls instead of 5 (retried "Common Mallard" → "Mallard"), and used a markdown `#` header in the narrative despite the prompt explicitly saying not to — Sonnet followed that instruction correctly.
- **Non-agentic vs. agentic (experiment2 vs. experiment1, same models):** dropping the Agent SDK for plain Messages API calls was the single biggest lever in the whole exercise:
  - Sonnet 5: agentic 26.2s/$0.0511 → non-agentic 18.0s/$0.0180.
  - Haiku 4.5: agentic 28.6s/$0.0260 → non-agentic **10.2s/$0.0061** (~2.7x faster, ~4.3x cheaper).
  - Non-agentic Sonnet 5 ($0.0180) beat agentic Haiku 4.5 ($0.0260) on cost — the Agent SDK/CLI-subprocess overhead outweighs the Sonnet→Haiku price difference.
  - Non-agentic runs show zero cache activity on either model (expected: no Claude Code system prompt riding along on a plain API call, so there's nothing to cache). Input token counts also dropped sharply (e.g. Haiku: 1,377 total tokens in non-agentic vs. 9,083 in agentic) since there's no system prompt or tool-definition overhead baked into each request.
  - Haiku's markdown-header quirk in the narrative persisted in the non-agentic version too — confirms it's a Haiku instruction-following gap, not something tied to the agentic/non-agentic axis.
- **`anthropic` package was not actually installed** in the venv despite `import anthropic` succeeding — it resolved to an empty namespace-package stub (`anthropic.__file__` was `None`, `pip show anthropic` reported not found). Root-caused via `python -c "import anthropic; print(anthropic.__path__)"` showing a `_NamespacePath`. Fixed with `pip install anthropic` (0.117.0) and added to `prototypes/requirements.txt`.
- **Async was unnecessary in experiment2.** User asked why async was used at all; established that experiment1's `async`/`await` was required only because the Agent SDK's `query()` is an async generator (streams from a subprocess) — nothing else in either script does concurrent work. Confirmed async adds no meaningful runtime difference for sequential calls (microseconds of event-loop overhead vs. seconds of network/inference latency), so the choice was about code clarity, not performance. Converted experiment2 to plain sync (`Anthropic()` client, `def` functions, no `asyncio.run`).

## Decisions and trade-offs

- **Decision:** Keep experiment1's narrative step isolated/unchanged (not folded into the same batched session as the descriptions). **Why:** isolates the one variable under test (per-species isolation vs. batching) so the cache-write comparison is clean. **Trade-off:** the narrative step still pays its own isolated cache-write cost in experiment1 — a further optimisation (folding narrative into the same session) was considered but not built, left as a possible future experiment.
- **Decision:** experiment2 fetches Wikipedia summaries directly in Python rather than via any tool-calling mechanism, even though it's no longer using the Agent SDK. **Why:** this is the defining feature of "non-agentic" — no LLM-directed tool use at all, matching the deterministic style already used for the GBIF lookup step. **Trade-off:** none identified; this is strictly simpler and also removes the order-matching fragility that experiment1's tool-call-order zip approach had.
- **Decision:** experiment2 is fully synchronous. **Why:** explicit user request after confirming async added no functional value or performance benefit for this sequential, non-concurrent pipeline. **Trade-off:** none — this is strictly simpler code for identical behaviour.
- **Decision:** cost in experiment2 is always the token-based estimate from `MODEL_PRICING` (never a reported `total_cost_usd`, unlike experiment1/the original spike which preferred the Agent SDK's authoritative figure when available). **Why:** the plain Messages API response has no such field. **Trade-off:** cost figures rely on the approximate public per-MTok pricing table rather than an authoritative billed amount — acceptable for a directional cost comparison, not for precise accounting.
- **Decision:** No tests written for either new experiment script. **Why:** consistent with all of `prototypes/` (throwaway scripts, no test suite), same override of the default TDD workflow as agreed in the 18 July session for this same file family.
