# Work Summary — 22 July 2026

## What was built

- **`prototypes/scripts/e2e_walk_spike.py`** — the first end-to-end integration prototype, chaining `intent_query_spike.py` (NL query → structured GBIF query → resolve taxa → parallel fetch/rank → quota merge), `waypoint_spike.py`'s nearest-neighbour ordering, and `species_narrative_cost_experiment2.py`'s non-agentic enrichment pattern (GBIF common name + Wikipedia lookup, batched per-species description call) into one script. Adds a new structured narrative call (intro + one paragraph per waypoint, JSON output) instead of experiment2's single flowing blob, so the result can drive a per-waypoint quest-log UI. Renders onto a ported, fully-interactive version of the Variant A "Zelda quest log" map (journal toggle, click-to-open modal, mark-discovered) from `prototypes/ux/map_narrative_layout_prototype.html`, fed with real generated data. Three independently-flagged models (`--intent-model` / `--description-model` / `--narrative-model`), default `claude-haiku-4-5-20251001`. Full prompt/usage/cost logging matching the existing prototype convention.
- **`prototypes/scripts/e2e_walk_spike_server.py`** — a copy of `e2e_walk_spike.py` (the working original was left untouched per explicit user instruction — working prototypes are checkpoints, copy before editing). `run_pipeline()` gained an `open_browser` flag and now returns `{species, intro, waypoints, map_path}` instead of just the species list, so a caller can render its own view from the result.
- **`prototypes/scripts/server.py`** — first HTTP server in this codebase. Minimal Flask app serving `prototypes/web/index.html` and one blocking `POST /run-walk` endpoint that calls `e2e_walk_spike_server.run_pipeline()` in-process and returns JSON. First cross-script import in this codebase (justified: thin HTTP wrapper, not a duplicate implementation). Runs on port 5050.
- **`prototypes/web/index.html`** — single-page frontend, no build step. Three JS-swapped states in one page: landing form (location fixed to "Retiro Park, Madrid", a disabled "draw your own area" placeholder select, NL query textarea with example-query buttons) → generic loading state (spinner + rotating quest-flavoured status text) → the Zelda quest-log map view (duplicated quest-log CSS/JS from `e2e_walk_spike.py`, fed with real fetched data instead of pre-baked arrays), plus a persistent query bar docked on the map view so a new walk can be requested without leaving the map. Whole flow is Zelda-themed throughout, including the landing/loading states.
- **`prototypes/requirements.txt`** — added `flask`.
- **`README.md`** (root) — rewrote the one-line project description to reflect the dynamic, NL-query-driven approach instead of the older static framing; added a "Current approach (prototype stage)" section pointing to `prototypes/README.md`.
- **`prototypes/README.md`** — new. Full navigation doc for coding agents: conventions (standalone scripts, copy-don't-edit working scripts, plain Messages API vs Agent SDK, Haiku default, fixed Retiro location, full logging, light TDD scope, venv setup), a folder map, every prototype script summarised in build order with what it answered and what won, run commands, and an explicit "proven vs. still open" summary.

## What was explored / learnt

- **Haiku validated on two more live test intents** for `intent_query_spike.py` (before the e2e work started): "Today I want to learn about plants" ($0.0043, 2.0s LLM wall — vs. Sonnet 5's $0.0107/3.4s for the same query) and "Show me a mix of birds, plants and mammals" ($0.0045, 1.8s LLM wall). Both produced correct structured output and correct downstream species selection (including the mixed-taxa quota/degradation behaviour), matching Sonnet 5's results at roughly 60% lower cost.
- **`e2e_walk_spike.py` integration insight:** `intent_query_spike.py`'s per-filter GBIF fetch already computes each species' hotspot centroid (`rank_species()`), so no separate waypoint-specific GBIF fetch is needed — `waypoint_spike.py`'s only real contribution to the merged pipeline is the nearest-neighbour ordering logic itself.
- **Live validation of `e2e_walk_spike.py`, full real run (GBIF + Haiku):**
  - "Today I want to learn about plants" → `{kingdom, Plantae}`, 5 real Retiro species (daisy, garlic, almond, celandine, stone pine), 730m route, $0.0112 total, 20.3s wall (11.6s of that pure LLM time across 3 calls).
  - "Show me a mix of birds, plants and mammals" → correct 2 birds/2 plants/1 mammal split (magpie, woodpecker, daisy, garlic, rat — mammal group correctly degraded to 1 given sparse Retiro data), 421m route, $0.0123 total, 21.3s wall.
- **`/grill-me` design session for `e2e_walk_spike.py`** resolved: keep the standalone-script convention (duplicate helpers, don't import); waypoint ordering ignores taxon grouping (pure nearest-neighbour); skip new unit tests for ordering/distance logic (visually verifiable, matches `waypoint_spike.py`'s own no-tests precedent); narrative call restructured to ask for JSON (intro + per-waypoint) instead of one blob, to properly drive the quest-log accordion with real content instead of the mockup's hand-split text.
- **`/grill-me` design session for the web frontend** resolved: minimal local Flask server (not a no-server manual handoff); Flask over FastAPI (nothing here needs async); single blocking POST + generic spinner for this round (user explicitly wants background-job/polling for staged progress in "the fuller version" — noted as a next step, not built); server returns raw species/narrative JSON and the frontend renders its own map client-side (not a redirect to the CLI's static artifact) — this means the quest-log JS/CSS is duplicated between `e2e_walk_spike.py` and `prototypes/web/index.html` rather than extracted into a shared asset, a deliberate choice consistent with the standalone-prototype convention; single-page JS state machine (not separate pages/URLs) with a persistent regenerate bar once in map view; Zelda theme carried through the landing/loading states, not just the map.

## Decisions and trade-offs

- **Decision:** `e2e_walk_spike.py` stays fully standalone (no imports from `intent_query_spike.py`/`waypoint_spike.py`/`species_narrative_cost_experiment2.py`), duplicating small shared logic instead. **Why:** matches the established convention across every other prototype in this codebase (see `PLANNING_INTENT_QUERY_210726.md` §7's original rationale) — user confirmed explicitly when asked. **Trade-off:** the taxon-resolution/quota-merge logic now exists in two files; any future bugfix to that logic needs to be applied in both.
- **Decision:** `server.py` is the one exception to the standalone convention — it imports `run_pipeline` directly from `e2e_walk_spike_server.py`. **Why:** user-agreed as a thin HTTP wrapper around the pipeline, not a second implementation of it — different in kind from prototype-to-prototype duplication.
- **Decision:** working, validated prototype scripts (`e2e_walk_spike.py`) are never edited in place once proven — always copy first. **Why:** user wants proven runs preserved as stable checkpoints, not silently mutated while building the next layer on top. **Trade-off:** some duplication between `e2e_walk_spike.py` and `e2e_walk_spike_server.py` (currently near-identical except the `open_browser`/return-value change) — acceptable for prototype stage.
- **Decision:** web frontend uses a single blocking `POST /run-walk` with a generic loading spinner, not background-job polling. **Why:** simplest correct Flask shape for this round; matches `run_pipeline()`'s existing synchronous nature. **Trade-off:** no real per-step progress in the UI yet — user explicitly flagged this as wanted for "the fuller version." **Next step, not yet built.**
- **Decision:** frontend renders the quest-log map client-side from raw JSON (not a redirect to a server-generated static HTML file), duplicating the quest-log CSS/JS between `e2e_walk_spike.py` and `prototypes/web/index.html`. **Why:** user-chosen over the alternative (extract a shared asset) to keep the standalone-prototype convention; avoids committing to a shared-module structure before the UI direction is validated further. **Trade-off:** the two copies of the quest-log rendering code can drift; flagged as a known cleanup item if this moves past prototype stage.
