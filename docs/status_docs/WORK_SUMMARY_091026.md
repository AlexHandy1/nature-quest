## What was built

- `prototypes/scripts/duckdb_parquet_prototype.py` — standalone prototype. Exports `species_cell_fact_g6_min2` (sorted by `cell`) and the species-dimension table from BigQuery to local Parquet (`prototypes/scratch/fact_sorted_by_cell.parquet`, `prototypes/scratch/species_dimension.parquet`), computes candidate geohash-6 cells for the Retiro polygon (bbox grid-sampling), runs a DuckDB join query against the local files, and reports `EXPLAIN ANALYZE` output, latency, memory, and file sizes. ## What was explored / learnt

- **BigQuery dataframe download without the Storage API is genuinely slow.** First run of the fact-table export fell back to paginated REST (`UserWarning: BigQuery Storage module not found, fetch data with the REST endpoint instead`) — killed the run after observing low CPU% (I/O-bound) and 318MB resident after ~2 minutes. Installed `google-cloud-bigquery-storage`, which `to_dataframe()` auto-detects, and the re-run completed the full 221M-row download in the time it took to write this summary (~1% per second observed by the user, so roughly 1.5-2 minutes). **Caveat on the kill decision itself:** the original "this will take a long time" call was made from a single memory snapshot plus low-CPU%, not two samples over time — not rigorous, though installing the Storage API was a strict improvement regardless of whether the diagnosis was airtight.
- **Observability fix, now the established pattern for this script:** Python buffers stdout when it isn't a tty, so background-redirected runs showed nothing until a buffer flush. Fixed by running with `python3 -u` (unbuffered) piped through `2>&1 | tee prototypes/logs/<name>_<timestamp>.log` — matches the existing repo convention already used by `intent_query_spike.py` etc., rather than a bespoke logging setup.
- **`to_dataframe(progress_bar_type="tqdm")`** gives a live download progress bar — useful run interactively in a real terminal, but doesn't play well with the `Monitor`/`tee`-to-file setup used for live-watching from this session, since `tqdm` overwrites its line via `\r` rather than emitting discrete `\n`-terminated lines. Recommended running directly in the user's own terminal for real-time visibility instead.
- **Geohash string order is not spatial order.** Decoded `ezjmu5`, `ezjmu6`, `ezjmu7` directly (`pgh.decode_exactly`) to confirm: `ezjmu5`/`ezjmu7` are real east-west neighbors at the same latitude band; `ezjmu6` sits one row south, outside the Retiro bbox entirely. Lexicographically adjacent geohash characters do not imply spatially adjacent cells — bbox-grid sampling (not string-neighbor inference) is the correct way to enumerate candidate cells, which is what `candidate_cells()` already does.
- **Candidate-cell generation is bbox-based, not true polygon intersection** — finds every cell overlapping the polygon's rectangular bounding box, which can include cells outside the actual (non-rectangular) polygon. Acceptable for this prototype; the real polygon→cells geometry refinement (bbox tiling + `shapely` intersection) remains a separate, later step.
- **Row-group pruning validated at three scales, with results that directly answer the original design question:**
  - **Retiro (8 candidate cells):** 1 of 212 row groups read (`1,048,576` rows), latency 0.47s. All 8 cells happened to be lexicographically close enough to fit inside one ~1M-row chunk.
  - **Greater Madrid (783 candidate cells, ~30km x 25km):** still only 1 of 212 row groups touched — confirmed independently via `parquet_metadata()`'s `stats_min_value`/`stats_max_value` footer stats for the `cell` column (note: the raw `stats_min`/`stats_max` columns came back `None` for this dictionary-encoded string column — had to use the typed `_value` variants instead). Finding: geohash's shared-prefix sorting means even a city-metro-sized area can fit inside a single row group if local occurrence density is low relative to the global table's per-group row count.
  - **Mainland Spain (39,721 candidate cells):** 12 of 212 row groups read, in two disjoint clusters (`[70-76]` and `[125-129]`), confirmed exactly by row count (`12,582,912` = `12 × 1,048,576`). This is the key proof: DuckDB skipped the ~48 row groups in the gap between the two clusters, not just reading everything from the first match to the last. Latency 0.79s.
  - **Species results across all three scales are plausible real-world outputs** — Retiro/Madrid both top with `Pica pica` (magpie) and common urban birds; Spain-wide shifts to more rural/widespread species (`Hirundo rustica`, `Sylvia atricapilla`, etc.) — a reasonable sanity check on the data itself, not just the mechanism.
- **Parquet compression**: the filtered/normalized fact table came to 709.96MB on disk (down from BigQuery's 4.71GB logical size), dimension table 39.06MB — total served-bundle estimate ~750MB.
- **Peak-memory measurement via `tracemalloc` reads ~0MB** during the DuckDB query — flagged as a measurement gap, not a real zero: `tracemalloc` only tracks Python-heap allocations, and DuckDB's actual work happens in its native engine, invisible to that instrumentation.

## Decisions and trade-offs

- **Decision: sort-by-cell + DuckDB Parquet row-group pruning is validated as the serving mechanism** — confirmed working at Retiro, Madrid, and Spain scale, including the harder case (pruning across a non-contiguous gap, not just a leading/trailing range). **Why:** this was the open question carried over from `WORK_SUMMARY_081026.md`'s next-steps list (item 3) — whether a request could prune straight to the relevant cells without loading the whole 221M-row/4.71GB table. **Trade-off:** none newly introduced; this closes out the uncertainty rather than trading anything away.
- **User steer (quick assumption, not yet fully stress-tested): bake the served index bundle into the Docker image**, rather than fetch from Cloud Storage at cold start. **Why (user's framing, confirmed with one correction):** this moves the cost of handling the ~750MB bundle to deploy/build time rather than adding a new live fetch step at Cloud Run cold start. **Correction made during discussion:** it's not literally zero-cost at cold start — Cloud Run still has to pull the (now larger) image when a new instance spins up, same mechanism as any deploy; baking in avoids adding a *new separate* network fetch on top of that existing step, it doesn't make image-pull itself free of the extra size. Net effect still favors baking in for simplicity (reuses existing CI/CD, no new GCS dependency) over the Cloud-Storage-fetch alternative that was left open in the prior session.

### What was explored / learnt

- **Initial approach (copying `app/frontend` into a trimmed React/Vite prototype) was reconsidered mid-session as too heavyweight.** User redirected to the established `server_*.py` + `prototypes/web/index_*.html` Flask/vanilla-JS pattern already used by `server_full_validation.py`/`index_full_validation.html` etc. — much faster to build and more consistent with this repo's "prototypes stay standalone, throwaway" convention.
- **Major finding: `specieskey` values in the BigQuery public dataset are NOT legacy GBIF numeric backbone keys.** Verified live: querying BigQuery directly for `species = 'Pica pica'` (real GBIF backbone key `2482484`) returned `specieskey = '4HPXM'`. Root-caused via the user-supplied link (https://data-blog.gbif.org/post/catalogue-of-life-taxonomic-backbone/, fetched and read this session): GBIF migrated its taxonomic backbone to Catalogue of Life (COL XR), whose taxon IDs are short alphanumeric strings like this one — the public BigQuery `occurrences` dataset's `specieskey` column now carries the COL XR id, not the legacy integer key. Old numeric keys still work on GBIF's live APIs, but only when the legacy backbone's `checklistKey` (`d7dddbf4-2cf0-4f39-9b2a-bb099caae36c`) is explicitly supplied — the default has moved to COL XR. GBIF publishes a bulk COL XR → legacy-numeric-key mapping file at `download.checklistbank.org/col/gbif/README.html`; alternatively, the v2 `species/match` endpoint with `checklistKey` set to the COL XR UUID (`7ddf754f-d193-4cc9-b351-99906754a03b`) and `scientificNameID=gbif:<legacy key>` returns the COL XR id for a known legacy key. **This does not block the prototype** — the fact/dimension join is internally consistent since both sides derive from the same BigQuery column — but it does invalidate the common-names batch job and any "View on GBIF" link as previously scoped (both need the legacy numeric key). Fixed in code: `species_key` is kept as an opaque string (no `int()` cast, no GBIF link built from it), with the finding documented inline in `duckdb_e2e_prototype.py`.
- **Second finding, verified not assumed: the Testudines rank override baked into production's `TAXON_GUIDANCE` is actively wrong for the local table.** Production's prompt forces `taxonRank="class"` for "Testudines" specifically because GBIF's backbone API has no single `Reptilia` class. Queried the cached dimension Parquet directly: `SELECT DISTINCT class, "order" ... WHERE class ILIKE '%testud%' OR "order" ILIKE '%testud%'` → `[('Reptilia', 'Testudines')]`. The local table (sourced from BigQuery's raw occurrence string columns, not GBIF's backbone API) has the opposite shape: `class='Reptilia'` is a real value, and `'Testudines'` only appears in `order`. Querying `class = 'Testudines'` against this table returns zero rows every time. Fixed with a narrow, evidenced override — `adapt_filter_for_local_table()` in `duckdb_e2e_prototype.py` — which rewrites `(class, "Testudines")` to `(order, "Testudines")` before building the SQL filter. Confirmed working end-to-end: a live "I want to see turtles" query returned `Trachemys scripta` (red-eared slider, a well-known real invasive species in Retiro's pond) as the top result.
- **This is the one adjustment the LLM taxon-resolution step actually needed** — not a prompt rewrite (the `{taxonRank, taxonValue}` output shape was already correct), but this one rank-override translation applied after the LLM call and before the SQL filter is built. Everything else in `TAXON_GUIDANCE` (reptile/fish expansion, negation handling, multi-taxa segmentation) remains **unverified** against the local string columns — same still-open spot-check carried over from the 8 Oct / earlier-9-Oct sessions, not resolved this session, now folded into next-steps priority 1 below (since the COL XR key problem and the Testudines-class problem are both instances of the same underlying risk: assumptions tuned against GBIF's live backbone API don't automatically hold against the raw BigQuery occurrence columns).
- **Multi-taxa selection validated live, not just read from code**: "plants and birds" correctly produced 2 taxon filters (`kingdom/Plantae`, `class/Aves`), ran one DuckDB query per filter (120ms-1.1s each), and `_select_species_across_groups` correctly quota-selected 3 birds + 2 plants (quota redistribution matches the unmodified production function's behavior).
- **UX problem found through live use, not anticipated in planning:** with geohash precision 6 cells this small relative to Retiro's size (8 candidate cells total), multiple species frequently share the exact same highest-count cell — their hotspot markers stacked exactly on top of each other (`distance_m: 0.0` in the API response), breaking the "walk between 5 distinct spots" visual. Brainstormed options before building (jitter pins / draw cells as zones / one stop per cell listing multiple species) and chose "draw cells as zones" as the quickest fix that stays honest about what the aggregated data actually represents (a cell-level count, not a point sighting) without restructuring the walk's species-per-stop model — deferred the bigger "one stop per cell" reframe as a larger change not needed to validate this session's core question.
- **Route line needed a follow-up fix**: after jittering markers within their cell's rectangle, the dotted route polyline still connected the raw (now visually empty) cell centroids rather than the displayed pins. Fixed by computing each species' jittered position once (`pinPositions`) and reusing it for both the marker and the polyline, so the 1→5 route visibly passes through every numbered pin again.

### Decisions and trade-offs

- **Decision: drop the GBIF `species/match` key-resolution step entirely for the local-index path, rather than adjust it.** **Why:** the local dimension table already carries taxonomy as plain strings; confirmed again this session (not just assumed from the 8 Oct decision) that the LLM's `{taxonRank, taxonValue}` output maps directly onto the table's columns without a key-lookup intermediary. **Trade-off:** none new — this was already the 8 Oct decision, just implemented and proven here.
- **Decision: common names and GBIF links are out of scope for this prototype.** **Why:** explicitly descoped by the user at the start of the session to focus on validating the pipeline shape first. **Trade-off:** species shown by scientific name only; turned out to be the right call given the COL XR finding — building the common-names job without first discovering the key-format mismatch would have wasted the batch run.
- **Decision: fix the clustered-waypoint UX problem at the display layer (geohash cell rectangles + in-cell marker spread) rather than changing candidate-cell geohash precision or data organization.** **Why:** user explicitly asked to solve this "before we think about changing the data organisation" — precision 5 was already ruled out as too coarse in the 8 Oct session, and precision/grouping changes would reopen the row-group-pruning validation from earlier today. **Trade-off:** doesn't fix the underlying density-vs-cell-size mismatch, just represents it honestly; the user may still want the "one stop per cell" reframe later if this isn't sufficient at larger scales (Madrid/Spain) or denser queries.
- **Decision: keep the `google-cloud-secret-manager` install rather than restructure the import to avoid it.** **Why:** discussed explicitly — the dependency is only needed to satisfy `anthropic_client.py`'s unconditional top-level import, never actually invoked locally (`K_SERVICE` unset), is already pinned in `app/backend/requirements.txt`, and keeping it preserves reusing `build_client()`/`resolve_taxon_filters()` completely unmodified (the explicit reuse goal for this prototype). **Trade-off:** one more package in the repo-root `venv` that isn't strictly required for this prototype's own logic.
