## What was explored / learnt

- **BigQuery dataframe download without the Storage API is genuinely slow.** First run of the fact-table export fell back to paginated REST (`UserWarning: BigQuery Storage module not found, fetch data with the REST endpoint instead`) — killed the run after observing low CPU% (I/O-bound) and 318MB resident after ~2 minutes. Installed `google-cloud-bigquery-storage`, which `to_dataframe()` auto-detects, and the re-run completed the full 221M-row download in the time it took to write this summary (~1% per second observed by the user, so roughly 1.5-2 minutes). **Caveat on the kill decision itself:** the original "this will take a long time" call was made from a single memory snapshot plus low-CPU%, not two samples over time — not rigorous, though installing the Storage API was a strict improvement regardless of whether the diagnosis was airtight.
- **Observability fix, now the established pattern for this script:** Python buffers stdout when it isn't a tty, so background-redirected runs showed nothing until a buffer flush. Fixed by running with `python3 -u` (unbuffered) piped through `2>&1 | tee prototypes/logs/<name>_<timestamp>.log` — matches the existing repo convention already used by `intent_query_spike.py` etc., rather than a bespoke logging setup.
- **`to_dataframe(progress_bar_type="tqdm")`** gives a live download progress bar — useful run interactively in a real terminal, but doesn't play well with the `Monitor`/`tee`-to-file setup used for live-watching from this session, since `tqdm` overwrites its line via `\r` rather than emitting discrete `\n`-terminated lines. Recommended running directly in the user's own terminal for real-time visibility instead.
- **Geohash string order is not spatial order.** Decoded `ezjmu5`, `ezjmu6`, `ezjmu7` directly (`pgh.decode_exactly`) to confirm: `ezjmu5`/`ezjmu7` are real east-west neighbors at the same latitude band; `ezjmu6` sits one row south, outside the Retiro bbox entirely. Lexicographically adjacent geohash characters do not imply spatially adjacent cells — bbox-grid sampling (not string-neighbor inference) is the correct way to enumerate candidate cells, which is what `candidate_cells()` already does.
- **Candidate-cell generation is bbox-based, not true polygon intersection** — finds every cell overlapping the polygon's rectangular bounding box, which can include cells outside the actual (non-rectangular) polygon. Acceptable for this prototype; the real polygon→cells geometry refinement (bbox tiling + `shapely` intersection) remains a separate, later step.
- **Row-group pruning validated at three scales, with results that directly answer the original design question:**
  - **Retiro (8 candidate cells):** 1 of 212 row groups read (`1,048,576` rows), latency 0.47s. All 8 cells happened to be lexicographically close enough to fit inside one ~1M-row chunk.
  - **Greater Madrid (783 candidate cells, ~30km x 25km):** still only 1 of 212 row groups touched — confirmed independently via `parquet_metadata()`'s `stats_min_value`/`stats_max_value` footer stats for the `cell` column (note: the raw `stats_min`/`stats_max` columns came back `None` for this dictionary-encoded string column — had to use the typed `_value` variants instead). Finding: geohash's shared-prefix sorting means even a city-metro-sized area can fit inside a single row group if local occurrence density is low relative to the global table's per-group row count.
  - **Mainland Spain (39,721 candidate cells):** 12 of 212 row groups read, in two disjoint clusters (`[70-76]` and `[125-129]`), confirmed exactly by row count (`12,582,912` = `12 × 1,048,576`). This is the key proof: DuckDB skipped the ~48 row groups in the gap between the two clusters, not just reading everything from the first match to the last. Latency 0.79s.
  - **Species results across all three scales are plausible real-world outputs** — Retiro/Madrid both top with `Pica pica` (magpie) and common urban birds; Spain-wide shifts to more rural/widespread species (`Hirundo rustica`, `Sylvia atricapilla`, etc.) — a reasonable sanity check on the data itself, not just the mechanism.
- **Parquet compression**: the filtered/normalized fact table came to 709.96MB on disk (down from BigQuery's 4.71GB logical size), dimension table 39.06MB — total served-bundle estimate ~750MB.
- **Peak-memory measurement via `tracemalloc` reads ~0MB** during the DuckDB query — flagged as a measurement gap, not a real zero: `tracemalloc` only tracks Python-heap allocations, and DuckDB's actual work happens in its native engine, invisible to that instrumentation.

## Decisions and trade-offs

- **Decision: sort-by-cell + DuckDB Parquet row-group pruning is validated as the serving mechanism** — confirmed working at Retiro, Madrid, and Spain scale, including the harder case (pruning across a non-contiguous gap, not just a leading/trailing range). **Why:** this was the open question carried over from `WORK_SUMMARY_081026.md`'s next-steps list (item 3) — whether a request could prune straight to the relevant cells without loading the whole 221M-row/4.71GB table. **Trade-off:** none newly introduced; this closes out the uncertainty rather than trading anything away.
- **User steer (quick assumption, not yet fully stress-tested): bake the served index bundle into the Docker image**, rather than fetch from Cloud Storage at cold start. **Why (user's framing, confirmed with one correction):** this moves the cost of handling the ~750MB bundle to deploy/build time rather than adding a new live fetch step at Cloud Run cold start. **Correction made during discussion:** it's not literally zero-cost at cold start — Cloud Run still has to pull the (now larger) image when a new instance spins up, same mechanism as any deploy; baking in avoids adding a *new separate* network fetch on top of that existing step, it doesn't make image-pull itself free of the extra size. Net effect still favors baking in for simplicity (reuses existing CI/CD, no new GCS dependency) over the Cloud-Storage-fetch alternative that was left open in the prior session.
