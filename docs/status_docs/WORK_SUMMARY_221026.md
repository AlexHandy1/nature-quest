## What was explored / learnt

- **Page-load cold start (no query) is ~19s, almost entirely Cloud Run container provisioning**, confirmed via Cloud Logging timestamps: ~19.3s gap between "Starting new instance" and "Started server process", then <2ms for the actual Python/FastAPI boot, then 207ms for the first real response. `startup_cpu_boost` had no measurable effect (~18.2s vs ~19.6s, within noise) — it only speeds CPU-bound boot work, and the bottleneck here is I/O-bound image pull/provisioning.
- **Cloud Run instances go "idle" (still warm) before scaling to zero** — checking only the `active` instance-count metric gave a false "0 instances" reading while an `idle` instance was still live and answering requests in ~50ms. Had to check both states to get a real cold sample.
- **Production deploys (and CI's post-deploy health-check smoke test) absorb the first cold-start hit before a human ever manually tests** — explains why a redeploy "didn't feel cold" even though the cold start technically still happened, just earlier and invisibly.
- **Early LLM latency spikes (up to 14s) didn't correlate with request order** — one spike landed on request #4 of a sequential run, not #1, ruling out a "connection warm-up" theory; more consistent with OpenRouter's own per-call provider routing variance (same pattern ADR-015 already flagged).
- **A single shared `duckdb.DuckDBPyConnection` is unsafe under concurrent threads — empirically reproduced, not just asserted.** 8 threads hammering one shared connection produced 239/240 wrong-or-missing results (no exceptions, just silently wrong answers); the same test using `.cursor()` per thread produced 0 mismatches. Re-confirmed against the real running server with 3 genuinely concurrent `/api/query` requests for different taxa (birds/plants/reptiles) — each got exactly its own correct species list.
- **Cloud Logging has real ingestion lag** (observed up to ~90s) — an initial checkpoint pull right after a fast test showed incomplete/interleaved-looking data across requests; re-pulling after a short wait resolved cleanly. Don't trust a log pull taken immediately after rapid-fire requests.
- **`taxonRank` is functionally load-bearing in the DuckDB query, not cosmetic** — it selects which `species_dimension` column gets filtered (`RANK_TO_COLUMN` in `services/species_index.py`); the wrong rank silently returns zero rows rather than erroring, which is exactly what the stale Testudines eval assertions would have masked in production.
- **`latency_provider_comparison.py` prototype confirmed `openai/gpt-oss-120b:nitro` running well under 1s per call** (both pinned-to-Cerebras and generic/unpinned), vs. `google/gemini-3.7-flash`'s 2–4s+, with no accuracy loss across all 25 real eval cases.
- **Auto-mode classifier blocked `gcloud run deploy`** (correctly — a real production deploy) **and then over-broadly blocked a read-only Monitoring API call and a plain `curl`** against the same project; corrected mid-session to stop over-applying that caution to unrelated read-only/public-URL actions once flagged by the user.
- **Dead end, corrected mid-session:** spent effort forcing fresh Cloud Run revisions before each production test cell for "guaranteed cold" rigor — the spec's actual "cold vs warm" comparison only meant request-1-vs-2-5 within one run against whatever's currently live, not a guaranteed-zero-instances container. Dropped the forced-redeploy approach once corrected.

## Decisions and trade-offs

- **Decision: cache DuckDB connection/OpenRouter key/client as lazy, double-checked-locking module-level singletons, with the `lifespan` hook just eagerly calling the same lazy builders — not a strict lifespan-only dependency.** **Why:** the existing test suite uses `TestClient(app)` without a context manager in ~15+ files, which never fires FastAPI's ASGI lifespan events (confirmed empirically) — a lifespan-only design would have silently broken every one of those tests. **Trade-off:** none really; this gets "warm once per process" in production and zero test-suite churn simultaneously.
- **Decision: scope credential caching to OpenRouter/GCS only, not `anthropic_client.py`'s Secret Manager key.** **Why:** `anthropic_client.py` is only the manual rollback path for taxon resolution, not the live one, and wasn't part of the original report's recommendation table.
- **Decision: handle newly-cached-credential rotation risk procedurally (document "rotate → must redeploy"), not with TTL/refresh code.** **Why:** both cached credentials are already least-privilege/read-only scoped (ADR-016/018); demo-stage traffic means instances churn often anyway; consistent with this project's existing "accept forced-redeploy over incremental-refresh infrastructure" philosophy (ADR-017). **Trade-off:** a leaked-and-rotated secret needs an explicit redeploy to actually stop already-running instances from using the old value — documented in `infra/README.md`.
- **Decision: switch to `openai/gpt-oss-120b:nitro`, generic/unpinned, not pinned to a specific provider (e.g. Cerebras).** **Why:** the prototype's own data showed generic/unpinned was as fast or faster than the Cerebras pin on this model in real samples; pinning adds a dependency on a human-readable provider-name string in the request body that could silently stop matching if OpenRouter renames/removes that provider.
- **Decision (deferred, explicit): `min_instances ≥ 1` (~$45/month) was discussed at length — the one lever that would also fix the separate page-load cold-start problem (~19s container provisioning) — but not implemented.** Left open given per-request latency is now ~0.7–1.1s, which may change the cost/benefit calculus worth revisiting.
- **Decision (deferred, explicit): the LLM call's own remaining approach/variance beyond the model swap is out of scope for this session** — the user has further ideas to pick up separately.
