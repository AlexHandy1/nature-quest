# Work Summary — 8 October 2026

Design/exploration session, no production code changed. First-principles exploration of replacing the live GBIF API dependency with a pre-aggregated local index built from GBIF's BigQuery public dataset, validated with real BigQuery queries against `bigquery-public-data.gbif.occurrences`.

## What was built

- Scratch BigQuery dataset `nature-quest-504414.gbif_exploration` (auto-expiring, 30-day default table TTL).
- `species_cell_index_global_g6` — materialized global aggregation, geohash precision 6, grouped by `(cell, specieskey, species, kingdom, phylum, class, order, family, genus)`, `WHERE occurrencestatus = 'PRESENT' AND specieskey IS NOT NULL AND decimallatitude/decimallongitude IS NOT NULL`. **549,190,060 rows, 56.25GB.**
- `species_cell_fact_g6_min2` — normalized fact table (`cell, specieskey, occurrence_count` only, taxonomy columns dropped) filtered to `occurrence_count > 1`. **221,666,294 rows, 4.71GB** — the current best candidate for the actual serving artifact.

## What was explored / learnt

- **Request flow was fully traced and diagrammed** for a single-taxon query (e.g. "Birds") through the current production pipeline: LLM taxon resolution (OpenRouter) → `species/match` (GBIF, live) → `occurrence/search` (GBIF, live, paginated) → route ordering (pure) → per-species enrichment (`vernacularNames` GBIF live + Wikipedia live, sequential pair per species, ≤3 species concurrent). Confirmed via `app/backend/routers/query.py` and `app/backend/services/species_enrichment.py` — minimum ~12-13 live HTTP calls per single-taxon query, three distinct `GbifUnavailableError` points (stages 2 and 3 explicitly guarded; stage 5's `fetch_common_name` GBIF call is **not** guarded with the same `gbif_unavailable` outcome branch — worth noting as an existing gap, not something this session's redesign addresses).
- **BigQuery schema check** (`bigquery-public-data.gbif.INFORMATION_SCHEMA.COLUMNS`, table `occurrences`) revealed the real schema differs from assumption: **no numeric rank-key columns** (`kingdomkey`/`classkey`/etc. don't exist) — only string columns (`kingdom`, `phylum`, `class`, `order`, `family`, `genus`, `species`) plus `taxonkey`/`specieskey` typed as **STRING**, not INTEGER. No `hascoordinate` boolean either — must filter on `decimallatitude`/`decimallongitude IS NOT NULL` directly. `order` is a reserved SQL keyword, needs backticks.
  - **Consequence (positive):** taxon-rank filtering can be plain string equality (`class = 'Aves'`) matching the LLM's own output directly — eliminates the need for any `species/match`-equivalent key-resolution step for the local index path entirely, not just as a fallback.
- **BigQuery on-demand cost model clarified through direct testing:**
  - Full global aggregation query (9 columns, no filter tricks): dry-run estimate **393.21GB** — comfortably inside the 1TB/month free tier, so $0/month for a monthly rebuild job under current pricing.
  - Adding a `WHERE countrycode = 'ES'` filter **increased** the estimate past 400GB rather than reducing it — confirmed that row-level `WHERE` filters don't reduce bytes scanned on this unpartitioned/unclustered table (they only reduce output size); the extra column referenced in the filter adds to the scan instead.
  - Geohash precision (`ST_GEOHASH(..., 1)` vs `(..., 6)`) **does not affect bytes scanned at all** — it's a compute-time scalar function, not a storage/column-read change. Precision is free to pick based on product fit, not cost.
  - `TABLESAMPLE SYSTEM (n PERCENT)` is the only lever that actually reduces scan bytes (samples random storage blocks pre-filter) — useful for quick sanity checks, not for precise country-specific row counts (samples globally, not within a country).
  - Real job stats: "Slot time" (10hr 25min) and "Bytes shuffled" (610.94GB) are **not** billing metrics under on-demand pricing — only "Bytes billed/processed" is. Actual wall-clock elapsed time for the full materialization: **42 seconds**.
  - Confirmed real-world cost math: BigQuery storage pricing $0.02/GB/month (first 10GB free); the 56.25GB scratch table ≈ $0.93-1.13/month if left indefinitely (not the plan — it's scratch, auto-expiring).
- **Dead end / correction: querying BigQuery live, per-request, is not viable as the serving path** — BigQuery's query startup overhead and per-scan billing make it a worse fit than even the current GBIF live API for request-time latency. BigQuery's role is strictly the monthly batch-build source; the serving side must be a local file (DuckDB/SQLite) loaded by the Cloud Run instance, never queried live.
- **Correction on Cloud Run statelessness concern:** the user raised whether Cloud Run's ephemeral instances rule out an in-memory/local index. Clarified: statelessness only prohibits relying on in-memory data as a *write* system of record. A read-only index rebuilt monthly and *loaded fresh* at each cold start (either baked into the Docker image or fetched once from Cloud Storage at startup) is a standard, safe pattern — the real cost is added cold-start load time, not data loss.
- **Row-count reality check:** the first full materialization (549M rows / 56.25GB) was far larger than the original "tiny index, load entirely into memory" assumption. Root cause: geohash precision 6 (~1.2km cells) applied globally, combined with biodiversity data's enormous long tail (most rows are single-sighting species-in-cell combinations).
- **Two independent shrink levers tested:**
  - **Schema normalization** (move `kingdom`/`phylum`/`class`/`order`/`family`/`genus` out to a separate species-dimension table, since they're fully determined by `specieskey` and don't vary per cell): confirmed the dimension table is small — **1,322,269 distinct species globally** (`COUNT(DISTINCT specieskey)`, run cheaply against the already-materialized table rather than the raw 393GB source). Normalization reduces bytes/row (~102 → ~20 bytes/row estimated) but **does not reduce row count** — taxonomy columns don't add grouping granularity beyond `specieskey` itself.
  - **Coarser geohash precision**: ruled out by the user — precision 5 is already too coarse for the walk-design use case (needs to stay closer to the current dynamic 5×5 per-query grid's effective ~1km resolution).
  - **Minimum-observation-count threshold** (drop `occurrence_count = 1` rows, i.e. require a species be seen more than once in a cell): tested at two thresholds against the real materialized table:
    - `>1` (seen ≥2): removes 327,523,766 of 549,190,060 rows (59.6%), leaving 221,666,294.
    - `>2` (seen ≥3): removes 417,413,692 rows (76.0%), leaving 131,776,368 — diminishing returns, and a materially different risk profile (starts risking under-surveyed areas/species being dropped entirely, not just filtering out true one-off anomalies). `>1` was chosen as the working threshold for the materialized fact table.
- **Specieskey-null sanity check**, run against the live GBIF API first (confirmed no "is null" filter capability exists on `occurrence/search` — only equality filters on specific key values), then correctly against BigQuery itself (same table the extraction uses, most apples-to-apples source):
  - Live API: 3,961,449,047 total global occurrences; 3,825,243,649 with `occurrenceStatus=PRESENT`.
  - BigQuery (`bigquery-public-data.gbif.occurrences`, `WHERE occurrencestatus = 'PRESENT'`): 278,030,856 missing `specieskey` / 3,327,758,745 with it / 3,605,789,601 total — **7.71% missing**, and these are understood to be records identified only to a higher rank (genus/family/order), not corrupted data, so the exclusion is well-justified for a species-listing product.
  - **Noted but not yet investigated further**: BigQuery's `PRESENT` total (3,605,789,601) is ~5.7% lower than the live API's current `PRESENT` total (3,825,243,649) — consistent with the already-accepted monthly-snapshot staleness trade-off, not a new concern, but the first time the actual size of that gap has been measured.
- **Resolved a console/CLI friction point**: `CREATE TABLE ... AS SELECT` into a destination table failed with `Access Denied: Table bigquery-public-data:gbif.occurrences: User does not have permission to query table ... or perhaps it does not exist` — diagnosed as a **location mismatch** (the public dataset lives in the `US` multi-region; a destination dataset created in a different region breaks a single-location job), not a permissions or Legacy-SQL issue as first suspected. Fix: create/recreate the destination dataset with location set to `US` (multi-region).
- Clarified BigQuery's bytes-processed field (not "Slot time" or "Bytes shuffled") as the only on-demand billing-relevant statistic — addressed directly after user confusion over the job-stats panel.
- Clarified the byte-conversion for the console's "Limit the number of query bytes processed" safety field: BigQuery uses binary GB (2^30 bytes), so 250GB = `268435456000`.
- **Common-names batch job sized directly against the live API**: `species_cell_fact_g6_min2` has **917,827 distinct species** (`COUNT(DISTINCT specieskey)`). Live-timed `GET /v1/species/{key}/vernacularNames`: single-call average ~0.166s (10 real species); a 100-species concurrency test (Python `ThreadPoolExecutor`, real GBIF calls) showed **zero `429`s at concurrency 3, 5, and 10**, with near-linear scaling (3: 5.45s total/0.0545s per call; 5: 3.24s/0.0324s; 10: 1.73s/0.0173s). Extrapolated to the full 917,827 species: **~13.9hr at concurrency 3, ~8.3hr at concurrency 5, ~4.4hr at concurrency 10**. Explicitly flagged as provisional — a 100-call burst over a few seconds doesn't test sustained multi-hour load the way production code's own `occurrence/search` 429s only appeared under real sustained concurrent use; a longer test (2,000-5,000 calls) at the chosen concurrency is still needed before committing to a number for the real batch job.
- **Deep design exploration: could RAG/embeddings replace the LLM taxon-resolution step, and could the resolution step work without an LLM/Jev-type router at all?**
  - Looked up **Jev** (typesafe.ai) via `WebFetch`: a hosted, closed-weight "System 1" decision model returning calibrated probabilities over a fixed, caller-supplied option set (Noul/Choice/Score question types), explicitly marketed for routing/filtering before an expensive LLM call. **Assessed as a plausible fit for a router role** (e.g. classifying "simple term / compound / adversarial-negated / qualitative-only" before deciding whether to hit a cheap lookup or the LLM) but **not adopted** — it's closed-weight, hosted-only, from a company with no published benchmarks/architecture and apparently still in early access, which cuts against this session's broader goal of *removing* fragile dependence on unverified external services, not adding a new one for a secondary cost optimization.
  - Designed a **tiered/cascading taxon-resolution architecture** as the RAG-adjacent alternative: Tier 0 (exact hash lookup on a normalized term → `{rank, value, specieskey}` flattened vocabulary table, spanning every rank kingdom→species, sourced from curated synonyms + real GBIF vernacular/scientific names fetched during the batch job above) → Tier 0.5 (fuzzy string match, e.g. `rapidfuzz`/trigram, no ML) → Tier 1 (small local sentence-embedding model, e.g. `all-MiniLM-L6-v2`, ~80MB, CPU, embeddings precomputed once at batch time over the vocabulary table, query-time only embeds the single candidate n-gram span) → LLM fallback for anything unresolved. Candidate extraction from free text (e.g. "I want to see some interesting birds and plants") designed as brute-force 1-3 word n-gram generation tested against the vocabulary, relying on the closed taxonomic domain to naturally reject filler words rather than needing real NLP parsing.
  - **Worked a concrete "magpie" example through this design and found real gaps, not just theory:**
    - A single term can map to **different specificities** ("birds" → `class:Aves`, broad; "magpie" → `species:Pica pica`, narrow) — resolved by baking the rank+value directly into each vocabulary anchor at batch time, not inferring it at query time.
    - **Common-name collisions are real and unresolved by a simple dict**: "magpie" as an English vernacular name isn't guaranteed unique to one species globally (e.g. regional magpie species elsewhere). A plain Tier 0 dict silently picks one meaning; this session converged on a better fix — resolve to the **top-N nearest embedding candidates**, run the geospatial fact-table lookup for all N `specieskey`s against the user's actual polygon, and let real local occurrence presence (not a hardcoded global default) disambiguate which species was actually meant.
    - **Dead end, caught and corrected mid-discussion**: initially claimed the LLM was already doing sophisticated, location-aware disambiguation for cases like this and therefore "justified its latency." Checked against the actual code and found this wrong on two counts — `routers/query.py`'s `_resolve_taxon_filters()` never passes the polygon to the LLM call at all, and `anthropic_client.py`'s `QUERY_SCHEMA_TOOL` enum (`kingdom, phylum, class, order, family, genus`) **has no `species` option** — the current production system cannot resolve to species rank in the first place, let alone disambiguate it by location. Neither the existing LLM step nor the proposed cascade solves species-level, location-aware disambiguation today; it would be a genuinely new capability if pursued, not a performance comparison between two systems that both already attempt it.
  - **Conclusion reached (checked and largely upheld):** RAG/embedding cascades are a poor fit for replacing what the LLM demonstrably already does well today — negation handling, adversarial/off-topic input, qualitative-intent dropping, multi-taxa segmentation — because none of that is genuinely solvable by closed-vocabulary lookup or embedding similarity alone. The one correction made on review: this isn't because "the LLM already handles disambiguation" (it doesn't attempt species-level disambiguation at all today), but because RAG doesn't compete with the specific NLP robustness the LLM provides — species-level disambiguation via geo-filtering would be *additive new scope*, not a replacement for the existing resolution step.

## Decisions and trade-offs

- **Decision:** Explore a BigQuery-sourced, monthly-rebuilt, pre-aggregated local index (geohash/cell × species counts) as the replacement for live GBIF `occurrence/search` + `species/match` calls, rather than live-querying BigQuery itself or just hardening the existing live-API retry/concurrency logic. **Why:** removes both the latency (pagination-heavy live calls) and reliability (429s under concurrency) problems identified in the existing `docs/FEATURE_IDEAS_BACKLOG.md` backlog item, within a $5-10/month ceiling and the user's explicit willingness to own more operational complexity in exchange for a learning opportunity. **Trade-off:** monthly freshness only (accepted explicitly); user now owns a batch ETL pipeline instead of an API-error-handling story; serve-time polygon↔cell matching introduces a new boundary-approximation error that the live API's exact point-in-polygon test doesn't have.
- **Decision:** Prior backlog suggestions (BigQuery/AWS/hybrid framings from earlier in this session) were explicitly **not** written into `docs/FEATURE_IDEAS_BACKLOG.md` — the user wanted a first-principles design discussion instead of parking ideas prematurely. **Why:** user explicitly rejected the parking-in-backlog edit mid-session. **Trade-off:** today's findings currently live only in this WORK_SUMMARY, not yet reflected in the backlog's existing "Rearchitect GBIF data dependency" theme — worth reconciling next session.
- **Decision:** Taxon-rank filtering against the local index will use plain string equality (`class = 'Aves'`) rather than numeric GBIF backbone keys. **Why:** the BigQuery public dataset only exposes rank names as strings, not numeric per-rank keys — discovered via schema inspection, not an upfront choice. **Trade-off:** depends on exact string/casing consistency with GBIF's backbone (not yet spot-checked against the local table the way the live API's `species/match` behaviour was verified in the 30 Aug session for Testudines).
- **Decision:** Working fact-table filter is `occurrence_count > 1` (not `>2` or unfiltered). **Why:** best balance found so far between row-count/storage reduction (59.6% of rows removed, 56.25GB → 4.71GB combined with normalization) and preserving genuine rare-sighting data the product's `sort: rarest` feature depends on; `>2` was judged to risk under-surveyed-area species starvation for only modest additional savings. **Trade-off:** `sort: rarest` will now mean "rarest among species seen ≥2 times in-area," a subtly different product claim than "rarest ever recorded" — not yet reflected anywhere user-facing.
- **Decision:** Serving architecture should use DuckDB over a `cell`-sorted/partitioned Parquet export (row-group pruning), not a full in-memory load and not a live BigQuery query per request. **Why:** 221.67M rows / 4.71GB is too large to safely load entirely into Cloud Run process memory, but a per-request query only ever touches the handful of cells covering a ≤25km² polygon — pruning avoids scanning the full table per request regardless of its total size. **Trade-off:** adds a new dependency (DuckDB) and a Parquet export/sort step to the batch pipeline; not yet prototyped.
- **Open, not yet decided:** whether the served index file is baked into the Docker image (reuses existing CI/CD, simpler, grows image/cold-start-pull size) or stored in Cloud Storage and fetched once per cold start (decouples refresh from deploys, adds a GCS dependency). Leaning towards Cloud Storage for separation of concerns, but explicitly left open.
- **Decision: do not attempt to replace the LLM taxon-resolution step with a RAG/embedding cascade or an external router (e.g. Jev).** **Why:** the LLM's demonstrated value is in NLP robustness (negation, adversarial/off-topic input, multi-taxa segmentation) that a closed-vocabulary lookup or embedding similarity search cannot reliably reproduce; a cascade's main concrete benefit (catching common single-term cases cheaply) is unproven against real traffic and adds real new failure modes (common-name collisions, threshold tuning) for an uncertain win. **Trade-off:** leaves LLM cost/latency (already flagged as ~2x original estimate per ADR-015) unaddressed by this decision alone — see the follow-up decision below.
- **Decision: the next concrete optimization target, once the local occurrence DB is live, is the LLM step itself** — explicitly **not** a same-tier swap to another hosted proprietary model (Haiku-class was raised and rejected — still the same cost/closed-weight category as the `google/gemini-3.7-flash` already in production and the ~2x-cost-overrun problem flagged in ADR-015). Instead: benchmark **radically lighter-weight, open-source models** (e.g. Gemma-family) sourced via OpenRouter and/or directly via HuggingFace, against the existing `test_taxon_resolution_eval.py` suite, and scope light fine-tuning on one of these smaller open-source models as a learning opportunity. **Why:** this is a narrow, well-scoped structured-output task (text → `{taxonRank, taxonValue}` pairs) well-suited to a much smaller/fine-tuned model; the model-agnostic OpenRouter client (`ADR-015`) already makes model-swapping a one-constant change for the OpenRouter-sourced route, and the eval suite already encodes the hard cases (Turtles, fish/reptile expansion, negation, adversarial input) needed to verify a lighter model doesn't regress on them. Open-source specifically also makes fine-tuning and potential self-hosting viable in a way a closed API model isn't. **Trade-off:** not yet started; needs a review of what's actually available on OpenRouter vs. HuggingFace directly (different cost/latency/self-hosting trade-offs between the two routes), and real production query volume before fine-tuning specifically is worth pursuing over just benchmarking smaller off-the-shelf models first.
