## What was explored / learnt

- **Judge non-determinism is real, not just narrator non-determinism.** Same evidence (e.g. "Western Palearctic" named verbatim from the extract), different runs of the judge gave opposite faithfulness verdicts. Set judge `temperature=0.2` (down from unset/default 1) to reduce this, narrator stays at `temperature=1` for creative variety per explicit request.
- **Judge prompt gaps found via live runs, not speculation**: "this precious habitat" (vague, unnamed) was wrongly flagged as a specific habitat claim — fixed by clarifying the judge tool's `unsupported_habitat_claims` description to exclude generic unnamed words. "buildings and open spaces" (a general description of the walk's own visible setting) was also wrongly flagged — fixed by extending the same carve-out to cover general-setting descriptions, not just place names.
- **Generator gaps found via live runs**: a run summarized 5 species down to essentially 1 (only the carp) — fixed by adding an explicit "mention every one of the N species by name" instruction to the prompt. "Worldwide"-style range overgeneralization (extract says "temperate Americas, Eurasia, North Africa", narrative said "worldwide") persisted even after one round of tightening — a second, more explicit ban on unqualified absolute-scope words was added, alongside a related but distinct "don't narrow a wide range down to sound local" instruction (`native to this very region` vs. the extract's actual `Western Palearctic`).
- **Near-miss: unmocked tests can make live paid API calls.** Three new field-length-validation tests were written referencing "422" as the expected status but without mocking `generate_narrative`/`synthesize_speech` — since no `max_length` constraint existed yet at that point, the request wasn't rejected at the Pydantic layer and the tests likely hit the real Anthropic API (getting 422 back by coincidence, probably the refusal guardrail firing on gibberish `"aaa...a"` input) at genuine cost. Caught immediately after the fact by noticing the test run passed *before* any implementation change existed. Fixed by adding the `max_length` constraints (making Pydantic reject before the route handler ever runs) and rewriting the tests to assert `mock_generate.assert_not_called()`/`mock_tts.assert_not_called()`, so a future regression would fail loudly rather than silently re-triggering live calls.
- **Terraform drift discovered live during `terraform plan`**: the Cloud Run service had `client = "cloud-console"` and an explicit `scaling { manual_instance_count = 0, min_instance_count = 0 }` block not matching the declared config — from a manual Console edit. User confirmed this is a recurring, known discrepancy (intended `max_instance_count = 2`). Applied in full (not scoped/targeted) per explicit instruction.
- **`terraform apply` hit a 409** — the `openrouter-api-key` secret already existed in GCP (created via Console when the user added the secret value), so Terraform's `google_secret_manager_secret.backend["openrouter-api-key"]` create step conflicted. Resolved via `terraform import 'google_secret_manager_secret.backend["openrouter-api-key"]' projects/nature-quest-504414/secrets/openrouter-api-key`, then re-planned and applied cleanly (added the IAM binding only). Confirmed for the user: importing this resource type pulls in no secret material — `google_secret_manager_secret` is metadata-only; the actual value lives in a separate `google_secret_manager_secret_version` resource never declared in this Terraform config at all.
- **Species dict field-name mismatch caught before wiring the router**: `generate_narrative()` was initially built against `lat`/`lon`, but production species dicts use `hotspot_lat`/`hotspot_lon` (`gbif_client.py:248-249`). Caught by checking `gbif_client.py` directly before assuming the shape, fixed across `services/narration.py`, `tests/test_narration.py`, and the eval sample-walk fixtures before the frontend/router work that depended on it.

## Decisions and trade-offs

- **Decision:** Wikipedia extract fetched in `enrich_species()` (piggybacked, free) but carried to the narration step via a frontend round-trip, not backend caching. **Why:** the app has no session/cache layer anywhere else; `enrich_species()` runs unconditionally on every query result while narration is optional, so backend caching would mean holding state for walks that likely never trigger narration. **Trade-off:** narration's request payload is a bit heavier (species objects carry extract text). See ADR-014.
- **Decision:** `POST /api/narrate` does narrative generation + TTS synthesis synchronously in one call, returns `{narrative, audio: base64}` — no separate audio-fetch endpoint, no object storage, no streaming. **Why:** the intended UI (one button, loading → play, audio ready before play is even offered) makes a two-step design add complexity without a real UX gain; object storage/streaming solve problems this ephemeral, no-accounts, single-session app doesn't have. See ADR-014 for the full alternatives comparison.
- **Decision:** Narration gets its own separate daily budget counter (`narration_budget.py`), same rate-limit mechanism as `/api/query`. **Why:** materially different, higher cost profile per call (narrative + TTS vs. one small classification call); narration is explicitly secondary, so a burst there shouldn't be able to exhaust the core query flow's budget.
- **Decision:** Abuse mitigation for inappropriate/non-organism content uses a prompt-level refusal mechanism at the generation step (model outputs a fixed marker instead of a narrative; code detects it deterministically), not a second LLM moderation call, not GBIF re-validation of client-submitted species data. **Why:** explicit user preference — avoid adding another non-deterministic check step to evaluate/protect separately; lean on the model's own alignment, reinforced by explicit prompt instruction, with deterministic detection on the code side. Confirmed working live against a crafted non-organism test case. **Trade-off:** this is a mitigation, not a deterministic guarantee — a sufficiently crafted prompt-injection attempt could theoretically still defeat it, since `/api/narrate` accepts client-submitted species data directly with no GBIF/Wikipedia re-validation. Recorded as an accepted residual risk in both the security review output and ADR-014, deliberately deferred (the stronger fix — re-fetching `common_name`/`extract` server-side and discarding client values — was discussed and explicitly not built this session).
- **Decision:** `OPENROUTER_API_KEY` follows the exact same explicit Secret Manager client-library fetch pattern as `ANTHROPIC_API_KEY` (ADR-006/REQ-005), not Cloud Run's simpler native env-var injection. **Why:** this is an open-source repo — the existing rationale (an explicitly-fetched secret can't be accidentally swept into a wholesale `os.environ` log dump the way a plain env var could; matters more for unknown future external contributors than a single maintainer) applies identically to the new key.
- **Decision:** PostHog AI observability wiring for narration mirrors `routers/query.py`'s `_resolve_taxon_filters` pattern exactly (`ai_observability.build_client()`, `posthog_distinct_id` extra kwarg, `on_response` usage capture, tokens logged alongside outcome). **Why:** explicit ask to route narration traces into the same observability system "along with the original queries" — this pattern *is* that mechanism, not separate scope from it.
- **Decision:** Security review's one actionable finding (unbounded `SpeciesInput` field lengths) fixed with `common_name`/`species` capped at 500 chars, `extract` at 2000 chars — generous headroom (~4x the largest real Wikipedia extract seen this session, ~350-500 chars) rather than tight limits, per explicit request ("still quite small and at least is some cap").
- **Decision:** Deterministic GBIF species-name validation (re-validating a submitted scientific name resolves to a real GBIF species before generating) was discussed as a second abuse guardrail but **not built this session** — user judged the refusal guardrail sufficient for now.
