## What was explored / learnt

- **PostHog's AI Observability product** (OpenTelemetry-based auto-instrumentation of the Anthropic SDK, `AnthropicInstrumentor().instrument()` + `PostHogSpanProcessor`) — researched via WebFetch against PostHog's docs. Captures every real Anthropic call as an `$ai_generation` event (input, output, tokens, cost, latency) with no manual cost-calculation code needed. Free at this project's scale (100K events/month free tier vs. a few thousand/month realistic usage). Key finding: it does **not** automatically share identity with the existing client-side PostHog SDK — `distinct_id` is an optional resource attribute that must be explicitly passed from frontend to backend, the same gap Slice 1's `ADR-007` already flagged and deferred for the interest-form's server-side capture. This slice is where that passthrough finally gets built.
- **DeepEval vs. PostHog AI Evals** — researched both via WebFetch. DeepEval is an open-source, pytest-native LLM eval framework ("Pytest-style assertions… built to run with pytest and CI providers"), suited to offline, pre-merge regression checks on deliberately chosen test cases. PostHog AI Evals runs *inside* PostHog against already-captured `$ai_generation` traffic (code-based/Hog rules or LLM-as-judge), suited to live, ongoing quality monitoring rather than a pytest-gated check. Concluded both add distinct value at different stages (offline dev vs. live production) rather than being alternatives to choose between — both are now in the spec.
- **Security-detail disclosure precedent** — confirmed via re-reading `ADR-007`/`ADR-008` and Slice 1's own spec (`REQ-017`/`GUD-002`) that this project has an established convention of naming the *category* of a protective mechanism in written specs without publishing its exact tuned parameters (rate-limit thresholds, budget caps, timeout/retry values), since the repo is public from day one. Applied consistently in the new spec (`CON-002`) — the numbers agreed upon during the interview are deliberately not written into the committed document.
- **GBIF's known scale problem re-confirmed**: `WORK_SUMMARY_250726.md`'s finding that birds (or any common taxon) over the `2023,2026` range in Retiro returns ~57,000 occurrences (~190 pages to paginate) is directly relevant to this slice's single-taxon-filter scope — carried the existing `e2e_walk_spike_clustering.py` scale-guard mitigation (probe count, fall back to single year above a threshold) into the new spec rather than re-deriving it.
- **API key delivery: Secret Manager client fetch vs. Cloud Run env-var injection** — worked through two threat models. Against an attacker with code execution in the container, the two approaches are equally exposed (Cloud Run's metadata server hands ambient service-account credentials to any code either way). They diverge only against accidental, self-inflicted leaks (e.g. this project's own `JsonLogFormatter` sweeping up `extra=dict(os.environ)` by mistake) — a narrower risk for a solo maintainer with personal discipline, but a real one for an open-source project with unknown future contributors. This was the deciding factor for choosing the explicit-fetch approach.
- **`max_instance_count`/`min_instance_count` pinning to 1, Firestore, and a GCS generation-precondition counter** were all explored in detail as alternatives to an in-memory daily-budget counter and rejected — none solve the redeploy-reset problem cleanly enough (instance pinning) or are judged proportionate to a solo project's current risk (Firestore/GCS), see the spec's §9 for the full reasoning.

## Decisions and trade-offs

- **Decision:** Slice 2's GBIF feature is a single high-level taxon-category mapping only — no mixed-taxa, no `q` free-text passthrough, no `rarest` sort, replacing the full `PLANNING_INTENT_QUERY_210726.md` design for this round. **Why:** the primary goal of this slice is proving the guardrails end-to-end against a real third-party call, not building the fuller feature; dropping `q` specifically removes the one field in the original design that relied on prompt-level instruction as its only guardrail. **Trade-off:** less query flexibility for now; explicitly deferred to later PRD slices (3+).
- **Decision:** Two independent, layered cost/abuse guardrails — per-IP rate limiting (`slowapi`, in-memory) and a separate global daily LLM-call cap (module-level counter, in-memory) — rather than either alone or a persistent-store-backed counter (Firestore/GCS/Redis all considered and rejected). **Why:** per-IP limiting alone doesn't cap total spend across many sources; a global cap directly matches the user's stated risk tolerance (solo, non-commercial, willing to degrade the whole app for a day rather than risk debilitating cost). Persistent stores were judged disproportionate infrastructure for current traffic. **Trade-off:** both counters reset on redeploy/cold start/multi-instance — explicitly accepted, backstopped by the pre-existing Anthropic account-level billing hard-stop.
- **Decision:** Anthropic API key fetched explicitly via the Secret Manager client library at app startup, not via Cloud Run's native `secret_key_ref` env-var injection (which was the initial recommendation). **Why:** reversed mid-conversation once the open-source contributor angle was raised — env-var injection is equally safe against an attacker, but meaningfully less safe against accidental leaks (e.g. a future external contributor's debug logging) than an explicitly-fetched variable, and "just don't do that" only holds for a maintainer who was part of this specific conversation.
- **Decision:** Unresolved taxon categories return a generic message with **no GBIF call made at all**, rather than falling back to a default unfiltered search. **Why:** explicit user preference — this is the branch that proves the pipeline correctly *doesn't* call the third-party API, mirroring the pre-validation gate already proven in the fuller prototype (PRD Story 4), rather than always showing "something."
- **Decision:** PostHog AI Observability (server-side LLM trace capture) is gated by the same client-side consent banner as existing product analytics, not treated as exempt first-party operational data. **Why:** consistency with the project's existing privacy posture — it sends real query content to a third party, a materially different decision than first-party Cloud Logging. **Trade-off:** declined-consent users get less LLM-level observability; Cloud Logging's guardrail/outcome-level signal remains available either way as a fallback if opt-in rates turn out too low.
- **Decision:** Both DeepEval (pytest-run, offline) and PostHog AI Evals (live, production-traffic) are built into this slice, not one or the other. **Why:** they serve genuinely different moments — pre-merge regression on known cases vs. ongoing drift detection on real traffic — and PostHog Evals' marginal setup cost is near-zero once REQ-019's OTel capture already exists.
- **Decision:** Basic GCP-native alerting (Cloud Monitoring uptime check + 5xx-rate alert policy, both emailing the maintainer) added to this slice's scope, deliberately narrow (one channel, no paging/escalation). **Why:** the project has logging and is gaining LLM observability this slice, but had zero alerting — nothing proactively notifies the maintainer when something breaks. Chosen as GCP-native (Terraform-provisionable, consistent with the rest of `infra/`) over a third-party tool, proportionate to a solo maintainer's stated need ("so I can see something going wrong and act"), explicitly framed as a foundation for more granular alerting later (e.g. per-guardrail-trigger or cost-anomaly alerts), not a comprehensive system now.
- **Decision:** The notification email address is a Terraform variable with no committed default (`CON-003`), not hardcoded into `monitoring.tf`. **Why:** the repo is public from day one (`ADR-008`) — a personal email address shouldn't be committed just because it isn't formally a secret.
- **Decision:** Exact numeric thresholds (rate limit, daily cap, max query length, GBIF retry/timeout values) agreed during the interview are **not written into the committed spec document**, per this project's existing disclosure convention (`ADR-007`/`ADR-008`, mirrored from Slice 1's `REQ-017`/`GUD-002`). **Why:** named explicitly to the user as a deliberate deviation from what was verbally agreed, since it changes what ends up in a public document; the user did not object. **Trade-off:** the actual production values now need to be chosen and set as build-time constants/config during implementation, not looked up from this spec.
- **Learning (agent behavior, not project-technical):** a mid-session checkpoint/planning doc written for continuity ("in case the session drops") is a snapshot of that moment, not a living document — should not be iteratively re-edited as later conversation turns revise earlier decisions. The user explicitly corrected this once (`PLANNING_LLM_GUARDRAILS_040826.md` should not have been re-opened for editing) and separately corrected an attempt to persist this exact learning to Claude's internal memory folder, which CLAUDE.md explicitly prohibits for this project — the correct home for durable learnings here is this WORK_SUMMARY file (and future ADRs/specs), not `~/.claude/.../memory/`.
