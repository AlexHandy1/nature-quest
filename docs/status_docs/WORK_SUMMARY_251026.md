# Work Summary — 25 October 2026

Follow-on from `WORK_SUMMARY_241026.md`'s first successful real run of the monthly GBIF update pipeline. That run promoted correctly, but investigating the common-names cache afterward surfaced a real, permanent bug: the same ~47,000-species ChecklistBank batch was being silently re-fetched and discarded every month, forever. Diagnosed, backfilled, fixed, and validated live.

## What was built

1. **`app/backend/jobs/backfill_common_names_negative_cache.py`** (+ `tests/test_backfill_common_names_negative_cache.py`, 3 tests) — one-off manual script that marks species already looked up in a prior run but with no ChecklistBank name as explicitly checked (`common_name=NULL` in the cache row, present rather than absent), with zero new ChecklistBank calls. Reuses `compute_top_n_specieskeys`/`new_entrants`/`write_parquet`/`upload_file`/`download_blob_to_file` from the main module rather than duplicating logic. Run for real against production: backfilled 47,064 confirmed-empty entries (cache grew from 59,199 to 106,263 rows, zero duplicate keys, all prior entries left untouched).
2. **`app/backend/jobs/monthly_gbif_update.py`** — added `fetch_and_merge_common_names(cache, entrants, dataset_key, fetch_fn)`, replacing the inline try/except in `run()`'s Step 4. Records `common_name=None` for every entrant that was attempted but got nothing back, not just the ones that succeeded. Updated `new_entrants`/`merge_into_cache`/`join_common_names` type signatures to `dict[str, str | None]` (no behavioral change needed in any of them - all three already handled `None` correctly once it existed, confirmed by tests). 5 new/updated tests in `tests/test_monthly_gbif_update.py`, including a rewritten `test_run_promotes_the_release_on_a_clean_pass` that now exercises a real `fetch_fn` (one entrant gets a name, one gets nothing) through the full `run()` orchestration rather than mocking the fetch away, and a dedicated zero-entrants regression test (`test_fetch_and_merge_common_names_is_a_cheap_noop_with_zero_entrants`) locking in the exact steady-state scenario expected going forward.
3. **`docs/decisions/ADR-020-common-names-cache-records-confirmed-empty-lookups.md`** — full write-up of the bug, the fix, the alternatives considered (a separate "attempted" column - rejected; per-task fault isolation in `fetch_common_names_for_taxa` - explicitly deferred per the user's call), and the consequences (permanent `None` entries never re-checked; a newly-flagged risk that cache entries aren't versioned against `CHECKLISTBANK_COL_XR_DATASET_KEY`, so a future dataset-key migration should clear the cache).
4. **`ARCHITECTURE.md`** — one-line addition to the "Monthly GBIF update" subsection pointing to ADR-020.

All changes merged to `main` via branch `fix_common_names_update` (PR #40), CI/CD green, deployed, and validated with a real live run (see below).

## What was explored / learnt

- **Root cause, found by re-checking production rather than trusting the "success" of the 24 Oct run**: `common_names_cache.parquet` showed exactly 59,199 rows both *before and after* the 24 Oct run - byte-for-byte unchanged, despite Step 4 having taken ~8m45s (consistent with 47,070 real ChecklistBank calls actually happening). Initially hypothesized a batch-discarding exception (one bad HTTP call killing the whole `future.result()` loop); **disproven** by checking real Cloud Run logs at severity>=WARNING for that execution - zero hits, no exception was logged. The user's own diagnosis was the correct one: `fetch_common_names_for_taxa` only ever produces a cache entry for a *successful* lookup, so a confirmed-empty result and a never-attempted one are indistinguishable - the same known-failing batch gets retried and silently dropped every month, with no possibility of ever resolving itself.
- **Traced the full common_name data flow end-to-end** (prompted by the user asking to "step through exactly at a code level" given prior misunderstandings this session): BigQuery/ChecklistBank fetch → cache persistence → `join_common_names`'s `LEFT JOIN` onto the dimension table → `services/species_index.py`'s live query (no fallback logic at all) → `routers/query.py`'s response → frontend. Found the one place a wrong sentinel choice would have broken something real: `ResultsPanel.tsx:42` and `NarrationControl.tsx:35` both use `s.common_name ?? s.species` (nullish coalescing) - only falls back for `null`/`undefined`, *not* for an empty string. Confirmed via `DESCRIBE`/`SELECT` against the real production dimension file that it currently has zero empty-string rows, only real names or `NULL`. This is why `None`/`NULL` was the right sentinel (already exactly what's expected downstream) rather than an empty string or a separate column, which would have needed an extra translation step at the join.
- **Verified the 47,070 entrant count itself was not the bug** - it matches the original 20 Oct manual batch run's own measured ~55.7% ChecklistBank hit rate for this exact species-ranking method (`WORK_SUMMARY_201026.md`: 106,247 top-N, 59,186 hits). The bug was purely that negative results were never persisted, not that the entrant computation was wrong.
- **Dead end explicitly corrected mid-session**: initially claimed "occurrence counts can drift slightly even without a new GBIF release" to justify expecting non-zero new entrants on the validation run. User challenged this; re-checking the 24 Oct run's own guardrail output showed *exact* equality (`2871617647 -> 2871617647` etc.), not "near-zero" - contradicting the claim. Corrected to the right expectation (zero new entrants, since source data is genuinely static between runs absent a new GBIF release).
- **That correction was then itself refined by real evidence**: the live validation run showed 35 new entrants (4 names, 31 confirmed-empty), not zero. Investigated rather than assumed - downloaded both the pre-run and post-run fact files and directly compared `compute_top_n_specieskeys` output: both top-N sets have exactly 106,247 members, with 41 swapped in/out at the boundary. Checked the swapped specieskeys' actual occurrence totals in both files - identical (e.g. `303` in both) for every one. Root cause: `compute_top_n_specieskeys`'s `ORDER BY total_occ DESC` has no secondary tiebreaker column, so which of several species tied at the exact 99%-coverage cutoff land just inside vs. outside the top-N is arbitrary per execution (DuckDB window-function row order, itself downstream of BigQuery's own non-guaranteed extraction row order). Confirmed with the user this level of non-determinism is acceptable - not worth adding a deterministic tiebreaker for.
- **Real BigQuery cost of the validation run**: confirmed before running that there's no way to test Step 4 in isolation via the live Cloud Run Job (`run()` is one monolithic function) - validating the common-names fix necessarily re-pays the full ~$2.97 scan+derive cost, even though the EXPORT DATA/concatenation mechanism itself was already proven on 24 Oct and didn't need re-validating.

## Decisions and trade-offs

- **Decision:** Represent "checked, ChecklistBank has nothing" as `common_name=None` in the cache - a present dict key/row, distinct from absent (never checked). **Why:** `None` is already exactly the value every downstream consumer (dimension file, frontend) expects for "no name" - confirmed by tracing the real code, not assumed - so zero translation logic is needed anywhere else in the pipeline. **Trade-off:** none within scope; the alternative (a separate schema column) would have added complexity for no benefit.
- **Decision:** Backfill the existing production cache locally (no new ChecklistBank calls), trusting the 24 Oct run's already-completed, exception-free result, rather than letting the next live run rediscover the gap through one more real 47k-call fetch. **Why:** avoids an unnecessary ~8-9 minute, high-volume repeat of calls whose answer we already have strong evidence for (no exception logged; each per-taxon fetch raises on any HTTP error, so a clean run means every lookup genuinely returned empty). **Trade-off:** relies on an inference (no exception = no silent failure) rather than a re-verified fact - accepted given the trace of the code confirmed there's no other path that could have silently dropped a successful result.
- **Decision:** Defer hardening `fetch_common_names_for_taxa`'s lack of per-task fault isolation (one HTTP failure among thousands currently discards the whole batch). **Why (user's reasoning):** the existing cache is kept unchanged on such a failure and already provides significant, durable coverage - a transient failure costs one skipped run's worth of mostly-negative results, not correctness. **Trade-off:** this exact class of silent-loss bug could recur at smaller scale in a future month if a single real call fails; accepted as low-probability and easy to revisit if it ever actually happens.
- **Decision:** Accept per-run churn from top-N boundary ties (a handful of specieskeys swapping in/out each month with no real data change) rather than adding a deterministic tiebreaker to `compute_top_n_specieskeys`'s `ORDER BY`. **Why:** confirmed via direct comparison that the swapped species have identical occurrence totals in both snapshots - this is inherent to a hard-cutoff ranking rule with ties, not a bug, and the cost (a few dozen extra lookups/month) is negligible. **Trade-off:** none practically significant; noted in ADR-020 so a future reader doesn't mistake this for a regression.
