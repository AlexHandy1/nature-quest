## What was explored / learnt

- **`GET /v1/species/{key}/vernacularNames` hard-requires an integer key.** Tested live: `GET /v1/species/4HPXM/vernacularNames` → `HTTP 400 "For input string: \"4HPXM\""` — a raw Java `NumberFormatException`, not a checklist-mismatch error. Confirms the COL XR string id can never be passed to this endpoint directly.
- **The specific legacy numeric key recorded in `WORK_SUMMARY_091026.md` ("2482484 = Pica pica") is stale/wrong today.** Live lookup: `GET /v1/species/2482484` → `Corvus woodfordi`, not Pica pica. Live `species/match` for "Pica pica" today returns `speciesKey: 5229490` — tested with the default checklist, with `checklistKey` explicitly set to the legacy backbone UUID (`d7dddbf4-2cf0-4f39-9b2a-bb099caae36c`), and with it set to the COL XR UUID (`7ddf754f-d193-4cc9-b351-99906754a03b`) — all three return the same numeric `5229490`, never the COL XR string id. **Conclusion: `species/match` always normalizes to a numeric backbone key regardless of checklist, and GBIF's backbone numeric keys are not permanently stable across backbone rebuilds** — a materially different (and more serious) finding than "we need a mapping file," since it means a numeric key captured once can't be trusted to still be valid later. This caught an overclaim mid-session: an early version of this finding wrongly implied COL XR ids themselves have no static mapping at all — corrected after the user pushed back; the actual proven fact is narrower (legacy numeric keys drift across rebuilds), not that COL XR ids are inherently unmappable.
- **The real breakthrough: ChecklistBank's own API accepts COL XR ids directly, no numeric-key translation needed at all.** `data-blog.gbif.org`'s COL XR migration post (fetched and read) doesn't cover vernacular names at all and only describes legacy→COL XR translation (`scientificNameID=gbif:<legacy key>` + COL XR `checklistKey`) — the wrong direction for this job. Instead, found and verified live:
  - `GET https://api.checklistbank.org/dataset/{COL-XR-release-key}/taxon/{COL-XR-id}` → full taxon record (verified `4HPXM` → `Pica pica`).
  - `GET https://api.checklistbank.org/dataset/{COL-XR-release-key}/taxon/{COL-XR-id}/vernacular` → vernacular names directly by COL XR id. Verified live: `4HPXM` → `Black-billed Magpie`, `Common Magpie`, `Eurasian Magpie`, `European Magpie`, `Magpie` (all `language: eng`).
  - **This doesn't need to be per-species at all.** `GET /dataset/{key}/vernacular?language=eng&limit=1000&offset=N` paginates the *entire* release's English vernacular table — confirmed **401,045 total English rows** for one COL XR release, i.e. **~401 paginated calls** to pull the whole thing, vs. the ~918K individual GBIF `vernacularNames` calls (4–14hr) scoped in the 8/9 Oct sessions. Each row carries `taxonID` (the COL XR id to join on) directly.
- **GBIF's own COL XR version is pinned, not "latest," and the pin is independently discoverable.** Found via GBIF's dataset registry record for the "Catalogue of Life" backbone-of-record dataset (`GET https://api.gbif.org/v1/dataset/7ddf754f-d193-4cc9-b351-99906754a03b`): its `identifiers` list carries `{"type": "CLB_DATASET_KEY", "identifier": "315557", "created": "2026-10-05..."}`. Resolved `315557` → ChecklistBank dataset `COL26.6 XR`, issued 2026-06-19 — **not** `COL26.9 XR` (key `316441`, the release used for the earlier probes in this session). Verified `4HPXM` resolves identically (Pica pica) in both `315557` and `316441` — the one data point so far suggesting COL XR ids are stable across releases, unlike legacy numeric keys. BigQuery's `bigquery-public-data.gbif.occurrences` table (`bq show`) has `lastModifiedTime` 2026-10-02 — consistent with, but not proven identical to, the `315557` pin.
- **ChecklistBank dataset discovery path, for reuse:** `GET https://api.checklistbank.org/dataset?q=Extended%20Release&limit=15` lists COL XR releases by `alias` (e.g. `COL26.6 XR`) and `issued` date — releases run roughly monthly (`COL25.10 XR` through `COL26.9 XR` seen in the listing). No stable "latest" alias/pointer endpoint found (`GET /dataset/col` → 404) — the GBIF registry's `CLB_DATASET_KEY` identifier is the correct way to find which release GBIF itself is actually using, not browsing ChecklistBank's own release list directly.
- **Dead end:** the `/dataset/{key}/export?format=COLDP` bulk-archive endpoint returns a cached 1.25GB JSON tree export regardless of the `format` query param passed (tested `ColDP` and `COLDP`, both ignored, both served from `x-cache: hit_cached`) — not a usable path to a ColDP package with a separate `VernacularName.tsv`. The dataset-scoped `/vernacular` search endpoint (used above) is the right bulk-access mechanism instead, not the `/export` endpoint.
- **Current `species_dimension.parquet` schema confirmed** (`prototypes/scratch/species_dimension.parquet`, all `VARCHAR`): `specieskey, species, kingdom, phylum, class, order, family, genus` — no `common_name` column yet. Sample row: `specieskey='QXMNH', species='Nitzschia lacuum', kingdom='Chromista', phylum='Ochrophyta', class='Bacillariophyceae', order='Bacillariales', family='Bacillariaceae', genus='Nitzschia'`.
- **Narration has exactly one path to Wikipedia data, and it isn't its own.** Re-checked against the real code (`app/backend/services/species_enrichment.py`, `app/backend/services/wikipedia_client.py`, `app/backend/models/narration.py`, `app/backend/routers/narration.py`) after an initial claim ("narration impact: none") was challenged and found to be imprecise. `species_enrichment.py`'s `_enrich_one()` is the **only** call site for `wikipedia_client.fetch_species_summary()` in the whole system — it runs once per selected species during `/api/query`. `routers/narration.py` never calls Wikipedia; `NarrateRequest.species[].extract` (in `models/narration.py`) is just passed through from whatever `/api/query` already returned, via the frontend. So narration has zero independent fallback — any cache-layer bug that dropped or truncated `extract` while leaving `image_url` intact would silently degrade narration's grounding quality with no separate error signal.

## Decisions and trade-offs

- **Decision: common names will be sourced via a bulk paginated crawl of ChecklistBank's `/dataset/{key}/vernacular?language=eng` endpoint, keyed natively by COL XR id — not via GBIF's `vernacularNames` endpoint, and not via any legacy-numeric-key mapping file.** **Why:** confirmed live that this is both correct (no GBIF numeric key ever involved) and dramatically cheaper (~401 calls for the whole release vs. ~918K individual calls / 4–14hr previously scoped). **Trade-off:** depends on ChecklistBank's dataset-scoped `/vernacular` endpoint remaining available and paginated the same way; not yet load-tested at full 401-page scale (only single-page `limit=1000` calls tested so far).
- **Decision: `species_dimension` (taxonomy + new `common_name` column) becomes a persistent, incrementally-maintained cache, not a table rebuilt fresh from BigQuery every month — reversing an assumption made earlier in this same session.** **Why:** the full-rebuild-every-month logic from the 8 Oct session was specifically justified for the **fact table** (occurrence counts genuinely change monthly, and BigQuery `WHERE` filters don't reduce scan cost anyway, so full-rescan is the cheap option there) — that reasoning doesn't transfer to the dimension table, whose taxonomy/common-name content is a slowly-changing dimension, not a fact. Caught by the user's direct pushback mid-session. **Trade-off:** monthly pipeline now needs explicit diff logic (new `specieskey`s in that month's fresh fact table vs. the existing dimension cache) rather than a simple full-regenerate-and-overwrite step; also needs a defined (if deferred) policy for handling a `specieskey` that gets deprecated/merged/reclassified between COL XR releases, since the cache no longer self-heals via full rebuild.
- **Decision: COL XR version for `species_dimension`'s common-name data will be pinned manually for the first release, with automated drift monitoring deferred.** **Why:** GBIF's own backbone is itself pinned (not auto-tracking latest COL XR — confirmed via the `CLB_DATASET_KEY` registry identifier), so manual pinning on our side matches how GBIF itself operates; building drift detection now would be premature before the pipeline exists at all. **Trade-off, corrected mid-session from an overstated first draft:** a species added under a newer COL XR version than our pin, or an existing species whose COL XR id shifts on a GBIF re-pin, would ship with full taxonomy and real occurrence counts (both sourced directly from BigQuery's own raw columns, unaffected by COL XR version) but a **missing `common_name`** until the pin is manually bumped — not missing occurrence data, which was the user's original (slightly overstated) framing of the trade-off.
- **Decision: Wikipedia image/extract enrichment is explicitly out of scope for this round of work — left exactly as the current live per-query call, not batched or cached.** **Why:** unlike common names, Wikipedia has no bulk-crawl shortcut (a full preload would mean ~918K individual calls, mostly wasted on long-tail species that are never selected for a walk), and — per the finding above — it's the sole data source for both the results-panel image and narration's grounding text, so a cache bug here carries real, hard-to-detect quality risk for a feature not part of this change's goal (removing the GBIF dependency). **Trade-off:** Wikipedia remains the one external data dependency in the live request path after this build (alongside the LLM calls for taxon resolution, narration generation, and TTS) — accepted explicitly, to be revisited separately if it ever becomes a priority.
