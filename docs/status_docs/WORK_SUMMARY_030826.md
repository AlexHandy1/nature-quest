## What was explored / learnt

- **jsdom + Node 26 localStorage clash**: `window.localStorage` was `undefined` in Vitest tests (Node 26 ships an experimental built-in `localStorage`/`sessionStorage` that appears to suppress jsdom's own implementation). Fixed with a small in-memory `Storage` polyfill in `src/tests/setup.ts`, applied only if `window.localStorage` is missing.
- **`tsc --noEmit` gave false confidence**: run bare (no `-p`), it picked up the root `tsconfig.json`, which has `"files": []` and no `include` — so it silently checked nothing. The real check is `tsc -b` (what `npm run build` actually runs), which uses project references properly and caught a real error later (see Blockers).
- **PostHog Project API Key / "Project token" is a write-only, public-safe key by design** — distinct from PostHog's Personal API Key (a real secret, unused here). Confirmed via the user's own PostHog dashboard label ("Project token"). Still, since it's fully public (embedded in shipped JS), it's exposed to event-injection/spam abuse from bots posting directly to PostHog's ingestion endpoint — Cloud Armor gives zero protection against this (bots bypass our backend entirely). Accepted as a proportionate, industry-standard risk at this traffic stage; not mitigated further this session.
- **GCP Cloud Armor + external HTTPS Load Balancer real cost**: ~$18.25/mo (forwarding rule) + $5/mo (WAF policy) + $1/mo (rate-limit rule) ≈ $24-25/month fixed, before any traffic. Deferred (see Decisions).
- **`/healthz` is a reserved path on Cloud Run** — Google's front-end intercepts it before it reaches any container (confirmed via `x-cloud-trace-context` header present on `/` and a bogus path, absent on `/healthz`; same behavior on both the old-style and new-style Cloud Run URL formats; cache-busting query strings made no difference). Found via web search after ruling out caching/DNS explanations: [Google Developer forums thread](https://discuss.google.dev/t/cloud-run-run-app-urls-return-google-frontend-404-before-reaching-containers/379303).
- **Bare `pytest` vs `python -m pytest` in CI**: the GitHub Actions `unit-tests-backend` job failed with `ModuleNotFoundError: No module named 'main'` even though it worked locally every time — because `python -m pytest` explicitly puts the current directory on `sys.path`, while the bare `pytest` console-script does not. Fixed by changing the workflow step to `python -m pytest`.
- **`gh` CLI was version 1.0.0** (from 2020) locally, predating `gh variable set` entirely (added in later versions). Upgraded to 2.97.0 via `brew upgrade gh`.
- **Dead end — mid-session `pip install ruff mypy` without activating the venv in the same command**: each Bash tool call starts a fresh shell (working directory persists, shell state/venv activation does not). Ran `pip install ruff mypy -q && ruff check .` without `source venv/bin/activate` first, which silently hit some other ambient Python environment (garbage/unrelated package versions — old fastapi/pydantic/pytest-plugins bundle, source unknown). Corrupted `app/backend/requirements.txt` via a subsequent `pip freeze` from that wrong environment. Caught immediately by checking `pip list`/`which python`, reverted the file, redid the install correctly (`source venv/bin/activate && pip install ...` in one command). No lasting damage, but a reminder to always chain venv activation within the same Bash call.

## Decisions and trade-offs

- **Decision:** Descope server-side PostHog capture (REQ-013/016) for now; client-side only. **Why:** requires a `distinct_id` passthrough from the frontend to correctly attribute the server event to the same anonymous visitor (PostHog server SDKs have no auto-persisted ID the way the browser SDK does) — judged excessive complexity for getting the basics running. Backend still unconditionally logs every submission to Cloud Logging (REQ-012), so no interest-signal data is lost either way, only PostHog's own event count/funnel accuracy for the subset of visitors whose client-side call doesn't fire. **Trade-off:** logged in `docs/FEATURE_IDEAS_BACKLOG.md` and `ADR-007`'s implementation note (with the `distinct_id` design to use when revisited) plus the spec's `[DEFERRED]` markers on REQ-013/016/AC-005/AC-006.
- **Decision:** Defer Cloud Armor + load balancer (REQ-017); use Cloud Run `max_instance_count=2` as an interim guardrail instead. **Why:** ~$24-25/month fixed cost, disproportionate to current "coming soon" traffic (ADR-007's own "proportionate to actual risk" principle) — and `max-instances` addresses the specific risk that mattered most to the user (cost creep from runaway autoscaling) at zero extra cost. **Trade-off:** does not address spam/junk-data pollution risk (no per-IP awareness) — accepted, logged in `ADR-007` and `docs/FEATURE_IDEAS_BACKLOG.md`.
- **Decision:** Provision an empty Secret Manager scaffold now (REQ-007) rather than skip it entirely. **Why:** user's explicit call, wanting the pattern ready before Phase 2 needs it, despite no real secret existing yet.
- **Decision:** Human-reviewed PR merge into `main` remains the trigger for deploy (no auto-merge). **Why:** established in an earlier session as the deliberate current checkpoint on the path toward more autonomous CI/CD; logged in `docs/FEATURE_IDEAS_BACKLOG.md` as a future item requiring automated PR-review checks before it could be removed.
- **Decision:** WIF trust is enforced twice — the workflow's own `if: push to main` gate, **and** a GCP-side `attribute_condition` on the Workload Identity Pool Provider restricting to `repository == "AlexHandy1/nature-quest" && ref == "refs/heads/main"`. **Why:** defense-in-depth per REQ-010 — even a maliciously modified workflow file (e.g. via a fork PR) couldn't obtain deploy credentials, because GCP itself independently rejects tokens outside that exact repo/ref, not just the workflow YAML's own logic.
- **Decision:** `WIF_PROVIDER`/`DEPLOY_SERVICE_ACCOUNT` stored as plain GitHub repo *variables*, not *secrets*. **Why:** neither is a credential — WIF has no long-lived secret at all; both are just identifying strings, safe even if fully public (same reasoning as the PostHog token and Cloud Armor: the real boundary is cryptographic/IAM verification, not secrecy of a name).
- **Decision:** `build` job runs on every PR (docker build validation, no push, no credentials), not just at deploy time. **Why:** catches build-breaking changes during review rather than after merge (this is exactly what caught the `tsc -b`/vitest-globals bug earlier in the session) — small CI-time cost, no security cost since nothing is pushed or deployed. User confirmed keeping this after discussing the trade-off.
- **Decision:** GitHub repo renamed to `nature-quest` (was `nature-walker` locally in git remote) — local `origin` URL corrected to `git@github.com:AlexHandy1/nature-quest.git`.
- **Learning (agent behavior, not project-technical):** user asked for short git commit messages — one-line summary plus at most 1-2 short context lines, no restating design discussions/rationale already covered in conversation (e.g. don't re-explain what a "Project API Key" is inside a commit body). Apply this to all future commits in this project.
