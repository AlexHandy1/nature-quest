Design and build session for the monthly automated GBIF data-update pipeline — the Phase 4 item explicitly deferred in `PLANNING_DUCKDB_MIGRATION_201026.md`, moving the current manual table-creation process (8–9 Oct prototype scripts) to an automated Cloud Run Job.

## What was built

All new code lives under `app/backend/jobs/`, prefixed `monthly_gbif_update_*` per an explicit naming convention request (to distinguish from future jobs), with matching tests under `app/backend/tests/`. Built and committed in this order, each as its own commit on branch `monthly_gbif_data_update`:

1. **`monthly_gbif_update_guardrails.py`** — `evaluate(current, previous) -> GuardrailOutcome` (pass/warn/block + reasons). Hard-blocks: missing schema columns, any decrease in total occurrence count / distinct cell count / distinct species count vs. the current production baseline. Soft-warns: near-zero change (<0.1%, possible stale GBIF snapshot) or >20% swing on any metric. `compute_stats_from_parquet(con, fact_path, dimension_path)` derives `RunStats` via DuckDB aggregate/`DESCRIBE` queries against Parquet (local or `gs://`) — added/evolved later in the session once the memory-scaling problem below was found. 11+ tests.
2. **`monthly_gbif_update_common_names_cache.py`** — `new_entrants`, `merge_into_cache` (existing entries never overwritten — once a name is cached, kept regardless of later top-N status), `bootstrap_cache_from_production` (DuckDB query, column-projected + filtered, not a full table read), `compute_top_n_specieskeys` (DuckDB coverage-cutoff query against a fact Parquet file, not Python rows).
3. **`monthly_gbif_update_bigquery_extract.py`** — `extract_fact_and_dimension(client, fact_destination_uri, dimension_destination_uri)`. Session-scoped BigQuery query (one raw-table scan into a TEMP TABLE, avoiding a double-scan), then two derived queries each writing to their own destination table. `extract_table()` writes both results **directly to GCS, server-side** — row data for either table never passes through Python. Stats (schema + counts) come back via tiny aggregate/metadata queries. `MAXIMUM_BYTES_BILLED` capped at 1TB (the free-tier ceiling) as a cost circuit-breaker.
4. **`monthly_gbif_update_common_names_fetch.py`** — ported `pick_best_name`/`build_common_name_map`/junk-filtering from `prototypes/scripts/species_common_names_batch.py`, plus `fetch_common_names_for_taxa` (concurrent, injected `fetch_fn`). `CHECKLISTBANK_COL_XR_DATASET_KEY = 315557` pinned as an explicit constant (not resolved live — see Decisions). Verified against GBIF's registry this session: resolves to ChecklistBank dataset 315557, alias "COL26.6 XR", version "2026-06-19 XR".
5. **`monthly_gbif_update_gcs_release.py`** — `write_parquet`/`read_parquet_rows` (DuckDB, real local I/O), `release_blob_path` (dated `releases/<date>/` prefix), `promote_release` (GCS-to-GCS copy, dated → fixed root paths the app already reads), `download_blob_to_file`, `open_gcs_write_connection` (DuckDB `httpfs` with a write-capable GCS secret — new credential, not yet provisioned in Terraform), `join_common_names` (DuckDB join of the cache onto the raw dimension file, written straight back to GCS, no Python row materialization).
6. **`monthly_gbif_update_logging.py`** — `log_monthly_gbif_update_outcome` (one structured JSON log line per run: verdict + full block/warn reasons). `JsonLogFormatter`/`configure_json_logging` **duplicated** from `main.py` rather than extracted into shared code (see Decisions).
7. **`monthly_gbif_update_run.py`** — orchestration script, the Cloud Run Job's entrypoint. Wires 1–6 together: read production baseline stats → BigQuery extract (always writes the dated release files) → cache bootstrap/diff/fetch/merge (non-blocking) → common-names join → guardrail evaluation → log outcome → promote only if not blocked. Two integration tests (clean-pass, blocked-run) using patched collaborators.

Also: `requirements-job.txt` (the pipeline's own deps: `google-cloud-bigquery`, `google-cloud-storage`, `pandas`, `pyarrow`, `requests` — kept separate from the live service's `requirements.txt` to avoid bloating its cold-start-sensitive image); `requirements-dev.txt` updated to pull in both plus `pandas-stubs`/`types-requests` for CI's mypy step.

## What was explored / learnt

- **Real local measurement, using the 9 Oct session's still-present cached files** (`prototypes/scratch/fact_sorted_by_cell.parquet`, 744MB, 221M rows): running the actual `compute_stats_from_parquet` fact aggregate and `compute_top_n_specieskeys` queries against this real file took **2.25s and 2.08s respectively**, peak memory **~697MB** (same order as the file size, not a multiple of it) — confirms the DuckDB-pushdown redesign (see Decisions) genuinely avoids the Python-memory blowup a `list[dict]`-based approach would have caused (likely tens of GB for 221M rows).
- **The same two queries against the real production bucket (`gs://nature-quest-504414-index-data/fact_sorted_by_cell.parquet`) were dramatically slower** — still running after 120s+ (DuckDB's own progress bar estimated ~8 minutes for just the first query) before the task was stopped by the user mid-run. Confirmed this is a fair comparison, not an artifact: neither query has a `WHERE` filter, so **no row-group pruning is possible in either case** — both the local and `gs://` runs do a genuine full-column scan of all 212 row groups; the only variable is network (httpfs range requests to GCS) vs. local disk (likely page-cache-warm). This is categorically different from the app's own validated read path (sub-second), which only works because it prunes to a handful of row groups via a `cell IN (...)` filter — these guardrail/top-N queries have no such filter and can't benefit from pruning at all.
- Verified `google-cloud-bigquery-storage` is genuinely unused in the current code (no `to_dataframe()`/`to_arrow()` calls anywhere) — a real dependency that fell out of the redesign, not yet removed from `requirements-job.txt` (interrupted before this edit landed).
- Confirmed (via `grep`, not assumption) that `pandas`, `google-cloud-bigquery`, `google-cloud-storage`, and `requests` remain genuine new dependencies the live FastAPI service doesn't have — the two-Docker-image-target decision (separate job image, avoiding bloating the cold-start-sensitive live service image) still stands even though DuckDB itself is already shared between the two.
- Reconstructed `house-management-agent`'s existing Cloud Run Service+Job pattern (`app/backend/jobs/`, one shared image, `gcloud run jobs update --image=...` in CI) as the structural precedent — adopted the folder convention, but diverged on image-sharing specifically because of the dependency-weight difference (house-management's job only needed deps the service already had; this one doesn't).

## Decisions and trade-offs

- **Decision: single Cloud Run Job (not Cloud Workflows), triggered by Cloud Scheduler on the 7th of each month.** **Why:** the whole run is minutes long with no need for independent per-step retry/fan-out; reuses the `index_refresh` write-only service account already provisioned in `infra/gcs_index_data.tf` anticipating this job. **Trade-off:** GBIF's actual snapshot publish day is unconfirmed (couldn't access their occurrence-snapshots page), so the 7th-of-month trigger is a reasoned assumption, not a verified fact — mitigated by the near-zero-delta soft-warning check.
- **Decision: write every run to a dated `releases/<date>/` GCS prefix, promote (copy) to the fixed root paths only on a non-blocked verdict; keep all dated releases indefinitely (no lifecycle rule) given the trivial storage cost (~$0.18/month for 12 months).** **Why:** gives real rollback capability (documented as a manual runbook step, not scripted) and makes the job idempotent on re-run. **Trade-off:** the promote step is two separate GCS copies (fact then dimension), not atomic — accepted as a narrow, low-probability race window given request latency and monthly run frequency.
- **Decision: hard-block on any decrease in total occurrence count / distinct cell count / distinct species count; soft-warn (promote anyway) on near-zero or >20%-swing deltas.** **Why:** cost of an extra month of staleness is low; false-positive blocks just cost a manual re-run, false negatives risk silently shipping corrupted data. Distinct cell count specifically must be monotonic non-decreasing (not fixed) — it's the set of *populated* cells, which can only grow as more surveys happen.
- **Decision: common-names fetch failures (ChecklistBank, or the dataset-key lookup) are entirely non-blocking.** **Why:** the incremental cache design means any given run only needs to fetch a small delta of newly-top-N species, not the full ~100K; the existing cache already provides durable coverage independent of any single run's success.
- **Decision: pin `CHECKLISTBANK_COL_XR_DATASET_KEY` as an explicit constant (315557), not resolved live via GBIF's registry on every run.** **Why:** our fact/dimension `specieskey`s come from whatever COL XR release GBIF had pinned *at BigQuery's snapshot time*; resolving live at pipeline-run time could silently drift to a newer release than the data actually uses, with species whose ids only exist under the newer release failing to resolve (graceful degradation — missing name, not wrong data, and self-healing on the next successful fetch after a deliberate pin update). No resolver function was built into the job — re-checking the pin is a plain two-call API lookup, not maintained code (rule-of-three: a function with no real caller is dead weight).
- **Decision: fact and (raw) dimension tables are extracted directly from BigQuery to GCS via `extract_table()`, never materialized as Python `list[dict]` — and the production-baseline/top-N stats come from DuckDB aggregate queries against Parquet, not a persisted `production_stats.json` manifest.** **Why:** the original `list[dict]`-based design (built first, then caught) would have required holding ~221M Python dict objects in memory every run — a severe, recurring cost, not a one-off. A manifest file was considered and rejected as unnecessary: once DuckDB aggregate-with-pushdown was adopted for stats, querying the real production files directly is just as cheap as reading a manifest, with no second source of truth to drift out of sync. **Trade-off, now a known open risk (see Next steps):** these guardrail/top-N aggregate queries have no filter predicate, so unlike the app's own pruned reads they cannot skip row groups — confirmed this session to be dramatically slower over `httpfs` than local disk (DuckDB estimated ~8 minutes for one query against the real bucket, vs. 2.25s locally for the same query).
- **Decision: the common-names dimension join also happens entirely in DuckDB (`join_common_names`), reading the raw dimension file and writing the final joined file straight to GCS — needs a new write-capable GCS secret (`open_gcs_write_connection`), not yet provisioned in Terraform.** **Why:** avoids materializing the dimension table in Python the same way the fact-table fix does; rejected an earlier "download 40MB locally and join" alternative once it was established that on-disk Parquet size is not a reliable proxy for in-memory Python cost (the actual concern), and that using one consistent pattern for both tables is simpler than two.
- **Decision: separate Docker image/build target for the pipeline job, not shared with the live service's image** (unlike `house-management-agent`'s shared-image pattern). **Why:** the job genuinely needs `pandas`, `google-cloud-bigquery`, `google-cloud-storage`, `requests` — none of which the live FastAPI service needs — and this project already spent a full session (22 Oct) fighting Cloud Run cold-start time, which is dominated by image pull size. Confirmed by `grep`, not assumption, that these are real added dependencies regardless of how lightly DuckDB-based code uses them.
- **Decision: `upload_release_file` removed as dead code mid-session** once the BigQuery-direct-extract redesign made it unreachable in the real pipeline (nothing uploads the big tables via Python anymore) — caught and deleted along with its test rather than left as unused code.
- **Decision: `JsonLogFormatter`/log setup duplicated in the job's own module rather than extracted from `main.py` into shared code.** **Why:** rule-of-three — this is only the second place it's needed; an extraction attempt was made and explicitly reverted this session when the user pushed back on touching existing production logging for this case.
