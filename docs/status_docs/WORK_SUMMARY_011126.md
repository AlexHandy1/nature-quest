# Work Summary — 01 November 2026

## What was built
- `venv312/` — a new Python 3.12 virtualenv at the repo root, separate from the existing `venv/` (Python 3.13), created specifically to run `prototypes/scripts/server_semantic_search.py` on an Intel (x86_64) Mac host.
- Got `prototypes/scripts/server_semantic_search.py` running locally outside the Docker container for the first time, confirmed reachable and working at `http://127.0.0.1:5057` via browser.

## What was explored / learnt
- **Port 5057 "already in use" (Docker container):** the container `agent-sandbox-agent-1` (ID `6f1443284080`) had a leftover `venv/bin/python server_semantic_search.py` process (PID 1212) from an earlier run still bound to the port inside the container's netns. No `ps`, `ss`, or `netstat` available in the container — found it by walking `/proc/[0-9]*/cmdline` and cross-checking `/proc/net/tcp` for the hex-encoded port (`5057` = `13C1`). Killed with `docker exec 6f1443284080 bash -c 'kill 1212'` (no `kill` binary directly on `$PATH`, had to invoke via `bash -c`).
- **Browser "connection refused" even with the container server running:** `docker inspect 6f1443284080 --format '{{json .NetworkSettings.Ports}}'` returned `{}` — the container has no ports published to the host at all (`docker port` also empty). `127.0.0.1:5057` on the Mac never reaches the container's internal network namespace regardless of what's running inside it. This is a container run/compose config gap, not something fixable from inside the running container — would need `-p 5057:5057` on container creation or a `ports:` entry in docker-compose and a restart. **Not fixed this session** — pivoted to running the server on the host instead.
- **Running on host hit a platform gap:** `ModuleNotFoundError: No module named 'sentence_transformers'` → `venv/bin/pip install -r prototypes/requirements.txt` triggered a pip dependency-resolution backtrack through ancient `sentence-transformers` releases (0.2.x–0.3.x) because `torch` wasn't installed first (comment in `prototypes/requirements.txt` says to install the CPU wheel separately).
- Tried `pip install torch --index-url https://download.pytorch.org/whl/cpu` — that index only hosts Linux/Windows wheels, not macOS. Plain `pip install torch` on the existing `venv` (Python 3.13, x86_64) found zero compatible versions: **PyTorch dropped macOS/x86_64 (Intel) wheels starting around torch 2.3** — recent releases only ship `arm64`/`universal2` for macOS. Confirmed via `pip debug --verbose` compatible-tags output and by listing PyPI's `torch` file index for `macosx`+`x86_64` wheels, which stops at `2.2.2`.
- `torch==2.2.2` (the last Intel-mac build) only has wheels up to `cp312` — no Python 3.13 (`cp313`) build exists. Confirmed by checking the `/usr/local/bin/python3.12` interpreter was present on the host and creating `venv312` from it.
- After installing `torch==2.2.2` into `venv312`, `import torch` warned `Failed to initialize NumPy: No module named 'numpy'`, then after installing the rest of `prototypes/requirements.txt`, `import torch` failed harder: numpy 2.5.4 (pulled in unpinned) is ABI-incompatible with torch 2.2.2 (compiled against numpy 1.x), and the latest `sentence-transformers`/`transformers` pulled in required `torch>=2.6` (`NameError: name 'nn' is not defined` inside `transformers/distributed/pipeline_parallel.py`, `transformers` itself logging "PyTorch >= 2.6 is required but found 2.2.2").
- Fixed by pinning `numpy<2` and `sentence-transformers==2.7.0` (installed after `requirements.txt`) — this pulled in a compatible older `transformers`. Verified with a clean import of `torch`, `sentence_transformers`, `flask`, `duckdb`, `numpy` (resolved versions: torch 2.2.2, sentence-transformers 2.7.0, numpy 1.26.4).
- Confirmed root-cause context from `docs/status_docs/semantic_search_experiment_report_311026.md`: all prior speed/latency figures for this prototype were measured inside the Docker container ("8-thread CPU container, no GPU") — there was no prior host install to reference; this was the first attempt to run outside the container.
- Also clarified for the user: mean P@5 of 0.60 means, on average, 3 of the top-5 results returned were relevant (0.60 × 5 = 3) — it's an average across queries (individual queries can vary) and doesn't capture rank order (MRR/NDCG@5) or recall against the full relevant set.

## Decisions and trade-offs
- **Decision:** Created a brand-new `venv312` instead of recreating/replacing the existing `venv/`. **Why:** avoids disrupting any other project scripts that assume Python 3.13 in the main `venv`. **Trade-off:** two virtualenvs to maintain going forward; `server_semantic_search.py` and related prototype scripts must now be run with `venv312/bin/python`, not `venv/bin/python`.
- **Decision:** Pinned `torch==2.2.2`, `numpy<2`, and `sentence-transformers==2.7.0` rather than chasing a newer combination. **Why:** this is the last version combination that both supports macOS/x86_64 wheels and avoids the `transformers>=torch 2.6` requirement. **Trade-off:** running an older, unmaintained `sentence-transformers`/`torch` stack on the host; the container's stack (whatever Linux wheel versions it resolved) may differ and drift from this pinned host stack over time.
- **Decision:** Did not fix the Docker container's missing port mapping this session, chose to run on host instead. **Why:** user explicitly chose the host-venv path over fixing the container's `-p 5057:5057` / compose `ports:` config. **Trade-off:** the container route (if picked up again later) still needs that port published before it'll be reachable from a browser on the host.
