# Work Summary — 24 October 2026

Stress-tested, redesigned, and finally ran for real the monthly automated GBIF data-update pipeline built on `monthly_gbif_data_update`/validated on `test_monthly_gbif_update` (23 Oct session). Found and fixed three real bugs along the way (a missing `GROUP BY`, a Cloud Run OOM, a BigQuery `EXPORT DATA` URI requirement) before the pipeline succeeded end-to-end for the first time.

## What was built

All changes landed via three merged PRs on top of the 23 Oct work, each on its own branch:

1. **`test_monthly_gbif_update`** (PR #36) — Fixed a missing `GROUP BY` in `_SCAN_INTO_TEMP_TABLE_SQL`/`_FACT_SELECT_SQL` (`app/backend/jobs/monthly_gbif_update.py`) that was costing ~700GB of extra BigQuery scan per run. Redesigned the fact-table export to shard via `extract_table()` with a wildcard URI (confirmed empirically the single-file export exceeds BigQuery's ~1GB logical limit); added `recombine_sorted_parquet` (full local DuckDB `ORDER BY` sort, since `extract_table()` gives no ordering guarantee), `verify_recombined_row_count` and `verify_sorted_by_cell` (row-group monotonicity, via `parquet_metadata()`) as hard-failure mechanism checks. Moved guardrail stats and `compute_top_n_specieskeys` to run against the local recombined files instead of BigQuery, closing the "guardrails never see the actual promoted bytes" gap. 45 tests.
2. **`gbif_monthly_update_validation`** (PR #37) — Two real Cloud Run executions OOM-killed at 4Gi ("the configured memory limit was reached"). Local measurement against the real shard set (downloaded from the failed run) found `recombine_sorted_parquet`'s full in-memory sort peaks at ~8.4GB RSS / ~13-14GB peak footprint — confirmed via web search this isn't a container-memory-detection bug: Cloud Run's **default filesystem is memory-backed**, so DuckDB spilling to `temp_directory` wouldn't help without also provisioning the Preview "ephemeral disk" feature. Bumped `infra/monthly_gbif_update_job.tf`'s Cloud Run Job to 16Gi/4 vCPU (still OOM'd — see below). Separately: confirmed via BigQuery's own docs that `EXPORT DATA` (unlike `extract_table()`) guarantees `ORDER BY` is preserved globally and distributed sequentially across shards — redesigned the fact/dimension export to use `EXPORT DATA` directly (no intermediate destination table) and changed the local recombine step from a full sort to a plain ordered **concatenation** (`recombine_ordered_shards`), relying on that guarantee. Measured locally against the real 221M-row dataset: peak memory dropped from ~14GB to ~2.75GB. Added a regression test (`test_recombine_ordered_shards_follows_the_given_list_order_not_filename_order`) proving DuckDB's `read_parquet([list])` respects explicit list order, not filename order — the prior test happened to have both coincide. 47 tests.
3. **`write_up_gbif_monthly_update`** (PR #38) — Real retry still failed: `EXPORT DATA`'s `uri` option always requires a wildcard (no single-file exception, unlike `extract_table()`) — confirmed via docs and a free literal-query test against the real bucket. Fixed by giving the dimension export its own shard prefix (`RAW_DIMENSION_SHARD_PREFIX`), downloaded/concatenated the same way as fact (no sortedness check needed — dimension has no `ORDER BY`). Before this retry, built a local end-to-end harness (`fake_gcs.py` + `run_harness.py`, not committed — scratch only) backed by a local directory instead of real GCS, pre-seeded with real cached production-scale data (28 real fact shards, real production fact/dimension baseline), `generate_target_release` mocked to skip BigQuery entirely. Ran the *actual* `run()` function through all 5 steps for free: confirmed it reaches `verdict: "warn"` (as expected — no new GBIF release this month) and correctly promotes; measured whole-pipeline peak memory at ~4GB locally, giving a ~7.8GB Cloud-Run-equivalent estimate once file-bytes-count-as-memory is added back. 48 backend tests total after this change.

## What was explored / learnt

- **Real BigQuery job-history checks (`region-us.INFORMATION_SCHEMA.JOBS_BY_PROJECT`) throughout**, not estimates — caught that this session's repeated real runs pushed the project to 2.52 TiB billed this month (~$9.50 beyond the 1 TiB free tier), at ~$2.97 per full scan+derive cycle (393GB scan + ~12GB fact + ~52GB dimension), not the ~$1.50 figure assumed earlier in the (pre-24 Oct) session.
- **Free/near-zero-cost BigQuery validation technique discovered and used repeatedly**: a literal `SELECT`/`UNNEST` wrapped in `EXPORT DATA` or `bq query` costs essentially nothing (no real table scan) and validates syntax/URI requirements/overwrite behavior for real against the live project — used this to confirm the wildcard requirement, and to directly prove (not just trust docs) that `EXPORT DATA overwrite=true` does **not** delete stale files left over from a prior run under the same wildcard prefix that the new run doesn't rewrite. Decision: don't engineer around this for a once-a-month job — manually clear the dated release prefix before a same-day re-run instead (did this once via `gsutil -m rm -r` on `releases/2026-10-24/`).
- **GCS soft-delete surprised the user**: the index-data bucket has a default 7-day soft-delete policy (`retentionDurationSeconds: 604800`), so deleted objects can still appear in some Console views for up to 7 days even though `gsutil ls`/`gcloud storage ls` (and the pipeline's own `list_blobs_with_prefix`) correctly show them as gone immediately. Confirmed this doesn't affect pipeline correctness either way. No action taken — left to auto-purge.
- **Local memory measurement via `/usr/bin/time -l` (macOS)** was the key tool throughout — "maximum resident set size" and "peak memory footprint" lines gave real numbers at every stage (recombine-only: ~14GB sort vs ~2.75GB concatenate; whole-pipeline harness: ~4GB).
- Dead end avoided: didn't build a code-level delete-before-export cleanup step for the stale-shard risk — user explicitly judged it not worth engineering for a monthly job with manual oversight.

## Decisions and trade-offs

- **Decision:** Switch both fact and dimension BigQuery exports from `extract_table()` on an intermediate destination table to `EXPORT DATA` direct-to-GCS. **Why:** `extract_table()` gives no row-order guarantee at all (a BigQuery table has no order at rest); `EXPORT DATA` with `ORDER BY` guarantees global order preserved sequentially across shards (confirmed via docs). **Trade-off:** `EXPORT DATA`'s `uri` option always requires a wildcard (no single-file exception), which the dimension export initially missed and had to be fixed for; also means intermediate BigQuery destination tables no longer exist for inspection.
- **Decision:** Local recombine changed from a full `ORDER BY` sort to a plain ordered concatenation, relying on `EXPORT DATA`'s guarantee, with `verify_sorted_by_cell` kept as a hard-failure safety net. **Why:** the full sort OOM'd Cloud Run even at 16Gi; concatenation measured at ~2.75GB vs ~14GB. **Trade-off:** correctness now depends on an external guarantee (BigQuery's) rather than something fully verified by our own code at write time — mitigated by keeping the row-group monotonicity check, which was confirmed (by testing against genuinely unordered real data) to actually catch a violation rather than rubber-stamp it.
- **Decision:** Raised the Cloud Run Job from 4Gi/2 vCPU to 16Gi/4 vCPU. **Why:** recovering from a real OOM; Cloud Run Jobs pricing makes the cost difference negligible for a monthly run. **Trade-off:** none significant — there's now real headroom after the concatenation redesign, so this could be sized back down later if desired, but no pressure to.
- **Decision:** Don't add a delete-existing-shards-before-export step to the code for the confirmed stale-file risk; handle it manually if it ever recurs. **Why (user's reasoning):** multiple automated runs against the exact same release-date folder is an unlikely operational scenario for a monthly job — engineering around it now is premature. **Trade-off:** a future same-day re-run (e.g. after a mid-month fix) needs a manual `gsutil rm` of the dated prefix first, or risks corrupting the recombine with leftover shards.
- **Decision:** Build a local end-to-end harness (fake GCS over a local directory, real cached production-scale data, only `generate_target_release` mocked) to validate the full pipeline before the costly real retry, rather than just re-running against real BigQuery to find out. **Why:** each real run costs ~$2.97 and ~10+ minutes; the harness was free and caught nothing new (confirming confidence was warranted) while also producing a real measured memory number instead of an estimate. **Trade-off:** the harness isn't committed (scratch-only, cleaned up after use) — if this kind of validation is wanted again, it'd need rebuilding, though it's cheap to recreate from this summary's description.
