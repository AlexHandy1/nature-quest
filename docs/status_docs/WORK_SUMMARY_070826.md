## What was explored / learnt

- **Root cause of the "only one alert ever received" bug**: `condition_threshold` alert policies use incident open/close state semantics, not per-event notification. A log-based `DELTA` counter metric only ever emits a data point when a matching log line occurs — it never emits an explicit "0" for a quiet period. So once the first `query_outcome` log line opened an incident (right after the policy was created on 2026-08-06), the incident never closed (GCP's default missing-data handling holds incidents open, only auto-closing after 7 days of silence). Every subsequent matching log line was "still violating" the same open incident, not a new violation — no new notification. Confirmed via direct Cloud Logging query: 8 `query_outcome` events in the prior 24h, exactly 1 notification, timed to the very first evaluation window after policy creation (matches the 20:57–21:03 UTC burst, not the earlier 20:33 UTC events which predate the policy).
- **`condition_matched_log` is the purpose-built fix** — a `LogMatch`-type condition that notifies per matching log entry directly, with no incident-state model to get stuck open. Confirmed live: GCP requires `alertStrategy.notificationRateLimit` on this condition type and enforces a **hard 300-second minimum** (tested `60s` directly against the API, got `Error 400: the rate limiting period for a log-based alert policy has to be at least 300 seconds`).
- **This 300s floor is a real GCP product limitation, not a config workaround away** — `google_monitoring_alert_policy` (Cloud Monitoring's alerting product) is built around an ops-incident model (uptime, error-rate), not per-event business/product notification. The correct GCP-native shape for true sub-5-minute, uncapped per-event alerting would be a Cloud Logging sink → Pub/Sub topic → a small Cloud Run/Cloud Function subscriber sending its own email — meaningfully more infrastructure than the current ~20-line Terraform block, not worth it at current traffic (~8 events/day).
- Applying a targeted `google_monitoring_alert_policy` change pulled in an unrelated `google_cloud_run_v2_service.app` scaling-block diff (`manual_instance_count`/`min_instance_count` drift, provider-schema noise, not a real config difference — `cloud_run.tf` only sets `max_instance_count`). Deliberately left untouched/out of scope; confirmed via `terraform plan` that no other drift remains after this change.
- **CI/CD did not trigger on merging PR #15 — confirmed as expected behaviour, not a repeat of the 6 August GitHub outage.** `.github/workflows/ci-cd.yml`'s `paths` filters (`app/**`, `.github/workflows/ci-cd.yml`) don't match this PR's diff (`infra/**`, `docs/**`, root `.md` files only) — so GitHub Actions correctly declined to run. Verified via `gh api .../actions/permissions` (Actions enabled, `allowed_actions: all`) and `check-suites` for the merge commit (`total_count: 0`, same diagnostic signal as the real 6 August outage, but this time explained by the path filter, not a platform incident). Not yet fixed/decided — see Next steps.
- Investigated exact GCP alerting pricing while designing the fix: log-based alerting policies are billed **$0.35/month per metric reference, $0 points-returned** (Google's own example: 100 log-based policies = $3.50/month total) — essentially cost-neutral vs. the prior metric-threshold setup (~$0.35–0.40/month). The fix was not a cost trade-off.

## Decisions and trade-offs

- **Decision:** Switched `query_submitted` alert policy from `condition_threshold` (log-based metric) to `condition_matched_log`. **Why:** the threshold approach structurally could not deliver ADR-010's own stated intent ("fires on every single query submission") — see root-cause above. **Trade-off:** GCP's enforced 300s notification-rate-limit floor means multiple `query_outcome` events within the same 5-minute window still only produce one email, not truly one-per-event — a real, confirmed ceiling on this alerting shape, not a config oversight.
- **Decision:** Did not pursue a Pub/Sub + Cloud Run/Function pipeline for true uncapped per-event alerting. **Why:** meaningfully more infrastructure than the current fix for a pre-launch, already-flagged-as-temporary alert (ADR-010) at ~8 events/day — not proportionate right now.
- **Decision:** Flagged (not yet actioned) that Cloud Monitoring's alerting product may be the wrong tool for product/usage-event observability going forward. **Why:** the 300s floor is a symptom of `google_monitoring_alert_policy` being built for ops-incident signals (uptime, error rate), not discrete business events. **How to apply:** worth evaluating a dedicated observability/error-tracking tool (e.g. Sentry) for this class of need before building further bespoke GCP plumbing here — noted in ADR-010's Consequences section for the next session that revisits alerting.
- **Decision:** Left the `google_cloud_run_v2_service.app` scaling-block Terraform drift untouched. **Why:** unrelated to this task, cosmetic (`min_instance_count`/`manual_instance_count` = 0 is equivalent to unset), out of scope for a targeted fix.
- **Decision:** Did not add `infra/**` to `ci-cd.yml`'s path filters as part of this session. **Why:** the current `deploy` job only does `docker build` + `gcloud run deploy` + app smoke test — no Terraform step — so adding the path wouldn't actually make CI apply infra changes, just run redundantly. Deliberately deferred rather than half-fixed; see Next steps.
