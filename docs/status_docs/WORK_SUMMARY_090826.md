## What was explored / learnt

- **Round-robin quota merge mechanism** (ported from `prototypes/scripts/e2e_walk_spike_full_validation.py`'s `select_species_across_groups`): confirmed it generalizes to any number of groups, not just two — `divmod(5, 7)` for the fish case gives quotas `[1,1,1,1,1,0,0]`, with shortfall redistribution handling the (expected, common) case where several of Retiro Park's 7 fish groups are locally empty.
- **GBIF's `occurrence/search` ANDs filters within one request but cannot OR across different rank fields** — confirmed (again, from the 21 July planning doc) that mixed-taxa and multi-order lay-term expansions require one GBIF call per resolved filter, not one call with multiple `orderKey` values — matches the prototype's `fetch_and_rank_group` design (each fish order becomes its own group/call, own quota slot).
- Confirmed the frontend (`QueryForm.tsx`) has zero rendering dependency on `taxonRank`/`taxonValue` — only `species` and `message` are ever displayed — de-risking the router response-shape change substantially.
- Confirmed `services/logging_client.py`'s `log_query_outcome` fields are all optional/additive, so ADR-010's `condition_matched_log` alert (which matches on the `query_outcome` log event name) is unaffected by the response/logging shape changes made this session.

## Decisions and trade-offs

- **Decision:** Fish curated list expanded from 5 groups (67.9%) to 7 groups (80.6%): the 5 existing orders (Perciformes, Cypriniformes, Scorpaeniformes, Gadiformes, Clupeiformes) plus Salmoniformes (order) and Elasmobranchii (class, sharks/rays). **Why:** user explicitly chose the "80/20 rule" threshold after seeing live coverage numbers for all 52 fish-related groups. **Trade-off:** rejected the 90%/12-group option as diminishing returns for 5 more parallel GBIF calls per fish query.
- **Decision:** Fish/reptile lay-term expansion is LLM-taught (system-prompt worked examples), not deterministic code-side expansion. **Why:** user wants to preserve flexibility and see how well the LLM performs on its own before hard-coding a lookup table. **Trade-off:** accepted hallucination risk (wrong/missing/misspelled group names) in exchange for flexibility; live eval runs this session (two independent runs) show Haiku reproducing the exact 7-group fish list and correct mixed-taxa splits reliably so far — no divergence observed yet, but this is not a large sample.
- **Decision:** No curated kingdom/class/order lookup cache reinstated in production taxon resolution (`taxon_resolution.py` stays live-only `species/match`, unchanged from the Slice 2 decision in `WORK_SUMMARY_050826.md`). **Why:** same flexibility reasoning as above — the blocker that originally justified removing the cache (single-filter schema couldn't represent multi-key concepts) is now gone, but the user chose not to reinstate it yet regardless, to keep the system's behavior easy to change. **Trade-off:** every resolved query now does up to 7 live `species/match` round-trips (one per filter) instead of 0 for the curated common cases; not yet parallelized (each is still resolved sequentially by `_resolve_taxon_keys`'s loop) — a real latency cost flagged but not addressed this session.
- **Decision:** `fetch_top_species` gained an optional `polygon` parameter (default `GBIF_POLYGON`, the existing Retiro Park constant) so eval tests can pass an explicit search area. **Why:** the user flagged that production will soon move to a user-drawn-polygon input, and wanted this one seam abstracted now for reproducibility in tests. **Explicitly scoped down by the user**: this is only the one function parameter — no config plumbing, no router/API wiring for user-supplied polygons yet; that's future work.
- **Decision:** logged "full GBIF catalogue + vector DB semantic search" to `docs/FEATURE_IDEAS_BACKLOG.md` rather than pursuing it now. **Why:** user's explicit call as the more complete long-term alternative to hand-curated lay-term lookups, worth revisiting if LLM-taught expansion accuracy/coverage becomes a real problem.
