## What was explored / learnt

- Confirmed the Vite frontend tests (`QueryForm.test.tsx` at the time) fully mock `fetch` via `vi.stubGlobal` — no real network calls, by design.
- `ThreadPoolExecutor.map` preserves input order regardless of thread completion order, because each future is paired 1:1 with its input at submission time, not by completion timing — confirmed with reversed-completion-order unit tests after being asked for stronger evidence than timing tests alone provide.
- GBIF's `species/match` doesn't populate a `class` field for most ray-finned fish orders (confirmed live: `Lepomis gibbosus` returns `order: Perciformes` with no `class` at all) — already documented in `TAXON_GUIDANCE`'s system prompt, but caught out an eval-test verification helper that assumed `class == "Actinopterygii"`.
- PostHog's `posthog_trace_id` is generated **locally**, inside the `posthog-ai` Python package (`uuid.uuid4()`, discarded after the call unless explicitly captured) — not something PostHog's servers hand back for reuse. `distinctId` is the real existing join key (already used for both client PostHog events and server-side `$ai_generation` capture via `posthog_distinct_id`), so no new ID was needed for Cloud-Run-log-to-PostHog correlation.
- Considered three designs for the browser-driven smoke test: (a) a reusable agent-browser-driven project skill (LLM re-reasons each run) — rejected once nearly the entire checklist turned out to be exact, scriptable assertions, including "species match the query" via the `kingdom`/`taxonFilters` fields already in the real API response; (b) Playwright — rejected in favor of (c) a plain Python script wrapping the already-installed `agent-browser` CLI, avoiding a new dependency entirely.
- `agent-browser network request <id> --json` returns `data.responseBody` as a JSON-**encoded string** (needs a second `json.loads`) — verified against a real request before writing the script's parsing code, rather than guessing the schema.
- Discussed real vs. imagined security risk of the new smoke-test script (fully open-source project): concluded it does **not** meaningfully increase secret-exposure risk (`.env` is gitignored/local-only; the script never reads secrets itself, only spawns `uvicorn`, which loads `.env` on its own) — an initial overstatement of this point was corrected after pushback. Confirmed the script never accepts `ConsentBanner`, so consent stays `false` throughout a run — PostHog test-data pollution is already avoided by that design property, not by anything the script itself enforces. One real, accepted cost left as-is: `--url` runs against the live deployment share the real `DAILY_LLM_CALL_CAP = 200` budget and per-IP rate limit with real users.

## Decisions and trade-offs

- **Decision:** Cap taxon filters processed per query at 10, truncating overflow into `unresolvedGroups`. **Why:** user's explicit call — partial success over all-or-nothing failure.
- **Decision:** Cap concurrent GBIF requests at 3 for both `fetch_top_species` and `_resolve_taxon_keys`. **Why:** uncapped concurrency triggered real 429s; user explicitly deferred a 429-backoff-retry approach ("concerned about introducing an additional conflicting and confusing retry and response loop") in favor of just capping workers. **Trade-off:** caps the latency win from parallelization; applied to `species/match` too even though only `occurrence/search` had proven 429s, on the same-host/rate-limit reasoning.
- **Decision:** Clustering AND ordering both happen inside `/api/query`; no new `/api/waypoints` route this slice. **Why:** re-examined under `/grill-me` — clustering/ordering are both free/deterministic, so splitting before them doesn't protect the user's stated reason for wanting two calls (early feedback on invalid queries), which `/api/query`'s existing 4 outcomes already guarantee. A future enrichment route (common name, Wikipedia, narrative) is the real place for a second call. **Trade-off:** `species_key` was added now specifically to avoid a schema migration when that route is built.
- **Decision:** Center point for route ordering derived dynamically from `polygon_centroid(GBIF_POLYGON)` rather than a second hardcoded constant. **Why:** user's suggestion — cheap now, sets up cleanly for future user-drawn-polygon support. **Trade-off:** the computed centroid (40.4137, -3.6826) differs ~150-180m from the prototype's hand-picked constant (40.4153, -3.6844); flagged and accepted.
- **Decision:** New pipeline-stage logs are separate log lines, not fields merged onto the existing `query_outcome` line. **Why:** a mid-pipeline failure should still leave everything-up-to-that-point visible in Cloud Run logs. **Trade-off:** up to 5 log lines per request instead of 1.
- **Decision:** `distinctId` (not a new per-request UUID) is the shared correlation field across all new logs. **Why:** matches how PostHog's Activity dashboard already joins events; PostHog doesn't hand back a reusable server-generated trace ID anyway. **Trade-off:** doesn't disambiguate two rapid back-to-back queries from the same user in Cloud Run logs — accepted as a narrow edge case.
- **Decision:** Clustering diagnostics are logged but stripped from the public `/api/query` response. **Why:** matches this session's payload-size discipline established earlier (don't ship server-internal debug detail to the client).
- **Decision:** Species list order in the API response is nearest-neighbour route order, not observation-count order. **Why:** deliberate and tested — the map needs a walkable order, not a popularity ranking. **Trade-off:** confirmed with the user after they flagged confusion seeing it live; explicitly decided **not** to add UX-clarifying copy yet.
- **Decision:** `QueryForm.tsx` deleted outright rather than kept dormant. **Why:** its logic is genuinely absorbed into `QueryPanel`+`MapView`, not simply unused — different from `InterestForm`'s situation.
- **Decision:** `QueryPanel` is always resubmittable after any outcome, not just after success. **Why:** user's explicit choice — simpler, more consistent than the old one-shot/refresh-required design.
- **Decision:** Added `ResultsPanel` after a manual visual check found markers alone unverifiable. **Trade-off:** partially reverses the earlier "fully replaced by markers, no text list" design decision from the `/grill-me` round — that decision didn't hold up once actually seen live.
- **Decision:** Mobile layout stacks panels top/bottom below 700px instead of the desktop opposite-corner layout. **Why:** manual mobile check found both panels overlapping/blocking the map. **Trade-off:** explicitly scoped as a "quick, functional fix," not a full mobile design pass.
- **Decision:** Legacy `/api/interest` code fully deleted, not left dormant. **Why:** executes the CON-001 cleanup deferred since 6 August. **Trade-off:** CI/CD smoke test loses its only real write-path check (now only `GET /health`) — noted explicitly, not silently dropped.
- **Decision:** Smoke test built as a deterministic Python script wrapping `agent-browser`, not an LLM-driven skill or a new Playwright dependency. **Why:** the checklist turned out to be fully scriptable once examined closely. **Trade-off:** `taxonFilters`-based species-match verification checks what the system *believes* it resolved, not independently-verified ground truth (unlike the eval suite's live `species/match` cross-checks) — accepted as right-sized for a fast smoke test.
- **Decision:** `tests/e2e_web_smoke_test.py` lives in a new top-level `tests/` directory. **Why:** it's a full-stack script, doesn't belong to either `app/` subtree.
- **Decision:** `--url` live-mode runs get no extra confirmation prompt despite sharing production's real daily LLM budget/rate limit. **Why:** user's explicit call — already an explicit opt-in flag.

### Decisions and trade-offs

- **Decision:** Geolocation is client-side-only — used solely to `setView`/recenter the map, never sent to the backend, never logged, and gated behind explicit in-app UI (a "Use my location" button with copy) rather than firing the native browser permission prompt automatically. **Why:** user wants it clearly framed as separate from the existing PostHog analytics consent pathway (`ConsentBanner`), and an unexplained native permission popup on load was judged intrusive. **Trade-off:** none significant — geolocation failure/denial just falls back to manual pan/zoom, never blocks the draw flow.
- **Decision:** No auto-drawn starting shape from geolocation — it only recenters the map; the user always draws their own polygon from a blank canvas. **Why:** user's explicit call, keeps the interaction model to one mode (draw) rather than two (draw + edit-a-suggested-shape).
- **Decision:** Fixed-Retiro and draw-your-own are **not** two separate architectural paths — one `MapView`, one local area-mode state (`{mode, polygon, center}`), both resolving to a single `polygon` value passed into the same `/api/query` call shape. **Why:** explicit user pushback on an earlier proposal that implied two separate screens/flows — "that sounds like what you're pointing towards... this should be handled much more cleanly."
- **Decision:** Map renders first (Retiro-centered by default) with a choice popup overlaid on top, not a separate blank interstitial before the map appears. **Why:** user's explicit call — starting on a visible, navigable map communicates the product's nature immediately, rather than requiring a click through an unexplained box first.
- **Decision:** Once results are showing, three distinct docked actions — new query (same area), redraw area (stays put, no recentering), switch to Retiro (explicit, separate button) — rather than folding redraw and switch-to-Retiro into one combined "change area" action as first proposed. **Why:** user flagged that "redraw" silently relocating the map to a fixed park elsewhere in the world would be confusing; the added implementation cost of a third button (one more call to the same underlying setter) was judged low enough to justify the clearer UX. **Trade-off:** one extra control in the docked bar.
- **Decision:** Client-side polygon validation: minimum 3 vertices, maximum 25 km² bounding area. **Why:** matches the already-validated prototype's vertex check; 25 km² was the user's own proposed cap, judged "large enough to cover a large walking area" without matching the GBIF cost/volume exposure of the documented unfiltered-birds-in-Retiro case (55,756 occurrences). Not derived from a formal cost model — a starting guardrail, revisitable later.
- **Decision:** `/api/query`'s `polygon` field becomes **required**, with no backend default fallback to `GBIF_POLYGON` — the frontend always sends an explicit polygon (fixed or drawn). Server-side validation duplicates the client-side checks and is authoritative, returning a 4xx before any GBIF/LLM cost, since `/api/query` is a public endpoint and client checks aren't a security boundary (per the existing Slice 2 "no protection may rely on an attacker not reading the code" posture). **Why:** user's explicit confirmation this is the "one code path" they wanted; consistent with the codebase's existing public-endpoint guardrail stance.
- **Decision:** Self-intersecting/invalid-geometry polygon handling is explicitly out of scope for this slice. **Why:** GBIF's real behavior on invalid WKT isn't yet empirically confirmed, and Leaflet-draw's default UI already makes such shapes awkward to draw by accident — deferred as a follow-up investigation rather than guessed at.
- **Decision:** Polygon coordinates must be included in the structured Cloud Run logging already emitted per query. **Why:** explicit user request, to be called out in the spec.
- **Decision:** A new consent-gated PostHog event for area-mode selection (fixed/draw, plus redraw/switch actions) will be added, via the existing `trackEvent()`/`hasConsent()` pipeline. **Why:** user agreed it's useful, cheap, low-risk product-usage signal.
- **Decision:** No `localStorage` persistence of the drawn polygon or mode — a page refresh always returns to the initial choice popup. **Why:** consistent with the app's existing no-server-session-state design principle; redrawing is cheap, and true persistence is better served later by the already-backlogged shareable-walk-link idea.
- **Decision:** Removed the reference to `spec-tool-llm-guardrails-gbif-query-040826.md` as "the most recent prior slice spec" from the new spec's Related Specs section after user correction — that spec was written up *after* the fact for a slice that wasn't actually built spec-first, so it doesn't establish a "most recent" precedent to point to.
