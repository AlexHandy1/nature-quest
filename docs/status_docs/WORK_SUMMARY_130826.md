## What was explored / learnt

- **GBIF occurrence records already carry a `media` array** (mostly iNaturalist-sourced photo URLs) on the same records the pipeline already fetches during ranking — confirmed live against the real Retiro polygon, zero extra API cost to use. Built as the first pass, then explicitly reconsidered.
- **Rejected GBIF occurrence media as the image source** after the user challenged it directly: it's an individual citizen-science observation's attached photo, not curated or vetted for representativeness — could be blurry, badly framed, or (rarely) attached to a misidentified record, with no quality signal in GBIF's API to select on. Switched to Wikipedia's summary API instead (same approach already validated in `prototypes/scripts/e2e_walk_spike_full_validation.py`), partly because it also sets up reuse for a possible future narrative-description feature. Full reasoning in ADR-013.
- **Real GBIF data-quality bug found via the throwaway smoke script**: `fetch_common_name`'s original "first English-tagged result" logic picked `"COMO"` (a banding-code abbreviation, tagged `language: eng` by a single low-quality source) for *Gallinula chloropus*, ahead of `"Common Moorhen"` (the real name, repeated across 8 independent sources in the same response). GBIF's `vernacularNames` endpoint has no preferred-name flag. Fixed by majority-voting across English-tagged names instead of taking the first match — re-ran the smoke script afterward and confirmed the fix live.
- **Caught and corrected an inconsistency mid-build**: `fetch_common_name`'s first draft used an inline `timeout=15.0` (carried over unreflectively from the prototype script) instead of `gbif_client.py`'s existing `REQUEST_TIMEOUT = 30.0` constant; then `wikipedia_client.py`'s first draft compounded it with a second, different timeout value. Fixed both to share the same 30.0s convention. `USER_AGENT` was kept in `wikipedia_client.py` despite `gbif_client.py` having none — a deliberate difference, not an inconsistency, since Wikimedia's API has an actual etiquette requirement for it and GBIF doesn't.
- **Considered and dropped "show all sightings"** (all raw observation points per species, not just the hotspot) after a detailed trade-off discussion: the "few hundred points, tens of KB" estimate only holds for a typical species — the single most-observed species in a result is by construction the one most likely to have thousands of occurrences, which would also just render as an indistinguishable dot-blob on the map. The user decided to drop this requirement rather than solve the capping/sampling problem now.
- **Desktop layout direction confirmed via a second throwaway prototype**: naive "widen the mobile overlay" port wastes screen space and reads worse than a real sidebar; the sidebar direction was chosen and built as the real implementation, with an explicit no-side-scroll requirement carried through into `index.css` (`overflow-x: hidden`, fixed 340px column) and verified structurally.

## Decisions and trade-offs

- **Decision:** Species images sourced from Wikipedia's summary API, not GBIF occurrence media or the iNaturalist taxon API. **Why:** representativeness/quality matters more than avoiding a new dependency for an identification aid; Wikipedia is already a validated precedent in this codebase (`e2e_walk_spike_full_validation.py`) and also sets up reuse for a future narrative feature. **Trade-off:** one more external dependency (with its own `User-Agent` requirement); common name and image are now a sequential-per-species lookup (image needs the resolved common name first), parallelized across species instead. Full detail: ADR-013.
- **Decision:** Common name resolved via majority vote across English-tagged GBIF vernacular names, not first-match. **Why:** a live smoke test caught a real bug (`"COMO"` beating `"Common Moorhen"`) — GBIF has no preferred-name flag, and result order isn't a reliable quality signal. **Trade-off:** none identified; this is strictly more correct and costs no extra latency (same single API call, just counts strings already in memory).
- **Decision:** Enrichment (common name + image) runs only on the final ~5 selected species, not every candidate scanned during ranking. **Why:** each species costs one GBIF call plus one Wikipedia call; scanning every ranked candidate would multiply that cost for no benefit, since only the final selection is ever shown to the user.
- **Decision:** "Show all sightings" (raw per-species observation points) dropped from this slice's scope entirely, not deferred with a specific follow-up plan. **Why:** explicit user call after a detailed trade-off discussion (payload/DOM-rendering cost scales with how commonly-observed a species is, not a fixed "few hundred points" assumption) — user decided it wasn't clearly valuable enough to solve the capping problem for right now.
- **Decision:** `expandedSpecies` state lives in `MapView`, not internally in `ResultsPanel` (a controlled component). **Why:** required so a marker click and a results-panel row click drive the same expand/collapse state and stay in sync — this was the whole point of porting the map-first accordion interaction from the mobile prototype.
- **Decision:** Desktop results panel is a real document-flow sidebar column, not a widened version of the mobile bottom-sheet overlay. **Why:** a throwaway prototype (`species_detail_desktop_prototype.html`) demonstrated the naive-widen approach wastes most of the screen behind a floating card; the sidebar keeps the same accordion interaction while using the extra width properly. **Trade-off:** two different CSS layout treatments for the same component (flex sidebar above 700px, absolute overlay below) rather than one unified layout — accepted as the right trade since the interaction model itself stayed identical across both.

## Session 2 — Wikipedia image URL trust hotfix

Separate topic from the rest of this file: user asked whether the Wikipedia/GBIF URLs rendered by the app could be redirected in production to sites/materials outside their control. Investigated via a code-search subagent, confirmed one real gap, fixed it as a hotfix branched off `main`, and merged the result back into this branch (`explore_audio_ai_narrative_and_open_router`).

### What was built

- **`app/backend/services/wikipedia_client.py`**: `fetch_species_image` now validates the `thumbnail.source`/`originalimage.source` URL from Wikipedia's summary API response against a new `TRUSTED_IMAGE_HOST = "upload.wikimedia.org"` constant (`_is_trusted_image_url`, checks `https` scheme + exact hostname via `urllib.parse.urlparse`) before returning it — an untrusted/malformed URL now returns `None` instead of being passed through.
- **`app/frontend/src/components/ResultsPanel.tsx`**: added the same check (`isTrustedImageUrl`, same host/scheme logic via `new URL()`) as a second, independent layer before rendering `<img src={s.image_url}>` — defense in depth, per explicit user request, so the frontend doesn't blindly trust the backend API response either.
- **Tests updated/added, TDD (RED confirmed before implementing each layer):**
  - `app/backend/tests/test_wikipedia_client.py`: existing fixtures switched from `example.com` to `upload.wikimedia.org`; three new tests cover rejecting an untrusted host, rejecting `http://` (non-https), for both `thumbnail` and `originalimage` fields.
  - `app/frontend/src/components/ResultsPanel.test.tsx`: existing fixture switched to `upload.wikimedia.org`; new test confirms an untrusted `image_url` falls back to the existing "No image available" UI rather than rendering the `<img>`.
- All 110 backend tests and 64 frontend tests pass. `tests/e2e_web_smoke_test.py` run headed against real local dev servers and live GBIF/Wikipedia data: 41/41 checks passed, including a live "Show me some birds" query confirming real `upload.wikimedia.org` URLs still render correctly (the fix doesn't false-positive on legitimate images).
- Committed on branch `hotfix_validate_wikipedia_image_host` (branched off local `main`), pushed and merged into `main` by the user as PR #19 (commit `87ea10d`). Then merged from `main` back into `explore_audio_ai_narrative_and_open_router` (merge commit `00e0bbe`), so this branch now carries the fix.

### What was explored / learnt

- Traced every Wikipedia/GBIF URL construction site in `app/` (backend + frontend) via a code-search subagent. **GBIF species links** (`ResultsPanel.tsx`: `` `https://www.gbif.org/species/${s.species_key}` ``) and the **Wikipedia summary API call** (`wikipedia_client.py`: `f"{WIKIPEDIA_SUMMARY_URL}/{quote(title)}"`) were already safe — domain hardcoded, only a numeric ID or a quoted species name fills the path, so third-party data can't redirect the link to another domain.
- The one real gap was the **species image URL**: `wikipedia_client.fetch_species_image` took the *entire* URL (including host) verbatim from Wikipedia's REST API JSON response and passed it straight through to `<img src>` with no validation — a compromised/spoofed upstream response could have pointed the app at an arbitrary domain, not just a path within a trusted one.
- Verified live (`curl` against `en.wikipedia.org/api/rest_v1/page/summary/Red_fox`) that both `thumbnail.source` and `originalimage.source` are always served from `upload.wikimedia.org` before hardcoding that as the trusted host — didn't just assume the `wikimedia.org` domain family.
- Confirmed the correct fix location is the backend, not just the frontend: the untrusted data enters the system at the point the backend calls Wikipedia's API, so validating there protects any future consumer of the `/api/query` response, not just this one React component. Frontend check added afterward as an explicit additional layer, not a replacement.

### Decisions and trade-offs

- **Decision:** Validate the Wikipedia image URL's host against an exact-match allowlist (`upload.wikimedia.org`) in both the backend (at the point the untrusted API response is consumed) and the frontend (at the point it's rendered). **Why:** backend validation protects the trust boundary where third-party data enters the system and any consumer of the API; frontend validation is defense-in-depth per explicit user request, given the depth of the investigation already done. **Trade-off:** none significant — a `upload.wikimedia.org` becoming stale (Wikimedia changing image-hosting domains) would silently degrade to "no image" rather than error, which is an acceptable failure mode for a non-critical enrichment field.
- **Decision:** No comments added explaining the new validation logic. **Why:** explicit user feedback mid-session — comments weren't already a convention in this file for this kind of addition, and the existing `USER_AGENT` comment in `wikipedia_client.py` was removed as noise when the user reviewed the diff.
