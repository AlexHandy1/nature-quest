## What was built

Final design: ranks species by `SUM(occurrence_count)` from `fact_sorted_by_cell.parquet`, takes the smallest N covering 99% of cumulative occurrence volume (`compute_top_n_cutoff`), looks up each via ChecklistBank's per-taxon endpoint (`fetch_common_names_for_taxa`, 20 concurrent workers, pooled `requests.Session`), dedupes multiple English names per species via `pick_best_name` (rejects banding-code abbreviations, informal lowercase entries, and non-ASCII/mistagged names, then picks the longest survivor), and joins the result onto `species_dimension.parquet` via DuckDB, writing `prototypes/scratch/species_dimension_with_common_names.parquet`.
- Ran the full batch twice (6m30s and 6m24s wall time) against the real ChecklistBank API (pinned COL XR dataset `315557`, resolved live via `resolve_pinned_col_xr_dataset_key()` against GBIF's `CLB_DATASET_KEY` registry identifier — unchanged from the 19 Oct session's finding).

## Final output (species_dimension_with_common_names.parquet)

- Total rows: 1,322,269. With `common_name`: 59,186 (4.48% of rows). Without: 1,263,083.
- The 4.48% figure is low by row count but covers 99% of actual GBIF occurrence volume — the fact table only has 917,827 distinct species (not 1.32M; `species_dimension` is sourced from a broader, less-filtered BigQuery table), and occurrence volume is heavily long-tailed: top 50 species alone cover 25% of all occurrences (all 50 had a common name), top 106,247 cover 99%, top 10,000 already cover ~93%.
- Cutoff N is recomputed each run via SQL (cumulative-sum window function over species ranked by total occurrence), not hardcoded — came out to 106,247 both times.

## What was explored / learnt

- **ChecklistBank's bulk `/dataset/{key}/vernacular` endpoint hard-caps `offset` at 100,000** (confirmed via live 400 response and the OpenAPI schema: `"offset": {"maximum": 100000}`). The pinned COL XR release has 399,396 English-language vernacular rows, so plain pagination can only reach the first ~101,000 — this blocked the bulk-crawl approach scoped in the 19 Oct session partway through implementation.
- **Sector-based partitioning doesn't fully solve the cap.** `sectorKey` (ChecklistBank's per-row provenance field, naming which external source dataset contributed that vernacular name — not a taxonomic or alphabetical grouping) splits most of the 399k rows into 299 sectors, 298 of which are well under 100k — but one sector (`65865`) alone has 157,491 English rows, over the cap by itself, with no further filter dimension (`sectorDatasetKey` is 1:1 with `sectorKey`; `q` does whole-word full-text matching, not prefix/substring) to split it further.
- **`sectorKey` is not species-exclusive** — verified directly: Pica pica's 5 English names span 3 different sectors. It's a per-row provenance tag, not a taxonomic partition, confirmed by checking a known multi-name species.
- **Pagination order is stable/deterministic** (verified: 3 repeated identical calls returned byte-identical ordered results) but this doesn't help — the `offset<=100000` cap is a hard server-side validation rule independent of sort order, and the endpoint exposes no `sortBy`/`reverse` parameter anyway.
- **`/dataset/{key}/export` is impractically slow** — tested `format=DWCA&extended=true` hoping for a vernacular-names-only bulk file; it hung with zero response for 2+ minutes and was killed. Consistent with the 19 Oct session's finding that this endpoint does slow synchronous full-tree generation regardless of format.
- **`/dataset/{key}/nameusage/search`'s `facet=TAXON_ID`/`facet=SECTOR_KEY` is a hierarchical rollup, not a flat enumeration** — tested live; facet bucket counts reflect descendant-inclusive classification totals (one bucket showed `count: 7,897,384` out of a 7.99M total), not distinct leaf-taxon counts. Dead end for cheaply getting "the full list of taxonIDs with an English name."
- **No GBIF/ChecklistBank vernacular-names table exists in public BigQuery** — `bigquery-public-data.gbif` only has an `occurrences` table (already our fact-table source).
- **Pivoted to a product-aligned strategy instead of full-table completeness**: rank by occurrence volume, bound the per-taxon lookup to a cutoff covering 99% of real occurrences, rather than trying to enumerate ChecklistBank's whole COL XR tree. Validated the per-taxon endpoint's real cost empirically (not estimated): 50-taxon random sample → 0.55s/10 workers (18% hit rate); 300-taxon top-occurrence sample → 1.31s/20 workers (55.7% hit rate, 0 errors) → extrapolated ~7.7 min for the full 106,247 at 20 workers; actual full run took 6m23-30s, consistent with the estimate.
- **Dedup policy iteration**: original "shortest name wins" policy produced real, concrete bugs when inspecting actual top-50/top-100 output — banding-code abbreviations surfacing as names (`COST`, `TV`, `BASW`, `GRTI`, `CORA`, `EURO`), one outright wrong species name (`Macaw` for Buteo jamaicensis/Red-tailed Hawk), and an Indigenous-language name mistagged `language: eng` (`Tsįįłkaałii bitłʼaaʼ halchíʼígíí` for Red-bellied Woodpecker). Tested 3 replacement heuristics (filtered+shortest, filtered+longest, filtered+closest-to-2-words) against real candidate lists for the top 50 species; filtered+longest (reject all-caps short codes, lowercase-starting informal names, non-ASCII) produced the most standard/correct names and was adopted. Residual known trade-off: "longest wins" still occasionally surfaces verbose regional-qualifier variants (e.g. `Virginian Nightingale` for Northern Cardinal, `North American Red-winged Blackbird`) instead of the plain name a US user would expect — not a bug, an accepted cost of the heuristic.
- **GCS-fetch vs. bake-in for serving this data in production**: compared on latency (real measured local-disk baseline 0.447-0.795s from the 9 Oct prototype logs; GCS/`httpfs` estimated, not measured, at +50-350ms), cost (negligible either way, <$1-5/month at current scale), security (GCS-fetch introduces a new live runtime dependency needing least-privilege IAM — separate read-only app SA vs. write-only refresh-job SA, never combined — since write-access misconfiguration is a real integrity risk even though the data itself is non-sensitive), and architecture (GCS-fetch decouples code deploys from data refreshes; bake-in couples them but gets free historical versioning via Cloud Run revisions). Decided GCS-fetch — see ADR-016.

## Decisions and trade-offs

- **Decision: common names sourced via per-taxon ChecklistBank lookup (`/dataset/{key}/taxon/{id}/vernacular`) for the top-N species by occurrence volume (N = smallest count covering 99% of cumulative occurrences), not a bulk crawl of the whole COL XR vernacular table.** **Why:** the bulk endpoint's 100k offset cap makes full-table completeness unreachable (one sector alone exceeds it), and occurrence volume is so long-tailed that 99% coverage only needs ~106k species out of 1.32M dimension rows anyway — chasing full-table completeness would mean paying for ~1.3M speculative lookups to cover species that almost never appear in real queries. **Trade-off:** species outside the top-N get `common_name = NULL` (falls back to scientific name in the UI) — an explicit, deliberate gap, not a silent one.
- **Decision: dedup policy is "reject junk (all-caps short codes, lowercase-starting informal names, non-ASCII), then pick the longest survivor," not "shortest wins."** **Why:** shortest-wins was tested against real top-50/top-100 output and produced concrete, named bugs (banding codes, a wrong species name, a mistagged foreign-script name); longest-after-filtering fixed all three while three alternatives (filtered+shortest, filtered+closest-to-2-words) were tested side by side and scored worse. **Trade-off:** occasionally picks a verbose/regional-qualifier name over the plain standard one a user would expect (e.g. `Virginian Nightingale`, `North American Red-winged Blackbird`) — accepted as better than the alternative failure modes.
- **Decision: serve `fact_sorted_by_cell.parquet` / `species_dimension_with_common_names.parquet` to production from a GCS bucket via DuckDB `httpfs`, not baked into the Docker image.** **Why:** at this project's current scale, GCS-fetch's cost and latency downsides are small and bounded, while bake-in's downsides (code/data deploy coupling, image-size scaling cost, needing a full CI/CD smoke-test-gated pipeline built from scratch) compound over time; GCS-fetch also gives independent failure domains for code vs. data releases. **Trade-off:** introduces a new live runtime dependency and bucket-IAM surface needing explicit least-privilege design (separate read-only/write-only service accounts); the GCS/`httpfs` latency estimate (+50-350ms) is reasoned, not measured — should be validated with a real test before/shortly after building this. Full ADR: `docs/decisions/ADR-016-local-index-data-deployment-gcs-fetch-not-bake-in.md`.
- **Decision (deferred, explicit): monthly automated data-refresh pipeline is parked for a future session.** The user's stated plan for next session is a one-time, upfront, manual bucket setup to get a first version live — not the full unattended monthly pipeline. COL XR version pinning stays manual/offline-review, accepted explicitly (not automated drift detection).
