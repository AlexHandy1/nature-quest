## What was explored / learnt

- **GBIF rate-limiting is sensitive to search area size**, not just concurrent request count — this session's 50km²→25km² revert is a second, independent data point alongside the earlier `MAX_CONCURRENT_GBIF_REQUESTS` mitigation already logged in `FEATURE_IDEAS_BACKLOG.md`'s "Rearchitect GBIF data dependency" section.
- **`taxonRank`'s schema has no `species` value** (`kingdom, phylum, class, order, family, genus` only, per `anthropic_client.py`'s `QUERY_SCHEMA_TOOL`) — confirmed via user decision that species-specific queries should be tested as degrading to the nearest genus, not as an unsupported-rank failure case.

## Decisions and trade-offs

- **Decision:** `ARCHITECTURE.md` should describe only what's built and how it works today, not scope/roadmap/deferred status. **Why:** explicit user direction — that material already lives in `docs/prds/`, `docs/specs/`, `docs/status_docs/`, and duplicating it in the architecture doc had already gone stale/self-contradictory once (the "waypoint ordering not built" line).
- **Decision:** Species-specific eval queries assert resolution to the nearest supported genus rank, not an empty/unresolved result. **Why:** user's explicit call when asked, since `species` isn't a real option in the taxon-resolution schema — an LLM asked for a species-level result has no correct rank to return except its nearest supported parent.
- **Decision:** Area cap reverted to 25 km² rather than tuning down concurrency/rate-limit mitigations further. **Why:** fastest, safest fix for a production reliability issue; a proper GBIF-scaling fix (local data store, per the existing backlog item) is a larger, separately-scoped piece of work, not a hotfix.
