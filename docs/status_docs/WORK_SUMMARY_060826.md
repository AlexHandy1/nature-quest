## What was explored / learnt

- **DeepEval's local tracing gives no actual console visibility without a Confident AI account** — contradicts what the docs implied. Verified empirically: `@observe`/`update_current_span` produced only an HTTP-log line and `"[Confident AI Trace Log] No Confident AI API key found. Skipping trace posting."`, never the actual span input/output. Checked the installed CLI directly: `deepeval view` unconditionally calls `upload_and_open_link()` (cloud-only). Also hit a real library bug: `@observe(type="tool", name=...)` crashes (`ToolSpan() got multiple values for keyword argument 'name'`) because `Observer` reads `name` out of `observe_kwargs` into `self.name` without removing it, then `ToolSpan(**span_kwargs, **self.observe_kwargs)` spreads it twice — worked around by dropping `name=` on tool-type spans, but ultimately dropped DeepEval entirely once it became clear it wasn't earning its dependency cost (no metrics ever used either — a deterministic dict-equality check doesn't need an LLM-judge metric like `GEval`).
- **PostHog's OTel-based AI Observability approach (as originally spec'd: `AnthropicInstrumentor` + `PostHogSpanProcessor`) has a real architectural mismatch with REQ-020.** Read the actual `posthog-python` GitHub examples (`examples/example-ai-anthropic/chat.py`) — `posthog.distinct_id` is set once as an OpenTelemetry `Resource` attribute at `TracerProvider` construction (process-startup-level), not settable per-request. Found and switched to `posthog.ai.anthropic.Anthropic` — a wrapper subclass of the real Anthropic client accepting `posthog_distinct_id`/`posthog_trace_id`/`posthog_privacy_mode` as **per-call** kwargs on `.messages.create()`, reading its actual source (`posthog/ai/anthropic/anthropic.py`, `posthog/ai/utils.py`) to confirm it captures `$ai_input`/`$ai_output_choices` (full sanitized request/response), tokens, latency, http status per call.
- Confirmed `posthog.ai.openai.OpenAI` also just subclasses `openai.OpenAI` and passes `**kwargs` through — meaning a future OpenRouter migration (user's stated direction, `openai.OpenAI(base_url="https://openrouter.ai/api/v1", ...)`) is a straightforward wrapper-class swap, not a re-architecture. Minor nuance: `$ai_provider` would read `"openai"` for OpenRouter calls (gateway, not origin model), but `$ai_model` still carries the real model string.
- PostHog's Python client batches events via an internal queue + background thread — `capture()` returns immediately without guaranteeing delivery; `client.flush()` blocks until the queue drains. Without it, a short-lived test process can exit before the event is actually sent. Added `ai_observability._posthog_client.flush()` to the capture eval test; user confirmed the event landed in the real PostHog dashboard.
- GBIF's `occurrence/search` returned transient 503s twice during Tier 2 eval pagination (birds, ~190 pages) — matches the documented precedent in `WORK_SUMMARY_250726.md` ("not reproduced on retry — treated as GBIF-side flakiness, not a code bug"); both times passed on retry.
- Clarified for the user (concurrency mechanics): FastAPI dispatches sync `def` routes to a background thread pool (real OS threads — why `query_budget.py` needs a real `threading.Lock`), while `async def` handlers run cooperatively on the single event-loop thread via `await`. `handle_rate_limit_exceeded` had to become `async def` specifically to `await request.json()` — slowapi's rate-limit check intercepts *before* FastAPI parses the route's `QueryRequest` body (it only reads the caller's IP via `get_remote_address`), so the body is still unconsumed and safe to read there.
- Investigated a reported "consent banner not visible" issue via `agent-browser` — confirmed via a fresh browser session (`agent-browser open http://localhost:5173/`, screenshot, computed-style check: `display: flex; visibility: visible; opacity: 1`) that the banner renders correctly. Root cause was stale `localStorage['analytics-consent']` in the user's own browser from earlier manual testing (`ConsentBanner` correctly returns `null` once a choice is stored) — confirmed by the user via incognito. Not a bug.

## Decisions and trade-offs

- **Decision:** REQ-019 built on `posthog.ai.anthropic.Anthropic` (wrapper client), not OpenTelemetry `AnthropicInstrumentor`/`PostHogSpanProcessor` as the spec originally specified. **Why:** the OTel approach's `distinct_id` is process/tracer-level (`Resource` attribute), incompatible with REQ-020's genuinely-per-request `distinct_id`; the wrapper client's `posthog_distinct_id` kwarg is per-call natively, and is less infrastructure (no `TracerProvider`/`Resource`/span-processor setup). **Trade-off:** deviates from the committed spec's REQ-019/§6 ("`AnthropicInstrumentor().instrument()` + `PostHogSpanProcessor`") and §10 (dependency list still says `opentelemetry-instrumentation-anthropic`) — **spec not yet updated, explicitly deferred to the documentation pass** (tracked as pending task #1 this session).
- **Decision:** Dropped the `deepeval` dependency entirely from the eval suite. **Why:** its tracing gave zero local visibility without a paid/cloud Confident AI account (verified, see above), a real library bug was hit, and no DeepEval metric was ever actually used (correctness is a plain deterministic dict comparison, not something needing an LLM judge). Real visibility now comes from plain `print()` of the full request (model/system prompt/tool schema/query) + response, plus PostHog's dashboard for the real production-parity trace. **Trade-off:** REQ-024's spec text ("built on DeepEval") is now stale — also deferred to the docs pass.
- **Decision:** `resolve_taxon_filter()` gained an `on_response` callback param rather than changing its return type. **Why:** preserves the existing `dict | None` contract for all other callers/tests while letting `routers/query.py` extract token usage from the raw response for REQ-017's logging.
- **Decision:** `routers.query._resolve_taxon_filter()` now returns `(taxon_filter, usage_dict)` — this one **did** change shape and required updating existing test mocks in `test_query_outcomes.py` and `test_query_rate_limit.py` (previously `return_value={"taxonRank": ...}`, now `return_value=({"taxonRank": ...}, {})`).
- **Decision:** `services/rate_limiter.py`'s `handle_rate_limit_exceeded` is `async def`, reading the query text via `await request.json()`. **Why:** REQ-017 wants the query text logged even for rate-limited requests; slowapi intercepts before FastAPI's own body parsing, so this is the only place to get it. Safe because slowapi's rate check never touches the body itself.
- **Decision:** `InterestForm.tsx`/`InterestForm.test.tsx` left in place, unreferenced by `App.tsx` but not deleted. **Why:** user chose to match the backend's existing "dormant until a future cleanup slice" convention (`CON-001`) for consistency, even though `CON-001`'s literal wording only covers the backend route/model.
- **Decision:** `QueryForm` is one-shot (form → terminal result message, "Refresh the page to search again"), not resubmittable in-place. **Why:** explicit user call — "this is very much just in a state to prove this works end-to-end in production," map view (later PRD slice) is the real intended UX, not worth building repeat-query interaction now.
- **Decision:** Resolved species list shows name + count only, no kingdom badge, no hotspot lat/lon. **Why:** those fields have nowhere meaningful to render before map rendering exists (later PRD slice).
- **Decision:** Loading state disables both the input and submit button, with explicit copy ("The form can't be edited until this finishes"). **Why:** user feedback mid-session — the original version only disabled the button and didn't make the one-shot/wait behavior clear enough.
- **Decision:** Dropped `"or \"something rare\""` from the query box placeholder. **Why:** rarity/`sort` is explicitly out of scope this slice (REQ-007/§9) — user flagged this had been discussed and decided before, shouldn't have resurfaced in copy.
