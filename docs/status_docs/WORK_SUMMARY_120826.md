## What was explored / learnt

- **Extensive, ultimately unsuccessful automation of Leaflet-draw via `agent-browser`'s synthetic mouse events.** Manual, by-hand testing of the exact same interaction (via `agent-browser` refs/clicks in an interactive exploration) worked reliably — real polygon drawing, oversized-area rejection, and a geolocation override all confirmed working live. But driving the identical click sequence programmatically from the Python smoke-test script was flaky across many iterations: dropped vertices, "shape edges cannot cross" errors, and inconsistent results even after several rounds of fixes (longer settle delays, a verify-and-retry loop with `Escape`-based cancellation, geometry/centering changes). Root cause was never conclusively identified — plausible contributors include synthetic CDP mouse events landing in Leaflet-draw's click-vs-drag disambiguation window, and system load from a **stale `agent-browser` daemon left running for days** (confirmed and killed mid-session) degrading timing-sensitive interactions. After the user's own repeated headed test runs kept failing the same way even post-cleanup, the decision was made to cut scope rather than keep sinking time into it (see Decisions).
- **`gbif_unavailable` on drawn-area queries was investigated as a possible real bug** (asymmetric failure — fixed-Retiro queries never failed, drawn-area queries failed consistently) before concluding it was very likely GBIF rate-limiting responding to a burst of automated requests (5 real GBIF calls fired in ~15-20s by the script, far faster than any human), not a polygon-handling defect — corroborated by the user's own manual testing working fine. Winding-order/invalid-WKT was considered and set aside once the user reported manual success, since a structural geometry bug would have failed for them too.
- **Diagnosed and fixed a real operational issue mid-session**: a uvicorn backend process had been started with the wrong working directory (repo root instead of `app/backend`), causing "Could not import module main" and pinning ~88% CPU; restarted correctly. Separately diagnosed and killed two `agent-browser` daemon processes that had been running since the prior Monday and Thursday, plus their spawned Chrome-for-Testing processes — a likely contributor to "suddenly very slow" system behavior reported mid-session.
- Confirmed via live `curl`-equivalent testing that `agent-browser`'s `set geo <lat> <lon>` + `mouse move/down/up` primitives are sufficient in principle to drive geolocation override and polygon drawing — the capability gap was reliability/timing, not missing functionality.

## Decisions and trade-offs

- **Decision:** Area selection redesigned from a popup/funnel + custom confirm button to a persistent `AreaControl` widget + Leaflet-native auto-confirm. **Why:** manual testing found the spec's original design (built faithfully first) had multiple real, user-blocking problems. **Trade-off:** the frontend now diverges materially from `spec-tool-draw-your-own-area-100826.md`'s written state machine (REQ-005 through REQ-009) — see ADR-012 for the full reasoning, alternatives considered, and consequences.
- **Decision:** No automated end-to-end coverage for the draw-your-own-area flow (drawing, oversized-area rejection, geolocation, redraw, mode-switching) in this slice. **Why:** the user's explicit call after ~an hour of repeated automation failures on already-manually-validated functionality — "let's not get blocked on this smoke test step." **Trade-off:** this is a real, accepted coverage gap for a slice whose core feature is exactly this flow; manual verification is the only current check. Documented explicitly and in detail in `tests/e2e_web_smoke_test.py`'s trailing comment block so it isn't silently forgotten.
- **Decision:** Security review findings (global daily LLM budget, per-instance rate-limiter/budget state on Cloud Run, unverified `X-Forwarded-For` handling, permissive polygon-prefix validation, unbounded `distinctId`) were logged but not fixed this session. **Why:** user's explicit call — "this is fine and write up can be kept in that report." **Trade-off:** these remain open, real findings for a future session; full detail in `tests/.security_review_output/20260812_133720/report.md`.
- **Decision:** `simplify` and `security-reviewer` skills copied verbatim (not modified) into `ai-agent-knowledge-bank`, with attribution added crediting brianlovin/agent-config despite the light customisations already made. **Why:** explicit instruction to preserve exact text and credit the source.
- **Decision:** README simplified aggressively — no "Current state" section, no prototype-validation narrative. **Why:** explicit user request for a much simpler README; the detailed current-state narrative duplicated what `ARCHITECTURE.md` already covers in more depth.

### 0. Mobile UX discussion + prototyping (do this first, before anything below)
Current mobile UX has enough distinct problems (see items 1-5) that it warrants a focused design discussion rather than one-off patches — likely with a few throwaway local prototypes (`/prototype`) to sanity-check direction (e.g. navbar layout, geolocation affordance, icon-heavy controls) before committing to real implementation. Do this before starting items 1-9 below.

### Production issues spotted (mobile UX) — specific symptoms for that discussion, not a fix list to start from
1. **Header/navbar color inconsistency**: the header bar renders a noticeably different (lighter) brown on mobile vs. desktop — unexpected, needs investigation (likely a CSS specificity/media-query interaction, not intentional).
2. **`AreaControl`'s second row of buttons overflows the viewport** on narrow phones (reported on iPhone SE) — the "Exploring: ..." row isn't fully visible/reachable.
3. **The whole top navbar is "crumpled" and not fully visible on mobile** — hard to see and hard to use to search. The mobile viewport check added this session (`tests/e2e_web_smoke_test.py`) only verifies the map retains a minimum height and there's no horizontal overflow — it does not catch this class of layout/usability problem.
4. **Drawing on the map is hard to use**, independent of the automation flakiness noted above — this is about real end-user UX, not just test automation. May be out of scope for a "quick" slice, but flagged.
5. **Geolocation ("Use my location") is hard to access and doesn't behave as expected on mobile.** Consider leaning more heavily on icons/mobile-native patterns rather than the current text+icon button.

### Results panel / map outcome state (currently a placeholder)
6. Show **common names**, not scientific names, in the results panel.
7. **Add a picture per species** — proposed to load only when that species' marker is clicked (not eagerly for all 5), to control cost/payload.
8. **Add a link to each species' GBIF entry** so users can go elsewhere for full detail. Explicit decision already leaning this way: do **not** try to fit descriptions directly in the UI — costly to generate/maintain and unreadable on mobile. Link out instead.
9. **Consider showing all observation points (not just the hotspot) for a species when its marker is clicked** — dots for every real observation, to build user trust in the data. Flagged as possibly not mobile-friendly; pick up in the mobile UX discussion (item 0) rather than deciding now.

### Constraints / user-facing transparency
10. **Surface the query's real constraints somewhere in the UI**, subtly if possible (a click-through page is acceptable if inline isn't feasible): observations are limited to since 2023, only 5 species are returned per query, and data is sourced only from GBIF.
11. **Review raising the area cap from 25 km² to at least 50 km²** — 25 km² was called out in the original spec as "a starting guardrail, revisitable later," and may be too small for more exploratory searches.
