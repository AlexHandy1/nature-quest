## What was explored / learnt

- DuckDB's `httpfs` has no native GCP ADC/metadata-server auto-discovery — it only understands a bearer token or HMAC key via `CREATE SECRET`. Chose a Terraform-generated, long-lived HMAC key over a self-managed OAuth token (would need per-request refresh logic), a sidecar/proxy, or a GCS volume mount (rejected as unmeasured for DuckDB's scattered Parquet row-group access pattern — a generic FUSE layer's behaviour under that access pattern isn't documented by Google and sits directly on top of the latency this architecture exists to protect).
- Measured GCS/`httpfs` latency empirically rather than trusting the original estimate: cold query ~3.0s, warm ~0.44s, matching local-disk performance — but this was measured by reusing one already-authenticated connection across repeated queries in a loop, which turned out not to reflect how production actually calls it (see Blockers).
- Measured `candidate_cells`' cost across area sizes and latitudes empirically before picking the new 2,000 km² cap — confirmed safe (well under 1s) even at extreme near-Arctic latitudes, where the fixed-degree grid step samples more points per unit area.
- Found that a common-name-first Wikipedia lookup can occasionally match a real article for a taxonomically different species (e.g. `Pica pica`'s common name "Black-billed Magpie" matched the American black-billed magpie's article, not the Eurasian magpie actually present in Madrid — confirmed by looking up the scientific name directly, which resolves correctly). Accepted as a moderate, un-fixed slippage risk for this general-narrative use case.
- Caught and corrected a mistake mid-session: `AreaSizeWarning.tsx` was deleted when the old area cap was removed (correct at the time), but then wrongly left removed when the new cap was reinstated — mischaracterized as a "pre-existing UX gap" rather than the real regression it was. Restored with updated copy.
- Caught a separate staging mistake via `git status`: that same `AreaSizeWarning` deletion had never actually been staged in the commit that claimed to remove it — fixed with a follow-up commit.
- **Live production latency investigation** (most recent, still open): ran 5 timed queries against the production URL and found 3.4–4.5s time-to-first-byte — worse than initially reported (1–2s) and worse than local testing suggested. `curl`'s own timing breakdown ruled out DNS/TLS/connect overhead (~0.2–0.3s, not the cause). Pulled structured Cloud Logging timestamps (`log_query_submitted` → `log_llm_taxon_filters_resolved` → `log_species_selected` → `log_species_enriched`) across all 5 runs and found a consistent split: LLM taxon resolution ~1.7–3.0s, the DuckDB query+auth phase ~1.3–1.7s, Wikipedia enrichment ~0.2–0.26s. Root cause identified for the DuckDB phase: `open_index_connection()` is called fresh on every single request with no connection or credential reuse — every request pays `INSTALL`/`LOAD httpfs`, two fresh Secret Manager API round-trips, and a cold DuckDB connection, none of which were part of the earlier "warm" latency measurement (which reused one connection across repeated queries in the same process). The LLM-side cost (1.7–3.0s) is separate and pre-existing — OpenRouter's "Balanced" routing mode picks the backend/tier per call unpredictably (already flagged in ADR-015), unrelated to this migration.

## Decisions and trade-offs

- **Decision: local DuckDB/Parquet index replaces all live GBIF taxon-resolution and occurrence-search calls.** **Why:** removes GBIF rate-limiting as a live production reliability problem (the root cause of a past area-cap revert, per `WORK_SUMMARY_150826.md`). **Trade-off:** loses the clean "unrecognized taxon" vs. "no occurrences here" distinction GBIF's `species/match` gave — both now surface as `no_results`; data freshness becomes a deliberate, separately-deferred concern (today's data is a one-time manual upload, no automated refresh yet).
- **Decision: HMAC key, not a self-managed OAuth token, for DuckDB's GCS auth.** **Why:** avoids the app minting/refreshing a short-lived token on the query's hot path; the HMAC key is a static credential matching the existing Secret Manager pattern. **Trade-off:** per-request Secret Manager fetches turned out to have a real, previously-unmeasured cost in production — see the open latency investigation above.
- **Decision: reinstate the polygon area cap at 2,000 km², not remove it entirely or keep the old 25km².** **Why:** `candidate_cells`' own Python-side grid-sampling has no bound at all otherwise; 2,000 km² was measured, not guessed, to stay fast even at extreme latitudes. **Trade-off:** still a fixed number a user might bump into, though ~80x more permissive than before.
- **Decision: accept the common-name/wrong-species-match risk in Wikipedia enrichment rather than add verification.** **Why:** moderate slippage risk judged acceptable for general narrative text, not a species-identification feature.
- **Decision: leave `tests/test_smoke_llm.py` and the broader eval strategy untouched this session.** **Why:** the user wants to revisit the whole eval approach together, not patch it piecemeal alongside an unrelated migration.

## Blockers

- **Production query latency is 3.4–4.5s end-to-end, driven mainly by two separable costs**: (1) the LLM taxon-resolution call (1.7–3.0s, pre-existing, OpenRouter routing variance) and (2) `open_index_connection()` rebuilding the DuckDB connection and re-fetching Secret Manager credentials on every single request (1.3–1.7s, new, root-caused but not yet fixed). Proposed fix for (2), not yet implemented: cache/reuse the DuckDB connection and HMAC credentials across requests within a process — safe since the HMAC key doesn't expire, unlike a short-lived token.
