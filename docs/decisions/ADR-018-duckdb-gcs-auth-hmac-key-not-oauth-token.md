# ADR-018: DuckDB's GCS Access Uses a Long-Lived HMAC Key, Not a Self-Managed OAuth Token

## Status
Accepted

## Date
2026-10-21

## Context

ADR-016 decided the fact/dimension Parquet files are served from a private
GCS bucket, read live via DuckDB's `httpfs` extension (`services/species_index.py`,
`open_index_connection`). That ADR didn't settle *how* DuckDB authenticates
to GCS — it's a separate question from *where the data lives*.

DuckDB's `httpfs` is a generic, cloud-provider-agnostic extension (it also
speaks S3 and Azure); it has no concept of GCP's metadata-server/Application
Default Credentials auto-discovery that every other GCP client library in
this codebase relies on (`google-cloud-secret-manager`, etc.). It only
understands being handed a credential directly, via `CREATE SECRET`: either
an OAuth2 bearer token or an HMAC access-key/secret pair. Confirmed
empirically — querying the bucket with no credential configured returns an
explicit 403 naming exactly these two options, nothing else.

## Decision

Use a long-lived HMAC key (`google_storage_hmac_key`, `infra/gcs_index_data.tf`)
for the read-only app identity (`nature-quest-run`), generated by Terraform
and stored in Secret Manager (`gcs-index-data-hmac-key-id`/
`gcs-index-data-hmac-secret`) alongside the app's other runtime secrets.
`open_index_connection` fetches both values via the existing
`secret_manager_client.fetch_secret` pattern and configures them with
`CREATE SECRET (TYPE GCS, KEY_ID '...', SECRET '...')`, only when running on
Cloud Run (`K_SERVICE` set) — locally, no GCS/auth configuration happens at
all, and callers pass local file paths instead (see `routers/query.py`'s
`FACT_PARQUET_PATH`/`DIMENSION_PARQUET_PATH`, required env vars with no
hardcoded default, so local dev can never accidentally point at the
production bucket).

## Alternatives Considered

### App mints and refreshes a short-lived OAuth2 bearer token itself
- Pros: no long-lived credential to store; matches how the app already
  authenticates to Secret Manager under the hood (via `google-auth`'s
  credential-refresh machinery).
- Cons: OAuth2 access tokens expire in roughly an hour. Since
  `open_index_connection` is called per-request, the app would be
  responsible for minting (and later, refreshing) a token on every query's
  hot path — a live round-trip to GCP's auth endpoint before the real
  DuckDB query even runs. `httpfs` doesn't call this refresh logic itself;
  whoever hands it a bearer token owns that token's whole lifecycle.
- Rejected because: this trades a one-time Terraform-managed credential for
  an ongoing per-request latency and complexity cost, for a security benefit
  (shorter credential lifetime) that doesn't meaningfully change the actual
  exposure here — the HMAC key is already scoped to read-only access on one
  bucket via IAM, not broad account credentials.

### A sidecar/proxy holding real ADC logic, exposing a local token endpoint
- Pros: decouples token-refresh logic from the main app process entirely.
- Cons: a new deployable component, new failure mode, for a problem this
  app's request volume doesn't actually need solved that way.
- Rejected because: disproportionate to current scale; worth reconsidering
  only if this app's traffic or dependency surface grows substantially.

### GCS volume mount (Cloud Run's native Cloud Storage FUSE support)
- Pros: would eliminate this whole question — the bucket would appear as a
  local filesystem path, authenticated by Cloud Run's platform layer via
  the attached service account, with zero auth code in the app at all.
- Cons: Parquet reads are scattered (footer first, then specific
  column-chunk byte ranges for row-group pruning) — exactly DuckDB's
  `httpfs` is built to request only the needed ranges efficiently; a
  generic FUSE layer's behavior under this access pattern is unverified
  and not benchmarked by Google's own documentation. This sits directly on
  top of the latency win this whole local-index architecture exists to
  capture (see ADR-017), so an unmeasured risk there is a bigger concern
  than for a typical read-mostly workload.
- Rejected because: untested for this specific access pattern, against an
  already-measured, working alternative (`httpfs` + bearer token: cold
  3.0s / warm 0.44s against the real bucket, matching local-disk
  performance). Worth benchmarking properly if the HMAC-key approach ever
  becomes a real limitation.

## Consequences

- **No app-level token-refresh logic exists or is needed.** The HMAC key
  is a static credential; the only operational concern is rotation, not
  expiry.
- **The credential's value is generated by Terraform, not pasted in by a
  human** — unlike `anthropic-api-key`/`openrouter-api-key`, which are
  empty Secret Manager containers a human populates out-of-band. The raw
  HMAC secret does pass through Terraform state (marked sensitive by the
  provider, redacted from `plan`/CLI output) — the same trust boundary the
  tfstate bucket's restricted IAM already covers.
- **GCS volume mounts remain unevaluated for this workload.** If `httpfs`'s
  bearer-token/HMAC model ever becomes a real constraint, benchmark the
  volume-mount path against this architecture's actual Parquet
  row-group-pruning access pattern before switching, rather than assuming
  it performs equivalently.
